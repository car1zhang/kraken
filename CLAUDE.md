# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

kraken (`k`) is a macOS CLI/TUI for managing live Claude Code and Codex sessions across tmux: list them (`k ls`), watch them (`k v`), jump to one (`k o`), message one (`k s`), read its transcript tail (`k r`), fork it (`k b`), kill it (`k k`), spawn new shells/claudes (`k n`/`k c`). Run `k help` for full usage.

## Commands

- `make build` — build the `kraken` binary. It **stamps the running build's short SHA** into it (`-ldflags "-X kraken/internal/util.BuildSHA=$(SHA)"`, read back by `util.Build()` and shown on the board's update button), so the package path in that flag must stay in step with `internal/util/build.go`: the linker silently ignores an `-X` it cannot resolve, and `Build()` then returns `"dev"` forever. A bare `go build` leaves the SHA unstamped (harmless) and **skips the `web-assets` prerequisite**, which is not optional: `make build` runs `npm ci && npm run build` in `web/_ui` to produce `web/_ui/dist`, which `web/embed.go` embeds. `dist/` is generated and gitignored, and `go:embed` cannot embed an empty directory, so on a clean clone a bare `go build` (and `go test ./...`) fails outright until assets have been built once. That failure is deliberate and loud; `make build` is the supported entrypoint.
- `make install` — build + install to `~/.local/bin` (with `k` symlink) + zsh completion. **Never `cp` over the installed binary directly**: macOS SIGKILLs running processes whose backing binary changes (code-signature invalidation); the Makefile copies to a temp name and `mv`s. Install also **code-signs** the fresh binary before that `mv` (identity `$(KRAKEN_SIGN_ID)`, else the first keychain codesigning identity; never fatal, never `--options runtime`) with the stable `--identifier dev.carl.kraken`, so a TCC privacy grant survives rebuilds (an ad-hoc signed Go binary looks like a new app to TCC on every rebuild). The launchd label is `$(KRAKEN_LABEL)` — it names the plist file, its `Label` and every `launchctl` target, and is deliberately NOT tied to the codesign identifier — resolved from the make line or environment, else the first `KRAKEN_LABEL=` line of `~/.kraken/env`, else `dev.carl.kraken`; the file is read both by a hand-typed install and by the one `k update` runs. `install` also appends `KRAKEN_OPERATOR=$(OPERATOR)` (default `id -F`) to `~/.kraken/env` when absent, and — on an UPGRADE only, i.e. when `kraken.db` existed before this make ran, checked at parse time since install-serve's fresh serve creates the database moments later — `KRAKEN_BRANCH_PREFIX=carl/` when absent, so an install predating the knob keeps its live cells and PR tracking on their `carl/…` branches. It never rewrites a line, and a failed write fails the recipe. `install-completion` uses the first of `~/.oh-my-zsh/custom/completions`, `~/.zsh/completions` that exists (creating only the latter), and succeeds with a note when neither is usable. The launchd restart is `launchctl kickstart -k`, not `unload`+`load`: one atomic kill-and-relaunch, which matters because the daemon is sometimes the process running this recipe (`k update`). `install-serve` regenerates the plist to a temp file and only `bootout`+`bootstrap`s when the content changed — kickstart relaunches from launchd's cached definition and never re-reads the plist.
- **Manual testing of in-progress changes runs a PARALLEL server on the laptop, never `make install` from a worktree** (carl's standing rule): install replaces the live `kraken serve` mid-run. Build the branch to a scratch path (`CGO_ENABLED=1 go build -tags sqlite_fts5 -o /tmp/kraken-test ./cmd/kraken` from the worktree, after `make web-assets` if the SPA changed) and run it against an isolated world on another port: `HOME=$(mktemp -d) /tmp/kraken-test serve -p 7878` (a fresh `HOME` also means an empty `~/.kraken/env`, so set any knob you need on the command line). `GuardServeStart` refuses only when `~/.kraken/daemon.json` names a live conflicting pid, and every state path roots at `HOME`, so the isolated instance coexists with the real serve; seed it with a test job. The isolation stops at the serve process: a cell it spawns comes up in the SHARED tmux server, and a tmux pane takes HOME and every variable except PATH and tmux's `update-environment` list from the tmux SERVER, so that cell's claude runs under the real HOME — its hooks reach the parallel serve because `hookCommandFlags` bakes `--serve-addr` into them, and its agent-side verbs because `mergeServeAddrSettings` writes `KRAKEN_SERVE_ADDR` into the cell's `.claude/settings.json` `env` block (a codex cell reads no settings.json and is not covered). For UI-only changes the lighter form is `npm run dev` in `web/_ui` (vite on :5173, `/api` proxied to the REAL serve, so new routes 404 until the backend half also runs in a parallel server).
- `make ios-testflight` — build the iOS app and upload it to TestFlight. A thin alias for `./ios/ship-testflight.sh` (flags via `ARGS=`, e.g. `ARGS=--dry-run`) and deliberately logic-free: the script is the ONE implementation, and `k ship-ios`/the board button call it directly, so anything added here would make a hand-run ship differ from a board-run one. The first run ever needs `ios/ship-testflight.sh --allow-provisioning-updates` by hand (it creates certificates and profiles on the real Apple developer account). Setup: `ios/TESTFLIGHT.md`.
- `make mac` / `make install-mac` — build the macOS board app (`macos/`: a frameless WKWebView over the SPA `kraken serve` embeds; the full native SwiftUI board it beat is preserved at commit 591800e) and install `Kraken.app` into `/Applications` with the same staged-copy + atomic-rename discipline. Nothing in CI builds Swift, so `make mac` is the compile check. The xcodegen regenerate MAY rewrite the tracked `macos/Kraken.xcodeproj`: `make mac` leaves that churn visible on purpose (and it blocks `k update`'s clean-tree preflight until committed or reverted), while `install-mac` snapshots and restores the generated files because `k update` drives it unattended.
- `go test -tags sqlite_fts5 ./...` — run all tests. The tag compiles FTS5 into the sqlite driver; without it every test that opens a store fails at migration with `no such module: fts5` (the retired knowledge graph's v15 migration still creates an FTS5 table on every fresh database — history is never edited — so the tag outlives the graph).
- `go test -tags sqlite_fts5 -run TestName ./<pkg>` — run a single test (main-package tests: `./cmd/kraken`; skills-embed tests: `.`)
- `go vet -tags sqlite_fts5 ./... && gofmt -l .` — lint

## Architecture

The binary is split into a strict dependency chain of packages, each owning one layer: `cmd/kraken/` (package main: CLI dispatch, `k ls` rendering, the bubbletea viewer, plus the `_k` zsh completion script) + `internal/util/` (stdlib-only helpers) + `internal/store/` (the sqlite layer: `kraken.db` schema + typed accessors) + `internal/core/` (discovery, `Peer`, tmux primitives, claude spawning, pane resume — `resume.go`'s guard/respawn/session-file cleanup — transcript reading, usage) + `internal/jobs/` (job files, cells, crew briefs, status derivation, archive, daemon) + `internal/api/` (JSON handlers + wire types, `apiContract`, `api.Register`) + `web/` (the embedded SPA — a React + TypeScript app whose source is `web/_ui/` and whose vite output `web/_ui/dist/` is what `go:embed` takes — plus artifact serving, bind logic, `web.Serve`). `cmd/` and `internal/` are pure Go; `web/` stays top-level because it carries the SPA, `docs/` holds operator-facing setup docs spanning layers (today: the Zed mental-model keybinding and its in-editor extension), `zed/` holds the Zed dev-extension crate (`zed/kraken-mm`, a Rust/WASM shim whose whole body is "run `kraken mm lsp`"; outside the Go module, with its own Cargo.lock), and one Go file stays at repo root — `skills_embed.go`, the module-root `package kraken`, pinned there because `go:embed .claude/skills` cannot reach above its package directory (cmd/kraken blank-imports it). The dependency DAG is `util ← store ← core ← jobs ← api ← web`, and `cmd/kraken` imports all of them; importing upward is forbidden. The only direct Go dependency is bubbletea (viewer TUI); everything else is stdlib. External state is shelled out to: `tmux`, `ps`, `lsof`, `git`, `gh` (read for PR state, and WRITTEN by the updater's account rescue), `osascript`, `python3` (the doc pipeline's fragment linter and card-wrap substitution run via python3 in cells).

The core type is `Peer` (internal/core/peer.go): one live agent process in a tmux pane, an in-process teammate known only from a team config (`Messageable=false`), or an agent-free shell pane (`Role "shell"`).

Data flow, shared by `k ls`, the viewer, and completion:

1. **Discovery** (internal/core/discover.go): `DiscoverAll()` snapshots tmux panes (`tmux list-panes -a`) and the full process table (one `ps` call), then walks each pane's process subtree for claude/codex processes. Agents in a pane are listed deepest-first: index 0 is the foreground agent — the one `tmux send-keys` actually reaches; deeper ones are nested subagents. Enrichment comes from `~/.claude/sessions/<pid>.json`, `~/.codex/state_5.sqlite` (the `threads` table, read-only) + lsof for codex, transcript files under `~/.claude/projects/<munged-cwd>/`, and `git`/`lsof` for branch/cwd. lsof is the slow path — results are memoized in package-level caches (`cwdCache`, `codexSessionCache`) because the viewer polls discovery on a tick.
2. **Refinement + nesting** (internal/core/peer.go): `refineStatus` peeks pane content via `tmux capture-pane` to detect blocked/question prompts, and to overrule a foreground claude's session-file "busy" when the pane shows no turn in progress — a lead with resident teammates never flips its file back to "idle", which otherwise wedges its cell reading "working" forever; `nestTeams` attaches teammates to their leads using `~/.claude/teams/*/config.json`; `OrderAll` produces the single flat numbering that every selector references.
3. **Selection** (internal/core/select.go): `SelectPeer` resolves a user selector — index, `.` (current pane), exact pane id (`%3`), session-uuid prefix (≥4 chars), or substring match — against that ordering.
4. **Action or render**: actions (internal/core/actions.go, internal/core/branch.go) drive tmux (`send-keys`, `kill-pane`, `new-window`) and ghostty focus via AppleScript, called from cmd/kraken's thin cmd wrappers (cmd/kraken/cmd_actions.go, cmd/kraken/cmd_branch.go); the one exception is `k b`'s `tmux split-window`, issued directly from cmd/kraken/cmd_branch.go. Rendering is cmd/kraken/ls.go (tables, grouping modes, colors) and cmd/kraken/viewer.go (bubbletea TUI that re-runs discovery on a tick and reuses ls.go's group/row builders).

### Jobs, cells and the board

A job (internal/jobs/job.go) is one row in `kraken.db` whose text is a `<slug>.job.md`-shaped frontmatter-plus-spec document, parsed strictly into a four-state board model — draft · working · blocked · done — that kraken derives, never hand-writes. There is no state between "carl has not submitted it" and "its cell is running", because **submitting a job starts its cell synchronously**, inside the POST: `jobs.SubmitJob` (internal/jobs/submit.go) is the ONE start surface every door funnels through (the board's `POST /api/queue`, whose URL is kept for shipped iOS builds; the viewer's `s`, though the TUI wires no store so its jobs pane is empty outside serve; the daemon's own dream creations; `k cell submit`). It refuses in a fixed order (unparseable → done → already started → empty spec → unresolvable repo → invalid branch prefix (`branchPrefixErr`) → no qualifying codex launcher, codex jobs only), submits SERIALIZE per job id on an in-process mutex (the ladder is check-then-act with a seconds-wide gap, and the editor's ⌘⏎ used to double-fire exactly that, the loser answering with a git-flavoured 409 from inside `git worktree add`), and `StartCell` writes `working` only once the cell is actually up, so a refusal and a half-failed start both leave the job as draft as it was. Some retired machinery still has shapes on disk: a `ready:` flag and a `prereqs:` DAG in the job frontmatter, a daemon queue pass with a 15-cell `CellCap`, a `StartErrors` side channel, and `/api/dequeue` + `/api/start`, both unregistered. `ready:` and `prereqs:` are ACCEPT-AND-IGNORE in `ParseJob` (the imported job corpus carries them on almost every job, and erroring would pin the whole board to draft), nothing writes one, `JobTemplate` emits neither, and `POST /api/job/draft` refuses either LOUDLY (`retiredFrontmatterKey`, scanning the frontmatter only, since a spec body may discuss prereqs in prose).

Two orthogonal extras sit beside the four states. **Archived** jobs (internal/jobs/archive.go) are job rows (and, by id, their artifact rows) moved into the archive — out of the active namespace entirely (slug freed, invisible to the daemon), renamed with a number on conflict, restorable via the board's unarchive action (state preserved; refused while the slug is taken) and hard-deletable only from the archive. **Reactivation** (the board's reactivate action, internal/jobs/cell.go) resurrects a done job into its original zeus session: kraken stamps zeus' session id into the job file (`session:` frontmatter) from the daemon's first tick after the cell comes up, so a done job can later be resumed with `claude -r` in a recreated worktree at the same path. `ReactivateJob` refuses first, before any worktree is touched, when `KRAKEN_BRANCH_PREFIX` makes an invalid branch name (`branchPrefixErr`, the same rung `SubmitJob` runs). The `<prefix><slug>-<id>` branch (prefix `KRAKEN_BRANCH_PREFIX`, default `kraken/`, read on every call by `branchPrefix`) recycles (reset off the base once fully merged), falling back to `<prefix><slug>-<id>-rN` (`run:` frontmatter) only when leftover unmerged commits would be orphaned. The id is the immutable `jobs.id`: a slug is unique only among ACTIVE jobs and archiving frees it, so a bare-slug branch let a new job collide with an archived generation's checkout. `branchFamily` still MATCHES the pre-cutover bare-slug names and every name under the legacy `carl/` prefix (PRs opened before each cutover sit on them, and dropping them would detach those PRs from their cards), but nothing writes one; only the current prefix and `carl/` are matched. The cell's artifacts come back with it: `ReactivateJob` restores the store's blob-canonical artifact mirror into the cell's `artifacts/` dir (`restoreCellArtifacts`, internal/jobs/sync.go) ONLY when that dir no longer exists — a surviving dir (the mid-run "resume" path) is the current truth, deletions included — and a failed restore fails the reactivation, because the freshly-made dir is a true-mirror SOURCE at the next teardown's sync and left half-filled it would propagate deletions into the stored rows. A torn-down job's uncommitted root-level notes (`*.md` at the worktree root, `rootNotes`) are captured as `root/<name>` rows; reactivation writes them back only where the checkout has no file of that name (`writeRootNotes` never overwrites), and on the recreate path each skipped note is staged at `<cell dir>/root-notes/<name>` (`restoreRootNotes`), with zeus' reorient prompt naming both the notes written back and the ones staged; on the resume path a skipped note simply stays a row.

**State derivation** (`internal/jobs/status.go`): `deriveState` combines the job file's own `state` with live-ness and a ROLL-CALL of the cell's claudes (`cellActive`: the zeus pane peer's own status, any nested subagents in its session, and non-lead team members cross-checked against live tmux panes — any one alive-and-running votes the cell working, else it reads blocked). A LIVE, WORKING job's first blocked reading is held for one tick by `holdBlocked` (daemon state `BlockedSince`, confirmed only by the immediately following tick), so only two adjacent blocked readings write the state, sync the artifacts and notify: the roll call reads a mid-turn zeus as idle for exactly one tick a dozen-plus times a night, and each unconfirmed flip was a "blocked" notification for a cell that never stopped. `FindPendingQuestion` pulls any still-open `AskUserQuestion` tool call out of zeus' transcript for the board and iOS app to render as answer buttons.

### Cells, zeus and side threads

A cell (internal/jobs/cell.go) is one job's runtime: a dedicated git worktree plus a tmux session holding **zeus**, the job's only working agent, in its first pane — there is no relay agent and no escalation-bus file; zeus reports status by saying it in its own pane, which the board surfaces as the cell's detail line. The cell's `tmux new-session` runs under `cellSpawnEnv`: this process' environment with the resolved `go`'s directory prepended to PATH via `util.PrependToolDir` (the same launchd reason `k update` has). It has to be the ENVIRONMENT of that command rather than `new-session -e PATH=…`, because tmux takes a new pane's environment from the issuing process and overrides any PATH set with `-e` (other `-e` variables survive, a convincing dead end); since zeus issues the `tmux new-window` for each teammate, one PATH here reaches the whole crew, as well as the side-thread window kraken itself opens. Unresolvable `go` returns nil (inherit), so a toolchain probe can never fail a spawn.

Beside zeus a cell may hold **side threads** (internal/jobs/thread.go): carl branches one to ASK about the work, and it comes up as a fork of zeus' session (`--fork-session` under a kraken-minted `--session-id`, named `thread-<slug>-<tid>`) in its own window of the same tmux session, reading the same worktree. Threads are rows in `kraken.db` (`internal/store/threads.go`), and a row is a POINTER, never a transcript: identity, provenance and the live pane/window, while claude's own transcript (located by `session_id`) is the conversation, so nothing is snapshotted and pane threads have no per-job cap. Kill ends the window and closes the row; revive resumes the SAME session in a fresh window; teardown closes every row without deleting one. A thread must never disturb the job it hangs off, which is three exclusions keyed off thread.go: it never votes in the roll call (`cellActive` takes the live thread panes as a skip set), it can never be elected zeus (`CellZeus` filters the thread name prefix and the live thread panes — elected, it would feed `stampSession` a thread's session id and take carl's steer messages), and Stop never interrupts it (`InterruptCell` skips the same panes). Deciding a thread is GONE demands positive evidence, never just a missing name: `Peer.Name` only appears once claude writes its session file, so the reconcile pass leaves a row alone inside its spawn grace window, while a still-nameless claude sits in its pane, or when the tick's tmux snapshots contradict each other — closing a LIVE row would un-skip its pane in the roll call, orphan kill/send, and let a revive start a second claude on one session id.

Since schema v36 a thread row also carries a `kind`: `pane` (all of the above) or `headless` — an **ask thread** (internal/jobs/askthread.go), which has no pane and runs one `claude -p` process per question as a child of `kraken serve`, forking zeus on the first (`--fork-session -r <zeus session> --session-id <minted>`) and resuming the thread's own session after, with the question on stdin, `--permission-mode default --permission-prompts none --restricted --strict-mcp-config --disable-slash-commands --system-prompt-snapshot off`, and a tool set keyed on the row's origin AND the question's sender: the read-only `AskThreadTools` (Read, Grep, Glob, WebFetch, WebSearch; cwd the worktree) only for carl's own question in a thread carl's own node opened, `--tools ""` for everything else, and a thread another node opened runs in the cell dir. `kind` is independent of the older `role` column (schema v33: `ask` for carl's question thread, `mind` for the mind thread of job 542, RETIRED by job 674 — `BranchThreadWithRole(..., "mind")` returns `ErrThreadRoleRetired`, existing rows stay readable; every new thread is `role: ask`, and the store refuses a headless mind row with `ErrThreadKind`); the value is `headless` rather than `ask` because `ask` was already `role`'s value on the same wire object. `POST /api/threads`' `branch` opens a headless thread by default for role `ask` (`headless:false` is the pane opt-in; role `mind` is refused 409). The row records its origin (tailscale node id, label, login), an `answering` flag a compare-and-set (`ClaimThreadAnswering`) holds while a run is in flight (one run per thread: two `claude -r` on one session id are two writers on one transcript), and a `note` when a run did not end cleanly (failed, timed out at `AskThreadTimeout`, cancelled by a kill, or lost to a serve restart, which `ReconcileThreads` clears); the reconcile pass never closes a headless row (only kill or teardown does, and teardown kills its run first). `thread-ask`, `thread-send` and `thread-kill` are the fleet's node-tier actions for it, admitted on readonly and public cards alike (`nodeThreadActions`), with the origin taken from the caller's verified tailnet identity and every question stamped `[from <label> · <login>]` (`[from <label>]` when the login is unknown) on stdin, with every `@` of a non-self question and of the stamp rewritten to `＠` so neither can mention a file; another node's live headless threads are capped per job at `MaxAskThreads` (5), carl's own never count, and a node may close only a thread it opened. The runner's only tmux contact is the `askCellLive`/`askZeusTarget` seams, and `askLauncher` is the process seam tests swap.

**Zeus' system prompt** (internal/jobs/crew.go) is unified — there is no job-level `type` (Q14): zeus itself decides, from the job spec text, whether a doc phase runs at all and which of Phase 1's two paths it takes. The brief carries ONLY what no skill can know — identity, the cell's real paths, how carl is reached, the model tier, the hephaestus/athena crew, the self-destruction guardrails, and which skill governs each phase — and points at `.claude/skills/{info,aim,do,dream}` for every procedure, plus `.claude/skills/load` for the load-estimate ladders; each skill's "Inside a kraken cell" section owns its phase's exact closing line. It is staged as a FILE (`<cell dir>/zeus-brief.md`, the initial prompt beside it as `zeus-prompt.md`) and referenced from the tmux command with `"$(cat …)"` via `spawnCommand`/`core.ShellReadFileArg`, never inline: tmux caps a command at ~16KB and rejects anything longer with a bare `command too long`, which is how a 17.5KB brief once wedged every cell spawn. Two tests hold the line — `TestZeusBriefDoesNotRestateSkills` (the brief must not copy a skill) and `TestSkillsOwnTheCellContract` (a skill must not drop what the brief handed it).

### The phases and the crew

The **spec path** is `/aim`: research, then the flat artifact set below plus open questions, stopping at the `/do` gate. The **explanation path** is `/info` (read by path from the cell's `.claude/skills/`, since a personal skill of the same name shadows it): research just as deeply, but ship ONE brief `00-overview.md` ending in a "go deeper" menu, then exactly one focused artifact per round carl asks for — never `/aim`'s section-doc floor unasked, and **never any questions rows**. What happens next is carl's move: when he sends `/do`, phase 2 begins — implement → the PR (do's own last step since job 624 folded the `pr` skill into it; opened BEFORE anyone has tested by hand, so every revision the manual test produces is a commit pushed to that same PR) → a manual-test gate (zeus reports "manual test ready" with the PR URL and stops until carl's reply passes it; the daemon, not zeus, watches CI and bumps zeus' pane on failing checks or new comments). A purely explanatory job never gets a `/do` and never opens a PR — carl accepts it from the board.

Phase 2 delegates slices to hephaestus TEAMMATES that zeus manages, reviewing each with three parallel single-dimension athena variants — athena-logic, athena-edge, athena-style. **Authorship of a slice and authorship of its tests are deliberately split between two agents**: hephaestus implements and never writes a test for the spec (a regression pin for a defect it fixes is the one carve-out — hephaestus tests bugs, athena tests requirements), while athena-logic and athena-edge write those tests from `50-contract.md`, the symbol-level contract zeus freezes BEFORE it dispatches anyone. The blindness is a property of the SCHEDULE: all three are dispatched in one message, so when the authors start there is no implementation to read, which is the only auditable version of "independently". They author but do not RUN; one barrier for the whole fan-out releases them once every slice is in, which is why a slice is not accepted (and its hephaestus not stopped) until BOTH gates have cleared it — the join, then the review round. A failing blind test is ambiguous by construction, so zeus arbitrates it against the contract TEXT — finishing BEFORE any review round, since reviewing means reading the implementation and an author cannot un-read it — into **code bug**, **test bug** or **contract defect**, plus a question row when the contract is genuinely silent on a product decision. Two rules keep the split from collapsing, both about which direction authority flows: a fix brief cites the contract OBLIGATION, never the failing assertion, and a contract defect is never resolved by sending athena to read the implementation (the same reason a compile failure caused by code deviating from a frozen signature is a code bug). It applies to every language a cell targets — Go, Python, TypeScript, Swift — with the caveat that a symbol-level contract can only name what a test can reach: Go, Python and Swift all reach non-public names (Swift through `@testable import`), so only TYPESCRIPT needs the export written into the frozen signature. The failure mode with no alarm on it is a round where every blind test passes first time (a contract written from existing code, or loose tests), so `90-build-report.md` carries a **Join** row recording authored/failed counts and the verdict for each. `.claude/skills/do/SKILL.md` owns the procedure. The pipeline renders its diagrams via per-figure hermes teammates, one per diagram id (`hermes-<diagram-id>`), resumed by name for a lint fix round rather than respawned.

Every one of those agents is a TEAMMATE rather than an in-process subagent — an Agent-tool call carrying a `name`, which gives it its own tmux pane, a team-config row `nestTeams` hangs under the cell (so carl sees it in `k ls`/`k v`), and an address `SendMessage` can resume; unnamed subagents are reserved for read-only exploration, meaning changing nothing in the repo rather than writing no file at all — such a subagent still writes its report to a scratch path. That promise is enforced: `mergeTeammateSettings` (internal/jobs/cell.go) writes `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` and `teammateMode: tmux` into the cell's own `.claude/settings.json`, merged never clobbered, so the crew does not silently degrade to in-process subagents when the user's personal settings change. Two rules bound the delegation: it must be **earned** — zeus makes small coherent edits itself and reaches for hephaestus only when the work genuinely splits into independent slices, while the athena review runs in parallel every time regardless of who wrote the code — and an agent is torn down on **acceptance**, not on reporting done, since a blocking finding has to go back to the same teammate. Zeus also never prompts: carl does not watch the pane, so an interactive question there is invisible AND blocking; zeus defaults, states the call in its final message, and keeps going, with `AskUserQuestion` a last resort and spawned agents forbidden from asking anything. The one exception is the **mid-build question round** (job 629, `.claude/skills/do/SKILL.md` step 5): a product decision that changes the core feature's functionality or usage, or a spec-changing deviation, met during Phase 2 is filed as question rows through the same `kraken questions` verbs `/aim` uses, P1/P2 defaults batched into the same round, and zeus stops on the P0s alone with a `questions pending:` line — the same protocol resolves a set's open P0s at the start of `/do`. Kraken never wakes a cell for a row (carl's decision): he answers on the board and then prompts the pane, the recall hook carries the answers into that prompt, and the only daemon-side sign of a round is the blocked notification naming the open P0 (`blockedNotifyBody`, internal/jobs/questionblock.go).

The doc phase produces a flat artifact set, never a single combined file: `00-overview.md` + `10`-`49` diagram cards + `50`+ section docs — no flatten step; each artifact is complete and shareable the moment it is written. Phase 2 closes by adding `90-build-report.md` (specified in `.claude/skills/do/SKILL.md`): a ≤1-page record of what shipped, every discrepancy between plan and reality, complications, deferrals, and verification — written on every phase 2, including jobs that never had an artifact set, with "None" spelled out rather than a section dropped. Open questions and carl's per-artifact feedback are rows in `kraken.db` behind `kraken serve`, not files — zeus writes questions but is READ-ONLY on feedback: `addressed` was the only feedback column a cell could ever write, and it no longer may. An ordinary cell reads its notes, acts on them, and says what it changed in its final message — the row records nothing, so a note it fixed keeps reading as open. ### PRs and stack links

A cell's **stack links** (job 622) are the PR chips' sibling for the thing to go and TRY: whatever the cell spun up for manual testing — a parallel `kraken serve` on `:7878`, a vite dev server — it registers with `kraken stack add <slug> <url> [--label <name>]` (`cmd/kraken/cmd_stack.go`, a proxy to the one-field route `/api/job/stack`, `internal/api/jobstack.go`). The rows live in `job_stacks` (schema v35, `internal/store/jobstack.go`, one per (job, url), written through verbs that bump NEITHER `rev` NOR `updated_at`), the board carries them as the additive `webJob.stack` array and renders each as a `⇱ <label> :<port>` chip in the card's PR band (and the steer modal's `#steer-stack` row), and the daemon's `stackProbePass` (`internal/jobs/stackprobe.go`, in the tick's `!mirror` block) dials each LIVE cell's loopback links every tick and stamps `status` `up`/`down` on change only, so a dead port renders muted and struck through; a non-loopback host (an ngrok tunnel) is never dialled and stays `unknown`. The rows are deleted at `teardownCell`, `add` is refused 409 on a draft or done job, the ninth distinct url is refused with the cap named, and a remote node's card renders the chips as plain spans. The `/do` skill's cell section mandates the add before the `manual test ready:` line whenever the gate involves a process on a port, and the clear after the reply passes it.

**PRs** are many-to-one with cells: the daemon's PR tracker records every PR shipped from the cell branch into the job's kraken-owned `prs:` frontmatter list (url + state, plus two kraken-owned watermark keys per PR — `last-comment-at`, `bumped-sha` — frontmatter-only, never on the wire). A merge is a notification + board chip + one `prWatchPrefix` notice typed into a live working/blocked cell's zeus pane (`mergeBumpMessage`/`mergeBumpWanted`, best-effort, never retried; without it the one party never told its PR closed was the agent still pushing to the branch), NEVER a teardown trigger — teardown lives only behind carl's explicit accept via board Done, and there is no `k reap` — and zeus recycles `<prefix><slug>-<id>` off origin/main after each merge for follow-up PRs. Each PR the hook sees is attached in real time by the cell's `pr-hook` through `POST /api/pr-attach`, a route that refuses (409) a PR whose GitHub repo is not the job's own (the hook cannot narrow by repo itself, and a `gh pr create` run against another checkout from inside a cell once attached that repo's PR to the wrong card); an unresolvable repo, an unreadable origin, or an origin that does not reduce to `github.com/<owner>/<repo>` fails OPEN, since refusing on missing evidence would drop real PRs. The one carve-out is a PR of a repo the job's own spec body names as a whole `owner/repo` token (`jobs.PRRepoNamedInSpec` — bare, as `github.com/owner/repo`, or as a clone URL, case-insensitively; a prefix or dotted-suffix match is not a name, nor is a link to its pull request or issue): that PR attaches, logged as `pr-attach-cross-repo` rather than `pr-attach-refused`, and the daemon's restart repair vouches for it (`specNamedPRs`, which considers only PRs outside the job's own repo) exactly as it vouches for a `gh pr create` found in the lead's transcript, which is narrowed to the job's own repo.

### The daemon

The daemon (internal/jobs/daemon.go) STARTS nothing on its own initiative — the tick's only start attempt is the single-shot `SubmitJob` for a dream job it created itself that same tick (a failure notifies, logs and leaves the draft; nothing retries it) — and otherwise tracks PRs (a live cell's every tick; an idle job's at most every 10 minutes and at most 8 per tick, since gh's PR queries bill a shared hourly quota), watches open PRs of active jobs for new comments or failing CI and bumps zeus' pane when either appears, reconciles each working/blocked cell's **colour** into that pane, and flags dead cells, owning nothing it cannot reconstruct from job files plus discovery after a restart. Every job interaction — starting, completing, archiving, reactivating — is CLI-free for CARL (Q14): `k`'s own surface is tmux/peer management plus the agent-side HTTP-proxy verbs (`questions`/`load`/`mm`/`cell`/…, each a thin front over a serve route with its guards server-side), carl's own moves stay on the board, and `kraken serve` is the sole runtime — the tick loop plus the web UI/API in one process (opens `~/.kraken/kraken.db`; the one-shot `kraken import` and `kraken cutover` verbs are retired with the pluto integration, job 584).

The **colour pass** (internal/jobs/color.go, `syncCellColor`) is deliberately the smallest thing the daemon types into a pane: a job's optional `color:` is one of the eight names Claude Code's own `/color` accepts (`Palette`, in `/color`'s order, with a dark hex, a WCAG-AA light hex, and an xterm-256 slot per entry — the same hexes are spelled out in `web/_ui/src/styles/style.css` and `ios/Kraken/Theme.swift`, kept in step by `TestJobPaletteMatchesCSS`/`...MatchesSwift`), unset means NO colour, and kraken sends `/color <name>` (never a BARE `/color`, which picks at random) only when the wanted colour differs from the `color.applied` watermark, so a `/color` typed by hand survives. It is hand-authorable like `model:` (`JobTemplate` offers a commented `# color:` line) and lands through the raw editor's parse, but the FORM save never writes it: `POST /api/job/color` is the only form-side writer — a one-field route because colour is cosmetic and so usable on a LIVE cell (the form save's `editableJob` gate covers exactly the states the delivery pass ignores), and because a full-replace form save from an older client would silently clear it.

The **linear pass** (internal/jobs/linear.go, `LinearPass`, skipped under `--mirror`) is the daemon's one INBOUND integration: every two minutes it asks Linear for issues assigned to carl since a kv cursor (`linear_sync`, advanced to the max `updatedAt` OBSERVED rather than to `now`, since Linear's clock is not this machine's), creates a DRAFT job for each new one whose workflow state matches `LINEAR_STATES` — body carrying the ticket's description verbatim, its comments, and its attachments downloaded through the uploads path as `[image: <path>]` lines — and thereafter keeps that job in step, bumping the cell's zeus with later edits and comments when the cell is live and APPENDING them to the body when the job has not started; a `linear_issues` row per issue makes creation happen exactly once ever (a slug collision records the reason and never retries), and its `last_event_at`, advanced only on a CONFIRMED delivery, is what lets an undelivered event hold the cursor rather than be lost.

The **dialog answerer** (internal/jobs/jev.go, `jevPass`, per job in the tick's `!mirror` block right after the auto-handoff loop) gets a cell past the Claude Code and codex dialogs that would otherwise stop it until someone pressed a key. Every tick it reads the last 25 lines of each depth-0 claude or codex pane in a live cell (side threads excluded by recorded pane and by name prefix), and when `core.ParseDialog` finds an option list it asks TypeSafe's Jev model, through `POST /v1/systemone`, two questions: whether the pane is a dialog an unattended operator may answer, and which option keeps the job running, with an `escalate` choice always offered. The operator's policy is enforced in code before Jev is asked. An AskUserQuestion looks the same on screen as a harness dialog, so the transcript decides: a pane whose agent has an unanswered AskUserQuestion, a codex `request_user_input` in its rollout (`FindPendingQuestion` reads both) or an unanswered `ExitPlanMode` plan approval (`pendingPlanApproval`) escalates without a call. A claude's transcript is found from its session id, a guessed id included, with the job's stamped session as zeus' fallback; any pane other than zeus with no resolvable transcript escalates, while a zeus with none is treated as still starting, with no tool call yet to be pending. A header naming a login, terms, an API key or `rm` (`jevHeaderVetoed`) escalates the whole dialog, and options matching `jevVetoWords` (exit, quit, reset, reset to default, use credits, extra usage, upgrade, purchase, delete, remove, on word boundaries) are struck from the choice set, and a dialog with nothing left escalates. A pick below 0.6 confidence, or a pane Jev rates below 0.7 as a dialog, escalates too. Each job's pass makes at most two API calls; any further dialogs wait for the next tick. Before typing, the pane is read again, and the keys go in only if the same header and options are there with the cursor where it was: the call can take seconds, and a replaced screen would take the Enter or arrow count on whatever option now sits under the cursor. A dialog is remembered by pane id, agent pid, header and option texts; it is typed into at most twice, never twice inside 60s, and a third sighting escalates as `still-showing`. Every decision is one event-log line holding the options (vetoed ones marked `✗`), Jev's probabilities, the keys and the pane tail; the tail, the header and every option text go through `core.RedactSecrets` before they reach the request or the log: `jev-answer` at info when it typed, `jev-escalate` at error, logged once per dialog, when it did not. The directive Jev is handed is the operator's `~/.kraken/jev-directive.md` when that file is non-blank, else `jevDefaultDirective`. The feature is off with no `TYPESAFE_API_KEY`. The spawn-window `acceptTrustPrompts` still answers the folder-trust dialog first, and now logs each answer as `trust-accept`.

### Account binding and the limit rescue

No CELL ever moves the main login (Q2, job 335): main is moved only by `k account <slug>`, the board's account-switch route, and the STANDING-agent rescue, and the manual pin (`k account <slug>` pins manual; `k account auto` releases it) means kraken takes no CLAUDE account decisions of ANY kind — a pinned machine spawns unbound cells and every rescue parks. In auto mode kraken BINDS each cell to its own pool account at spawn: `bindAccount` (internal/jobs/binding.go) stamps the emptiest eligible slot onto the job row — schema-v28 columns `account_slug`/`account_email`/`account_at`, written by `store.SetJobAccount`, which bumps NEITHER `rev` NOR `updated_at` and whose columns are absent from `jobFieldColumns` so a form save cannot clear a live binding — and `spawnCommand` prefixes the cell's launcher with `CLAUDE_SECURESTORAGE_CONFIG_DIR='<pool slot dir>'`, the Claude Code lane under which a process resolves that slot's OWN keychain item (`Claude Code-credentials-<sha256(dir)[:8]>`, the items ccp already creates) with its own refresh and locks. The prefix rides the COMMAND STRING and never `exec.Cmd.Env`, because `tmux respawn-pane` inherits no client env; the one seam covers StartCell, ReactivateJob and the rescue respawn, `threadSpawnCommand` applies the identical rule for side threads (a fork shares its cell's prompt cache, so it shares its account), teammates inherit zeus' account variable (Claude Code forwards `CLAUDE_SECURESTORAGE_CONFIG_DIR` to the pane it spawns, though not kraken's own exports such as `KRAKEN_JOB_SLUG`), and an UNBOUND job's command is byte-identical to pre-feature. Selection (`core.SelectBindTarget` + jobs' `decideBind`) reuses the rotation selector's `candidateGates` and ranks fewest-live-bound-cells first, counted by `boundCounts` under `liveOrFreshlyBound`, which also counts a binding stamped within `bindGraceWindow` (10m) because a bind lands before its tmux session exists — then fresh-over-stale, lowest session %, lowest Fable %, slug; stickiness returns a reactivated job to its previous slot while it stays eligible (Q6); a dry pool leaves the job unbound with a deduped `bind:no-target` notice (Q4); and a slot is excluded unless its keychain item exists AND its dir stats (Q1). The binding is served as additive `webJob.account` (pointer, omitempty; withheld for archived jobs), rendered as the card's `ac-chip` and the steer modal's account panel, decoded tolerantly on iOS (Q8).

A CODEX job binds through the same seam against its own pool: `bindAccount` branches on `Job.Agent` into `bindCodexAccount`, whose candidates are `ReadCodexUsageSnapshot`'s rows — written by `CodexUsagePass` (internal/jobs/codexusage.go) into the `usage_snapshot_codex` kv row or `~/.kraken/usage-codex.json`, built by READING each slot's newest rollout file since codex publishes no usage endpoint — whose counts come from `boundCountsFor(…, "codex", …)` (per-agent, so neither side reads the other's slots as loaded), and whose decision is `decideBindCodex`, which excludes the machine's own `~/.codex` identity (`core.CodexMainEmail`) and any slot with no usable `auth.json`, then hands the survivors to the same `core.SelectBindTarget`. `accountEnvPrefix` emits `CODEX_HOME='<slot dir>' ` for it, and NOTHING when the stamped slug does not name a usable codex slot (a claude slug stamped on a codex job would otherwise point a pane at a directory with no login). Two rules differ from the claude arm (Q4): the codex binder never consults the rotation mode, and neither does the codex rescue, so a machine pinned `manual` still binds and rebinds codex cells — the pin protects the machine's single claude login, and a codex binding moves nothing since `~/.codex` is never touched.

The **limit rescue** (internal/jobs/limitrescue.go, per-cell in the tick's `!mirror` block) handles a cell ALREADY RUNNING whose claudes hit a usage limit, and since job 335 its blast radius is ONE CELL: on a `rate_limit` hit it REBINDS that cell — selects a fresh pool slot through the same `decideBind` path (excluding the cell's own bound account, and main's identity with a snapshot-main fallback when `~/.claude.json` is unreadable), stamps the new binding, and kill+respawns zeus, whose `spawnCommand` then carries the new slot's env prefix. It calls `core.SwapMainTo` nowhere and takes no flock: the binder's in-process `bindMu` serializes it against spawn-time binds, and the cross-process `AcquireRotationLock` serializes exactly three holders — the two MANUAL swap surfaces (`k account <slug>`, the board's account-switch route) and `rescueSwap`, the STANDING-agent rescue's swap half (internal/jobs/standingrescue.go): iris is main's own tenant with no job row to bind, so moving main for it is the one automated main swap that outlives Q2. The standing agent gets the same two-trigger rescue through a one-row descriptor table (`standingAgents`, ids `standingAgentIDs`, once also holding kronos, retired in job 549 — the `agent` arm of `/api/limit-hit` and `kraken limit-hook --agent` survive with the list shrunk to `iris`, whose hits arrive through the transcript arm, classified on the kv-RECORDED session id only); hits key on `limit_hit:iris`, and the standing resume kills the agent's whole tmux session (kraken-made, single-window, re-verified single-pane before the kill) and lets `EnsureIris` respawn-resume it with the spawn backoff bypassed, since Ensure*'s session-name gate is the only spawn surface a standing agent has. Every swap site except `k account <slug>` stamps the `main_swap` kv watermark (`{at,to}`) that lets an UNBOUND cell's or a standing agent's unresolved hit ADOPT the landed swap (`adoptLandedSwap`) instead of repairing a limit already repaired — a BOUND cell never adopts; the CLI switch is exempt because that process has no store handle. `LimitHit` records the exhausted SOURCE account (stamped on fresh records only), and the notification's "from" side prefers it over the row's current email. The updater's `RecoverGHAccount` changes a machine-wide login too — the active `gh` account — on a different credential, outside that lock.

The limit rescue rests on two measured facts (2026-08-07, Claude Code 2.1.224). A RUNNING claude does NOT re-read a swapped credential: it resolves one at session start and re-resolves only on an auth error or a proactive refresh scheduled off the OLD token's expiry (probe turns up to +3m after a swap all still billed the swapped-OUT account). And a claude that has already 429'd holds a CLIENT-SIDE limit latch — it refuses further turns locally until the reset time the banner names — which neither the keychain swap nor a real `/usage` fetch clears. The one thing that moves a stalled claude is killing it and resuming: a fresh process reads the keychain at startup and carries no latch, with the conversation intact. So the rescue kills and respawns ZEUS' pane — zeus alone, because a tmux teammate has no resolvable session id to resume (`discover.go` leaves `SessionID` empty for every teammate row), which is why the resume prompt makes reviving or replacing the crew zeus' own first move. The respawn carries the FULL cell-spawn surface plus `-r <session>` (`spawnCommand(j, zeusSpawnArgv(j, "-r", sid), zeusLaunchBrief(j), prompt)`), because a resumed session retains neither `--append-system-prompt` nor `--model`. The rescue never kills a tmux SESSION, never tears down a worktree and never calls `ReactivateJob`.

Detection has two independent triggers. A cell's `.claude/settings.json` carries a `StopFailure` hook (matcher `rate_limit`), so a claude that dies on a limit runs `kraken limit-hook <slug>`, which POSTs to `/api/limit-hit` and never opens kraken.db — but `installHookSettings` runs only at SPAWN. The second covers older cells: the health pass classifies zeus' transcript, `core.classifyStall` returns `Kind "usage-limit"` for the banner texts (`usage limit` plus the session/weekly/opus phrases — a bare `rate limit` is deliberately NOT one, since it also matches an organisation burst 429 the ordinary nudge recovers), and `jobs.IsUsageLimitReason` routes on it. Either way the record is one kv row keyed on the job's IMMUTABLE id (`limit_hit:<id>`): nothing deletes it, and a slug freed by archiving would otherwise let a new job read a dead generation's record. A delivery whose `session_id` is one of the job's SIDE THREADS (`threadLimitHitTID`, resolved against the threads table, live or closed) is recorded under `limit_hit:<id>:<tid>`, resolved on record as `thread-hit`, with one notification per ten-minute quiet gap (none from a `--mirror` serve, `RecordLimitHitMirror`) — a thread shares its cell's account and hooks, so its first turn on an exhausted window fires the cell's hook naming the cell's slug, and attributed to the cell it bought a kill-and-resume of an idle zeus for a pane the rescue cannot reach. Deliveries fold — one exhausted window fails the lead and every teammate within seconds — and a fold increments the delivery count and touches no rescue state (it may only upgrade the evidence), since erasing the rebind watermark (`SwappedAt`/`SwappedTo`, names from the swap era) would send an already-rebound cell around for a second rebind. The rescue is two-phase across ticks: rebind, then kill and respawn on a later tick, so the rebind is recorded before anything SIGKILLs a pane. A manual pin never rebinds, and a landed rebind is always resumed even if the mode changed in between. A hit that spends its attempts with NO rotation target is terminal only when its banner never said when the window reopens: `parseLimitReset` reads the `resets 4:50am (America/New_York)` clause off the recorded details — anchored at the recorded hit so the target holds still across ticks, with ANY target further than `limitResetMaxWait` (6h) from that anchor reading as already-due, because on the transcript arm the hit's `At` can lag the banner by hours. The third park then stays UNRESOLVED as `parked-until-reset`, and the first tick past reset + `limitResetSettle` respawns zeus on `limitResetResumePrompt` and resolves the hit `resumed-after-reset` — in auto mode; on a pinned machine the first post-reset tick resolves it `parked-manual` instead, and while parked the pass skips before reading the mode, since a re-park under the pin would resolve the record early. `mergeLimitHitDelivery` folds a same-error delivery onto the still-UNRESOLVED hit with no time window (a 2-minute bound let the transcript trigger's 10-minute re-deliveries reset the attempt counter forever), adopting the delivery's details when they carry a reset clause the stored ones lack or name a limit window the stored ones do not (the Fable banner names one but has no reset clause), never at the cost of a stored reset clause, and taking that delivery's session id with it; the resume's no-agents cap is path-relative (`failCap`), since a reset re-arm arrives with its attempts already spent by the parks. The `--mirror` daemon RECORDS hits and never rescues.

A CODEX cell is rescued through the same pass with three differences, all forced by codex. Its hit arrives with no hook and no banner: `CellHealth` reads the `rate_limit_reached_type` field off the LAST `token_count` record in zeus' own rollout file (`core.CodexLimitReached`), and `codexLimitReason` writes the reopen moment into the reason string as `resets_at=<unix seconds>`, which `parseLimitReset` returns AS-IS (no regex, no 6-hour cap). The mode handed to `limitRescueDecide` is always `"auto"` (`rescueMode`). And the resume has to MOVE THE CONVERSATION first: `codex resume <id>` resolves a thread's rollout under the `CODEX_HOME` it runs in and fails with `no rollout found for thread id` otherwise (measured 2026-09-17), so `resumeCodexZeus` calls `core.PlaceCodexRollout` to copy zeus' rollout into the new slot's `sessions/` at the same relative path, then respawns on `zeusLaunch(j, cwd, prompt, zeus.SessionID)`. A failed placement respawns on a FRESH session carrying `codexHandoffPrompt`, which names the old rollout's absolute path and the artifacts dir (a zeus with no recorded session id takes the same fresh-session path); the respawn is followed by `acceptTrustPrompts`, because the new slot's home has never seen this worktree and codex blocks on "Do you trust the contents of this directory".

Ahead of the whole limit rescue sits the **Fable fallback** (internal/jobs/modelfallback.go, `tryFableFallback`, called first in both the cell pass and the standing pass). When a Fable-tier claude (zeus or iris; never codex) stops on its account's FABLE window while that account's session, weekly and Opus windows still have room, kraken neither rebinds nor kills anything: it types `/model claude-opus-5-5` (`core.FableFallbackModel`, its own exact id) into that pane through `SendToPeer`'s guards and, on a LATER tick, a one-line continue prompt — re-sent every minute (`fableFallbackBumpGap`) until the pane shows a turn ran since the send, since a typed prompt was measured to land and start no turn — and only that confirmation resolves the hit as `model-fallback`. A switch never confirmed within 30 minutes resolves anyway with a notification (`fallbackExpire`), stamped once per process (`ExpiredAt`, outcome `model-fallback-expired`) so later Fable re-deliveries on that process are absorbed silently; while one is pending neither rescue pass adopts a landed main swap (`fableFallbackPending`). Nothing is killed, so background tasks and teammates survive; the prompt cache does not, since the API's cache is keyed per model (measured 585K and 725K cache-write tokens on the first turn after a switch) — still far cheaper than a kill-and-resume. Fable exhaustion is read from the banner or the usage snapshot's Fable row (the hook arm's 429 never names the tier); headroom only from the snapshot. When Fable is what ran out, rotation usually has nowhere to go anyway: `candidateGates` excludes slots at Fable ≥ 80%, and the weekly Fable window drains across the pool together. The `fable_fallback:<id>` kv row records the PID switched; a later hit on that process is never switched again (it is on Opus now), and three same-process cases are held back from rotation: a re-delivery within two minutes of the confirmed continue (`fallbackAbsorb`), a pending switch bumped with the prompt alone for up to 30 minutes (`fallbackPrompt`), and a re-delivery after expiry. A respawned process (new PID) qualifies afresh; a hit whose `session_id` names another session is left to the ordinary chain. The fallback also has a SPAWN-TIME arm (`spawnModel`, described under the model policy below), and the cell pass hands `tryFableFallback` the model the process was actually spawned on (`zeusLaunchedModel`, from the cell dir's `zeus-model` stamp), so a zeus started on Opus is never a candidate: its hits take the ordinary chain, whose respawn resolves the tier afresh on whatever account it lands on. The fallback moves no login, so the manual pin does not gate it. Claude Code's `/model` also persists the choice as the user's default for new sessions, so after a night with a fallback carl's own next interactive `claude` comes up on `claude-opus-5-5` until he changes it back; every spawn kraken STARTS passes `--model`, and `k b`'s fork is the one kraken-launched claude that could inherit it.

### Background tasks

A claude's **background tasks** — a Bash call with `run_in_background` (a "shell"), a Monitor watch, and an in-process subagent from the Agent tool — are read by `core.ScanTasks` + `core.LiveTasks` (internal/core/tasks.go, job 612) and ride discovery as `Peer.Tasks`. None is a pane, only the first two are processes (a subagent has NO pid), and the session file's `status` stays `busy` through an idle-with-tasks window (measured 2026-10-20 on 2.1.304), so before this a zeus that fanned out six subagents and ended its turn read `waiting` and the roll call voted the cell blocked for the five minutes they took. The LEDGER is the transcript: a launch `tool_result` carries the task id in a fixed phrase per kind (`Command running in background with ID: <id>` / `Monitor started (task <id>` / `agentId: <id>` — a NAMED Agent spawn answers `agent_id: <name>@<team>` and is a teammate pane, never a task), a `<task-notification>` naming the id closes it whatever its `<status>`, a `TaskStop` tool_use closes what it names, and a `SendMessage` to a closed subagent's id reopens it. The ledger is PRUNED, because a transcript outlives its process (a `claude -r` resume, a `--fork-session` thread and a crash all carry the launch records forward): a task launched before the process started (`Peer.StartedAt`) is dead; a subagent whose sidecar `agent-<id>.meta.json` says finished after the task's last open event is dead, and one with no sidecar 30s after launch is dead; a shell or monitor with no direct child of the claude pid carrying its command text is dead. Every unreadable input degrades toward the ledger's answer, never to a phantom task. The scan is cached on (size, mtime) like `FindPendingWakeup`, beside which it sits in `DiscoverAll` under the same real-session-id guard. Tasks never change `Status`, and three consumers read them: `cellActive` gains a third vote — a pane claude not running but holding a VOTING task, under the side-thread and open-question guards — and only a subagent or a monitor votes (`taskVotes`, Q1 of job 612), since a background shell may be a dev server zeus left running at the manual-test gate, which IS a block; `CellCrew` (internal/jobs/roster.go) appends zeus' tasks to the roster, each `CrewAgent` carrying a `Kind` (`teammate`, or the task kind) and the wire's `webAgent` an additive `kind` (the web chips branch on it; iOS decodes it without rendering); and `peerCells` (cmd/kraken/ls.go) suffixes the status cell with `core.TaskSummary` — `waiting · 2 subagents · 1 monitor`. Side threads' own tasks never vote, and codex has no equivalent of these records.

### Load estimate

A blocked job carries a **load estimate**, which is how the board answers "which of these is worth unblocking first". Zeus writes two integers, both 1-10: `unblock` — how much effort unblocking costs CARL (1 a mechanical action, 10 deep thought over many decisions) — and `scope`, how big the claude work that reply unblocks is (1 a one-message reply, 10 a large implementation). Both ladders are ANCHORED — one concrete anchor per rung, plus a state map for recurring block states (review-only gate 1/1, live E2E gate 5/2, spec gate 3/6-8, credential 4/whatever it unblocks, working → clear) — because a ruler re-derived per cell produces numbers that do not compare across cells. Zeus' brief carries only the two pricing rules (`unblock` prices carl's ACTUAL move, `scope` only the work the reply buys) and the one-line state map; the rungs live in `.claude/skills/load/SKILL.md`, and the same anchor labels are mirrored byte-identically into the web and iOS drilldowns, pinned by a cross-source test. The clients rank on `roi = scope / unblock`, DERIVED wherever it is rendered rather than stored. A one-line `note` rides along, truncated server-side (`core.TruncateOneLine`, 200 runes) rather than refused. Both numbers in range or BOTH zero (the clear) are the only shapes accepted: `internal/api/jobload.go` refuses a half estimate with the reason. The request's two numbers are POINTERS: with plain ints an ABSENT key and an explicit 0 are one value, and since 0/0 is the clear, every body that merely failed to carry them would have wiped the row and answered 200; a missing number is the same 400, and `DisallowUnknownFields` makes an unknown key the refusal itself (a CASE variant is not one: encoding/json matches fields case-insensitively). Storage is four columns on `jobs` (schema v13), and `store.SetJobLoad` bumps NEITHER `rev` NOR `updated_at`, the same treatment `SetPRWatermark` gets: zeus rewrites this at the end of every turn, `updated_at` is each card's AGE, and `rev` is the editor's optimistic lock. It is reached from a cell by `k load get|set|clear <slug>` (`cmd/kraken/cmd_load.go`), one round trip to `GET/POST /api/job/load`, never a direct kraken.db open. `webJob.load` is a POINTER with omitempty: a zeroed object would claim an estimate OF zero, and the clear zeroes `load_at` with the numbers, so it is recorded as the absence of an estimate. Absence is the wire's ONLY spelling of "no estimate", shared by never-estimated, CLEARED and ARCHIVED. The clients render the badge only where a card reads as BLOCKED (a stale one on a running card reads as a current fact); the DRILLDOWNS — the web steer modal and the iOS job detail — render a whole estimate on any live job with its AGE beside it. Archived jobs are the one place the key is withheld outright (`archivedWebJob`, split out of `buildWebBoard` so a test can call it) — the opposite call from `tokens`, which is retrospective, while an estimate is forward-looking; the columns survive archive and unarchive, so the row comes back with the job.

### Spawn links, goals and token spend

**Spawn links** (internal/api/spawn.go, `stampSpawn`; internal/jobs/jobspawn.go) record which cell filed which job. A claude zeus runs with `KRAKEN_JOB_SLUG` exported, and the `kraken job draft` and `kraken cell submit` verbs send it as the `X-Kraken-From-Cell` header the cross-node steer already uses (`fromCellHeaders`, cmd/kraken/qfclient.go). `/api/job/draft` (on create) and `/api/queue` (after a successful start) record the first such cell as the new job's parent in `job_spawns` (schema v38, one row per child, keyed on immutable ids, bumping NEITHER `rev` NOR `updated_at`). The stamp never changes a route's answer — a refused submit, a header naming no active job or the job itself, and a child that already has a parent all record nothing. The board resolves the rows once per build into the additive `webJob.spawned` array and `spawned_by` object (`{slug, state}`), rendered as `↳ <slug>` / `↰ <slug>` chips under the stack row on the card and in the steer modal; the rows are history like `prs` and go only with a hard delete. Codex cells and side threads export no slug, so cells they file are unlinked.

**Goals** (schema v23, `internal/store/goals.go`) are carl's weekly and daily intentions — scope `week`|`day`, period keyed to a LOCAL calendar date (a week goal's period is its Monday; `store.GoalPeriods` is the one place either is derived), text, done, position, and for a day goal an optional `parent_id` naming the week goal it serves — written from the board's goals panel through `/api/goals`, linked to jobs MANY-to-many through schema v27's `job_goals` join table (`internal/store/jobgoals.go`: composite PK, a `position` column, `ON DELETE CASCADE` on both sides) and its own `/api/job/goal` route, and read back by every cell through `kraken goals get [slug]`, READ-ONLY on purpose: an agent that could write them could quietly rewrite what it is measured against. That route takes a PER-GOAL op — `{"slug", "goal_id", "op":"add"|"remove"}`, with `goal_id: 0` still the clear-all every pre-multi-goal client sends — rather than a list of ids: a client sends what it wants CHANGED, never the set it believes is current, so a stale board cannot silently unlink a goal it has not seen. Three store verbs (`AddJobGoal` appending at `MAX(position)+1` and no-opping on an existing link, `RemoveJobGoal`, `ClearJobGoals`) replace v23's `SetJobGoal`, each bumping NEITHER `rev` NOR `updated_at`. `store.Job.GoalIDs` carries the links in position order, filled by one attach helper from every job loader — including `GetJobByFormerSlug` in rename.go, the one that gets forgotten. The wire is additive: `webJob.goals` is the ordered array, the retained `webJob.goal` is `goals[0]` (built from the same slice by one function), `GET /api/goals?slug=` gains `job_goals` beside `job_goal`, and an archived card carries both. Deleting a week goal degrades its day children to unassigned (`ON DELETE SET NULL` on `goals.parent_id`), and deleting any goal removes the link ROWS of every job serving it — both from the schema. Every cell sees them through two injection points: `goalContext(j)` (internal/jobs/goalctx.go) is appended after `zeusBrief` (the `zeusLaunchBrief` composition) at all three spawn sites (`StartCell`, `ReactivateJob`, the limit-rescue resume), and the same renderer feeds a goals block onto the recall channel on `UserPromptSubmit` firings, emitted only when the rendered goal state DIFFERS from the last one that session saw (a per-session fingerprint), because goals are state to re-deliver on change, not notes to deliver once.

**Per-job token spend** is the one number the board and the dream loop both read and neither computes. Claude Code stamps a `usage` object on every assistant record, and kraken sums its four counters per JOB — `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, carried RAW with no weighted total (a stored "cost" bakes a price ratio into the database). It is called `tokens` everywhere and never `usage`: `usage` in this binary already means ACCOUNT QUOTA (`/api/usage`, `~/.kraken/usage.json`, `internal/core/usage.go`, `internal/core/usagepool.go`). It is STORED rather than computed on read: the board payload carries ~74 job objects behind a 2s cache polled every 3-4s, while a full re-decode of one 20–60 MB cell project dir costs 0.1–0.3s warm, so the daemon computes it and the board reads a stored row. What counts as ONE contribution decides the number: a naive per-record sum over-counts real cells by 1.84x overall and 1.36x-2.58x per job, so the ranking it feeds is noise. Two rules fix it, both in `core.SumTokensDelta`. First, one API message is written as one record PER CONTENT BLOCK sharing one `message.id`, so a message contributes once, tracked by that id, and the tracker SKIPS non-assistant records rather than being reset by them (a group's blocks are separated by 1-5 tool_result records). "Once" is NOT "the first record", and the difference is the whole of `core.tokenGroup`: THE FOUR COUNTERS DO NOT BEHAVE ALIKE, and the line that separates them is ROOT vs SIDECAR. `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` are stamped identically on every record of a group everywhere (0 of 39,818 multi-record groups vary), so they are taken from the FIRST record. `output_tokens` is stamped identically only in ROOT transcripts; in a SUBAGENT SIDECAR the leading records carry a streaming PARTIAL and the last carries the message's total (4,022 of 4,444 sidecar groups vary), so first-wins recorded 31,832 output tokens where 4,621,522 were spent. A group's output is therefore taken from its LAST record, by committing the DELTA against what the group has already contributed — last-wins rather than max-wins because `usage` is cumulative and the final record reports the finished message, which also makes the resume-boundary seed EXACT. Since a sidecar is always the subagent half, that error's direction was fixed: the delegated half deflated, zeus' share inflated; correcting it needed its own WIPE of both token tables (schema v14), the counters being accumulate-forward. The rule lives in exactly ONE function, `core.tokenGroup.commit`, called by the per-job sum (`addTokenLine`), the dream loop's per-session digest (`mine.go`'s `digestTranscript`) and the resume-boundary seed (`assistantGroup`, which REPLAYS commit on a fresh group) — the consolidation is what fixed it: the rule used to be written out twice, so the two readers agreed with each other and both disagreed with the transcripts. A test pins that the two readers produce the same four counters, paired with an assertion on the VALUE. Second, a kraken side thread is `claude --fork-session` in the same worktree, so a fork's transcript is SEEDED with the parent's records, `usage` and all; `session_id` (SNAKE case — the session that actually made the call) survives the fork while `sessionId` (camel) is rewritten on every replayed record, so the snake one is the only usable marker, and absent means own (sidecars carry none). Together they reproduce an independent globally-unique-`message.id` dedupe EXACTLY on 118 of 119 real cell dirs.

The total is also split by ORIGIN — how much the cell's lead burned versus everything it delegated to — and the split is a property of the FILE, decided by `isAgentTranscript` in three arms: a transcript under a `subagents/` dir is an in-process subagent's sidecar; a root transcript whose head carries an `{"type":"agent-setting"}` record was an Agent-tool spawn; and a root transcript whose head carries an `agentName` is DELEGATED unless that name is one kraken itself MINTS for a lead — `zeus-<slug>` (`jobs.ZeusName`) or `thread-<slug>-<tid>` (`jobs.ThreadAgentName`), the prefixes `core.IsLeadAgentName` tests and a jobs-side test pins. Everything else is the lead's, a side thread included (carl forking the lead). Arm 3 does the work, because arm 2 alone is WRONG: `agent-setting`'s payload is the spawn's `subagent_type`, so a teammate given a `name` but no `subagent_type` — exactly what zeus' crew is — gets no such record (15.2% of teammate transcripts measured, which alone rendered one job's zeus share 38% too high). Both content arms decode each head line as JSON rather than substring-matching, which makes the byte bound load-bearing: the line carrying `agentName` is usually a whole brief ending as far in as 57 KB, and an 8 KB window reproduced the unfixed number exactly. The probe is therefore a `bufio.Scanner` over a 256 KB `io.SectionReader`, seeded at 4 KB from its own `agentMarkerInit` rather than the main scan's 64 KB `mineScanBufInit`, stopping at the first record that answers. Only zeus' four counters are stored (`job_tokens.zeus_*`, served as `webTokens.zeus_in`/`zeus_out`/`zeus_cache_write`/`zeus_cache_read`) and the delegated half is the REMAINDER everywhere it renders. Adding the columns had to WIPE both tables (schema v11): a pre-existing row with the new columns at zero would report its job as 100% delegated forever. A probe that cannot read, and a head window with no signal, both degrade to the LEAD: a visibly-too-large lead half rather than a silently wrong total.

`core.SumTokensDelta` is what makes computing it affordable: transcripts are append-only JSONL, so it remembers how many bytes of each file it has already summed and reads only past that — a settled job costs one `stat` per file forever after. Five rules hold that up, each because its absence is silent: a file SHORTER than its recorded offset can only be a replacement, so it is re-read whole; an offset only ever lands on a newline-terminated line, so a transcript caught mid-write is resumed rather than skipped past; a message split ACROSS a resume boundary is still counted once, via `precedingGroup` reading the previous assistant record back out of the file rather than persisting it (rewinding the offset instead would leave a settled file's last group permanently uncounted AND re-read on every pass); the subagent sidecars count (a sum without them is wrong by ~24%); and an INCOMPLETE scan returns its counters WITH an error saying the number is not exact, because a failed read is not a zero and an absent path in an errored scan means "not seen", not "deleted" — `refreshJobTokens` carries those watermarks forward, since dropping them would re-sum those files from zero into counters that only accumulate. That last rule is about REPORTING: EVERY path that can see less than the whole truth has to raise an error — a line over the 16 MB ceiling, a subtree that cannot be listed, a file that cannot be `stat`'d, a group seed at a resume boundary that exhausts its lookback (which fails LONG rather than short), and a `JobProjectDirs` whose `os.ReadDir` of `~/.claude/projects` failed (one such measured a true 600 as 1100, forever, with nothing logged). An ABSENT projects dir or cell dir stays silent, since that is a job with no transcripts. A job's transcripts are located from `CellWorktree(j, repo)`'s **string** (`internal/jobs/tokens.go`'s `JobProjectDirs`), never `ExistingWorktree`, because `teardownCell` deletes the cell dir while Claude Code keeps the transcripts; `JobProjectDirs` builds bases along TWO legacy axes — `wt-<repo>` vs the legacy bare `wt`, and the current `<slug>-<id>` cell dir vs the pre-cutover bare `<slug>` one — and sums all of them. The bare-slug base is not optional — Claude Code filed every pre-cutover transcript under it, so dropping it would report zero for every job's history — and it is where two same-slug jobs still collide, unfixably: their transcripts are physically one directory. Both bases are PREFIX-matched against `~/.claude/projects`, because Claude Code buckets a transcript by the agent's startup CWD rather than the worktree root (a teammate spawned in a subpackage lands in a sibling dir like `…-wt-monolith-internal-dashboard`; missing those cost 5.0% of all cell spend). The match must be at a separator: the text between `-kraken-cells-` and `-wt-` is the CELL NAME, and `demo` id 25 munges to `demo-25` while `demo-2` id 5 munges to `demo-2-5`. The rows live in `job_tokens` (the counters, one row per job, what the board reads) and `job_token_files` (the per-file byte watermarks, what only the daemon reads) — schema v12, `internal/store/tokens.go` — split by reader so the hot read never sweeps the cold table, keyed on the immutable `job_id` (a slug-keyed row summed every generation of a reused name into one), with no FK and no cascade (an archived or hard-deleted job keeps its number); v12 DROPS every pre-existing token row. The refresh is `tokensPass` (internal/jobs/tokens.go, skipped under `--mirror`), which paces itself — every tick for a live cell, at most every 10 minutes and at most 8 per tick for everything else, all watermarks read in ONE query, `ResolveRepo` memoized for the pass, and no store write when nothing moved. The throttle stamp is written BEFORE the repo resolve can bail, or a job whose `repo:` no longer resolves consumes an idle slot and is due again every tick forever.

### Self-update and the iOS ship

`k update` (cmd/kraken/cmd_update.go) is the one implementation of the sequence — preflight (clean tree, on main, toolchain resolved to absolute paths; xcodegen alone resolves NON-fatally) → `git fetch` → `git merge --ff-only` (never `pull`, never `stash`, diverged means refuse) → `make build` → optional `go test` (`--test`) → `make install` → launchd restart → a best-effort sweep of any running `kraken mm lsp` (Zed's child holds the old binary's inode and Zed never restarts a live server, but it demand-starts a fresh one from PATH on the next matching buffer open) → `make install-mac` (deliberately after the restart: an Xcode failure finds the runtime already updated, and the record's `mac_app_sha` lets the next plain UPDATE click catch a missed app build up without `--force`) — writing each phase to `~/.kraken/update.json` (a FILE, not a store row: its writer outlives the `kraken serve` it restarts) behind a whole-run flock, and `--dry-run` reports without touching anything. The fetch is the one step that rescues itself: git authenticates it as whichever **gh account is ACTIVE** (`gh auth git-credential` is the credential helper `~/.gitconfig` names for `https://github.com`), and GitHub answers a private repo an unentitled token asks for with `Repository not found`. `jobs.RecoverGHAccount` (internal/jobs/ghauth.go) is the remedy: on a credential-shaped fetch failure it derives the account from origin's OWNER (never a hardcoded username), runs `gh auth switch --hostname github.com --user <owner>` (`--user`, never the bare form, which prompts once three accounts are logged in), confirms via `gh auth status --json hosts --jq …` (the plain form exits 1 when any account has an EXPIRED token, exactly the case the rescue exists for), and the updater retries the fetch exactly once. Its gates keep a machine-wide change from being made for nothing: a non-credential-shaped failure never reaches gh, an ssh or non-github origin is refused (read through `git ls-remote --get-url`, which applies `insteadOf` rewrites), an already-correct account is left alone (case-insensitively), `--dry-run` never reaches the rescue, and a refusal reports git's ORIGINAL error. The board's UPDATE button is `POST /api/update` (internal/api/update.go), which writes `phase=preflight` as its mutex, then spawns `kraken update --detached` with **`SysProcAttr{Setsid: true}`** — otherwise the child sits in the launchd job's process group and the `launchctl kickstart -k` it itself triggers kills it. The build tools run under a PATH prepended with the resolved `go`'s directory (`util.ToolchainEnv`/`util.PrependToolDir`, shared with the cell spawn). `jobs.ReadUpdateStatus` downgrades a run whose pid is dead, whose pid never claimed the record within 60s, or which has made no progress for 15 minutes (`updateMaxRun`) to `failed`. Separately, the daemon polls `origin/main` at most every 10 minutes (`kickUpdateAvail`) to decorate the button with a "N behind" count, skipped under `--mirror`.

`k ship-ios` (cmd/kraken/cmd_shipios.go) is a deliberate sibling of `k update`: same run-record shapes, and the same "the verb owns the record, a script owns the work" split — `ios/ship-testflight.sh` is the one implementation of xcodegen → `xcodebuild archive` → `-exportArchive` → `xcrun altool --upload-app`. The verb learns where a run has got to by **scanning the script's stdout** for its documented `KRAKEN-PHASE: <phase>` / `KRAKEN-BUILD: <n>` seam (`shipScanner`, which tees every byte to `~/.kraken/ship-ios.log`), never by inferring phases from elapsed time. Phases are `idle|preflight|generating|archiving|exporting|uploading|done|failed` in `~/.kraken/ship-ios.json`, behind a whole-run flock at `~/.kraken/ship-ios.lock` separate from update's — that lock serializes ship against ship, since two uploads racing to claim one build number is unrecoverable (App Store Connect burns a `CFBundleVersion` permanently). Ship against **update** is handled by refusal rather than a lock, because both drive `~/Developer/kraken` and an update's merge landing mid-archive yields an .ipa torn across two commits: each preflight reads the other's run record and says no (`PreflightShipIOS` refuses while `!UpdateTerminal`, `PreflightUpdate` while `!ShipTerminal`); a shared flock would only make one of them block silently for twenty minutes. `PreflightShipIOS` also refuses off main: the build number is `git rev-list --count HEAD`, and a branch's count can equal one main already uploaded. `jobs.ReadShipStatus` applies update's three staleness rules with a 45-minute deadline (`shipMaxRun`). Two things are deliberately unreachable from automation: `--allow-provisioning-updates` (the first run is by hand — `ios/TESTFLIGHT.md`), and the credentials, which come from `ASC_KEY_ID`/`ASC_ISSUER_ID` in the environment or `~/.kraken/asc.env` (`jobs.ASCEnviron`, injected into the script's environment; a file rather than `launchctl setenv` because setenv does not reach a job whose plist declares its own `EnvironmentVariables`), never written to the status file, the log, or an event. Those same credentials also authenticate the SIGNING: `-exportArchive` gets them as `-authenticationKey*` flags, because the distribution certificate is cloud-managed and Apple issues it per export (see the env-knobs section for why they ride on the export alone). Preflight resolves `xcodegen` to an absolute path via `util.ToolchainEnv`. `done` means **uploaded**, not installed.

### Invariants and code layout

Invariants that shape the code:

- **Verify before acting**: discovery output goes stale, so every destructive/targeted action re-checks the pane still holds the expected agent first (`checkSendTarget`, `verifyKillTarget`, `BranchGuard` in internal/core/actions.go and internal/core/branch.go; `RaiseSession`'s reattach fallback can close a window, so it guards with exact-match `SessionAlive`, a self-target refusal, never falling back on `errNoGhosttyWindow`, and standing down on a window this process opened inside the last 5 s — and raises of one session serialize in-process and wait for the opened window's client to appear before answering, because two opens issued inside Ghostty's launch gap each read "nobody attached" and the second's `attach -d` kicked the first). Preserve this pattern for new actions.
- `SessionIDGuessed` marks session ids inferred from cwd + newest transcript rather than a session file: fine for display, unsafe as a fork/read target.
- `k b` forks via `claude --fork-session -r <session-id>` in a tmux split, inheriting the source's permission mode from its transcript.
- `k k` refuses to kill the current pane and nested (Depth > 0) agents.

Tests (`cmd/kraken/main_test.go`, `cmd/kraken/viewer_test.go`, root `skills_embed_test.go`, plus a `_test.go` file alongside its source in each of internal/{util,core,jobs,api} and web) cover the pure functions — parsers, ordering, selection, rendering — by constructing `Peer` values directly; nothing shells out, so they run anywhere.

New code goes in the package matching its concern — CLI/rendering in cmd/kraken, tmux/discovery primitives in internal/core, sqlite accessors in internal/store, job/cell lifecycle in internal/jobs, wire handlers in internal/api, HTTP serving in web — and only exports what actually crosses a package boundary. The `util ← store ← core ← jobs ← api ← web` direction is load-bearing: a lower package must never import a higher one.

Every knob below can be set in the process environment or in `~/.kraken/env` (the environment wins — except for `PATH`, which the file PREPENDS to the inherited value, because the serve plist always supplies a PATH and a presence rule would make the file's dead on the daemon), and the file is the one way a knob reaches the launchd daemon and the hooks it spawns, since `launchctl setenv` does not reach a job that declares its own `EnvironmentVariables`. The per-person knobs, all read on every call: `KRAKEN_REPOS_DIR` (`jobs.repoRoot`) moves the repos dir off `~/Developer` — an absolute path, cleaned; unset, empty or relative falls back to `~/Developer` — and every repo reader (`ResolveRepo`, `RepoCandidates`, `PickRepo`, the mm render pass, the job editor's picker) goes through it, while kraken's OWN checkout is still `ResolveRepo("kraken")` under it (Q5), which is why the nightly dream pass is skipped (logged `dream-skipped`, once a day) on a machine without one. `KRAKEN_SELF_REPO` (`jobs.selfRepo`) names kraken's own checkout for `k update`, the availability poll and `k ship-ios`: an absolute path holding a `.git` (any other absolute path is an error naming the variable), or a repo name resolved under the repos dir; unset, it resolves `kraken` like a job's repo field. `KRAKEN_BRANCH_PREFIX` (`jobs.branchPrefix`) names the namespace cell branches are created under — default `kraken/`, a missing trailing `/` appended; `carl/` reproduces the pre-knob names byte for byte, and `branchFamily` matches both the current prefix and `carl/`. `KRAKEN_OPERATOR` (`jobs.Operator`) is the name every brief, context header, notice and materialized skill calls the person running kraken — trimmed, capped at 64 runes, falling back to `$USER` and then to "the operator", never to a built-in name; the repo-owned skills carry the literal `{{operator}}` and `installSkills` substitutes it into the cell copy only (inserted literally, never re-expanded; `MindPrompt` substitutes it the same way), while the board payload carries it as the additive `operator` key. `KRAKEN_LABEL` is a Makefile variable rather than a runtime one (see `make install` above).

Env knobs beyond the path overrides above: `KRAKEN_TAILSCALE` names the tailscale CLI the fleet shells out to (`core.ResolveTailscale`) — when set it is the ONLY candidate, a bare name PATH-looked-up and anything else used as given; unset, the ladder is PATH → `/usr/local/bin/tailscale` → the Tailscale app bundle's binary, and no candidate means no discovery and no node tier. `KRAKEN_NODES=off` (`jobs.FleetEnabled`) opts the machine out of the fleet in both directions — no discovery, no announce, no poll, an empty `/api/node/jobs` and a 404 on `/api/node` — and is the ONLY fleet knob: there is no seed list and no approval step, a kraken joins by existing on the tailnet. `KRAKEN_DEVICE_NAME` overrides the label every other board shows as a card's owner (`jobs.DeviceLabel`: the knob, else `scutil --get ComputerName`, else the tailscale hostname, else `os.Hostname()`). `KRAKEN_JOB_SLUG` is not a knob but a cell export: `withJobSlugEnv` (internal/jobs/cell.go) puts it on the command string of every claude zeus spawn, so `k s <node>/<slug>` run inside a cell — by zeus, or by a process zeus itself starts; a tmux teammate never sees it, since Claude Code forwards its own variables to a new pane but not kraken's — names the sending cell in the `[from … · cell <slug>]` prefix the remote zeus sees. Codex cells do not export it. `KRAKEN_SERVE_ADDR` overrides the localhost base URL a cell's pr-hook/recall-hook/logevent processes and agent-side verbs reach `kraken serve` at (`jobs.ServeBaseURL`, default `127.0.0.1:7777`); it is the cell export that has to reach the whole crew, so it rides the cell's `.claude/settings.json` `env` block (`mergeServeAddrSettings`, see the manual-testing bullet above), which Claude Code applies to every session started in the worktree. `KRAKEN_CODEX` names the codex launcher a codex cell spawns on (`core.ResolveCodex`) — when set it is the ONLY candidate, and one that is missing or below the 0.100.0 floor refuses the submit naming the variable rather than falling through to the ladder. `KRAKEN_CLAUDE` is its claude sibling (`core.ClaudeLauncher`). `CODEX_POOL_DIR` (`core.CodexPoolDir`) moves the codex account pool off `~/.codex-pool`, read on every call rather than cached so a test can point the whole pool at a directory it owns; an absent pool root is an empty pool rather than an error, so every codex job then spawns unbound on the machine's own `~/.codex` login. `KRAKEN_SIGN_ID` (`Makefile`, install target) picks the codesigning identity; unset falls back to the first identity `security find-identity -v -p codesigning` reports, and no identity is a warning rather than a failed install.

`ASC_KEY_ID` and `ASC_ISSUER_ID` (`internal/jobs/shipios.go`, `ios/ship-testflight.sh`) are the App Store Connect API credentials `k ship-ios` needs; both must be set or preflight refuses, they are passed through to the script's environment only, and their VALUES must never reach `~/.kraken/ship-ios.json`, `~/.kraken/ship-ios.log`, the event log, or any refusal message — only their names, and only to say one is missing. The matching private key lives at `~/.appstoreconnect/private_keys/AuthKey_<key id>.p8`, where `altool` finds it by convention, so the upload never names the key FILE (it does pass both ids as `--apiKey`/`--apiIssuer`). The EXPORT is the one bounded exception: App Store signing uses a cloud-managed distribution certificate Apple issues per run, fetching it requires xcodebuild to authenticate, and xcodebuild authenticates as the Apple ID signed into Xcode unless told otherwise — a dependency a launchd job cannot satisfy, which is how eight green ships turned into `exportArchive No Accounts` on 2026-07-27. So `ios/ship-testflight.sh` passes `-authenticationKeyPath`/`-authenticationKeyID`/`-authenticationKeyIssuerID` (its `ASC_AUTH`) to `-exportArchive`, putting those values in that child's argv. They still never reach the log, and the placement guarantees it: `xcodebuild archive` echoes its own full command line as its first output and `-exportArchive` does not, so the flags go on the export ALONE (`TestShipScriptKeepsCredentialOffArchive` pins it). A ship started from the board inherits `kraken serve`'s launchd environment, so both must be set there too.

The binary has three outbound API clients: the Slack and Linear intakes and the TypeSafe dialog answerer (the knowledge graph's OpenAI embedder was a fourth until job 542; `~/.kraken/openai.env` and the `OPENAI_*` variables are read by nothing). `SLACK_USER_TOKEN`, `SLACK_D_COOKIE` and `SLACK_USER_ID` (`internal/core`, `LoadSlackConfig`) configure the Slack intake bot, the only client that reads a human's messages. `SLACK_USER_TOKEN` is carl's own user token in one of two kinds. An `xoxp-` token is minted by installing a personal single-user Slack app, needs nothing beside it, and does not expire (rotation stays OFF, since it is irreversible and buys a 12h refresh treadmill for nothing). An `xoxc-` token is the one carl's own Slack client carries, and it is only half a credential: Slack binds it to the browser session cookie named `d`, so `SLACK_D_COOKIE` must carry that cookie's value verbatim or every call is rejected. That pairing is validated at load — an `xoxc-` token with no cookie returns `core.ErrSlackHalfConfigured`, which callers LOG (unlike `ErrNoSlack`, which they never do), because a half-configured poller is silent, doomed, and fixable by one line. The session kind is session-scoped, so a sign-out invalidates it with nothing to refresh it. `SLACK_USER_ID` is optional — absent, the daemon learns it once from `auth.test` and caches it in kv. Process env wins over `~/.kraken/slack.env`, and the loader's allowlist is exactly those three names. An absent token means `core.ErrNoSlack`, which every caller treats as "feature not configured" — the poll pass, the delivery pass and the iris spawn all become silent no-ops. The token's VALUE must never reach a log, a status file, an event, an API response, or any error message — only its name, and only to say it is missing; `GET /api/slack/status` therefore reports a load failure as `configured: false` and drops the error. A missing, unreadable or malformed file yields `ErrNoSlack` and never any other error (an error carrying a parse position of a credential file is a step towards an error carrying its contents). `LINEAR_API_KEY`, `LINEAR_DEFAULT_REPO` and `LINEAR_STATES` (`internal/core/linear.go`) configure the Linear intake: the personal API key the GraphQL client sends as a bare `Authorization` header, the `repo:` every job it creates gets (unset, the job takes `jobs.DefaultRepo()` — the sole checkout under the repos dir, else an empty `repo:`), and the comma-separated workflow STATE NAMES an issue must be in to qualify (default `Today`, matched case-insensitively). Process env wins over `~/.kraken/linear.env`, a malformed file degrades to the env-only view, and an absent key means the feature is off — `LinearPass` returns silently. The key's VALUE must never reach a log, an event, a status file, an error message, a job body, or a notification — only its name, exactly the ASC and Slack rules above. `TYPESAFE_API_KEY` and `TYPESAFE_MODEL` (`internal/core/typesafe.go`, `LoadTypeSafeConfig`) configure the dialog answerer: the key `TypeSafeClient` sends as `Authorization: Bearer`, and the Jev model the request names (default `jev-latest`). Process env wins over `~/.kraken/typesafe.env`, only those two names are read, a missing or malformed file degrades to the env-only view, and an absent key means `NewTypeSafeClient` returns nil and `jevPass` does nothing. The key's VALUE must never reach a log, an event, a decision line or an error message: a non-200 body is quoted with every occurrence of the key replaced by `[redacted]`.

The value-never-logged rule has a conversational half, and it binds every agent for every credential in this table: never INVITE a secret's value into the pane. When a credential file needs writing, hand carl the `printf '…' >> ~/.kraken/<file>.env && chmod 600 …` line to run himself — "paste it here and I'll write the file" puts the value into a Claude transcript, which later readers of that session (the dream sweep) then copy forward into new transcripts and kraken.db indefinitely. `core.redactSecrets` scrubs known token shapes from both readers' emission points as a backstop, but the invitation is the defect: a transcript, once written, is Claude-owned and cannot be clawed back.

## Protocol parity

Two protocols cross machine boundaries, and both are **kraken-core's**: they are identical in every fork, byte for byte at the wire, and any build of kraken-core interoperates with any fork in every direction — node↔node and phone↔node for the multiplayer protocol, and a fork updates exactly the way core updates. The **multiplayer protocol** is node discovery and announce (`tailscale status`, `POST /api/node/announce`), the `NodeEnvelope`, the routes a node serves to its siblings and the proxies a board calls on them — `/api/health`, `/api/node`, `/api/node/action`, `/api/node/announce`, `/api/node/artifact`, `/api/node/job`, `/api/node/job/raw`, `/api/node/jobs`, `/api/node/read`, `/api/node/thread/read`, `/api/node/transcript`, `/api/nodes`, `/api/nodes/action`, `/api/nodes/artifact`, `/api/nodes/job/raw`, `/api/nodes/read`, `/api/nodes/thread/read`, `/api/nodes/transcript` — the request gate's four tiers (owner, paired, node, anon), the pairing handshake and token (`/api/pair`, `/api/pair/challenge`, `/api/pair/devices`, `/api/pair/password`, `/api/pair/revoke`), the node action verb list, and the `[from …]` stamp a relayed message carries. The **update protocol** is `k update`'s phase sequence and its `~/.kraken/update.json` record, `/api/update` and `/api/update/status`, the availability poll, and the gh account rescue. A change to either is a protocol change and is flagged to the person making it: every protocol-bearing file (`internal/api/nodes.go`, `pair.go`, `gate.go`, `update.go`; `internal/jobs/node.go`, `nodes.go`, `update.go`, `ghauth.go`; `internal/core/tailscale.go`; `internal/store/nodes.go`, `pair.go`; `cmd/kraken/cmd_nodes.go`, `cmd_update.go`; `ios/Kraken/Pairing.swift`) opens with a `Protocol parity:` header comment saying so, the change lands in kraken-core FIRST and reaches every fork by sync (a fork's PR may be opened at the same time but merges only after core's), its PR title carries `protocol:`, and the agent making it names it as a protocol change in its final message before anything is pushed. An additive, omitempty card key is not a protocol change; a required key, a route, a gate tier, an action verb, the envelope, the pairing handshake or the update sequence is. `TestProtocolParityDocCoversTheSurface` (internal/api/protocolparity_test.go) pins this section against the registered routes and the header comments.

## Conventions

- Keep it stdlib-only outside the viewer; new dependencies need a strong reason.
- Data sources owned by other programs (session files, transcripts, codex logs) are read defensively — missing/malformed files degrade to blank fields, never errors — and content that is present but can go STALE is cross-checked against a live signal where one exists: a session file's `busy` outlives the turn when teammates stay resident, so `refinedStatus` overrules it against the pane's own spinner rather than trusting it at face value.
- **Model policy**: every claude kraken *spawns* runs on a model kraken names, passed explicitly as `--model` via `core.ModelArgs` — never left to claude's own config, the one mid-session change being the Fable fallback — and there are exactly three, split by ROLE. `core.DefaultModel` (`claude-opus-5`) is what `k c`, the board's spawn action and a cell's side threads get. `core.ZeusModel` (`claude-fable-5-1`) is the cell lead's, and the only reader that puts it on a command line is `jobs.zeusModel`, which both cell spawn paths (`StartCell`, `ReactivateJob`) resolve through via the one `zeusSpawnArgv` seam (`TestZeusSpawnPathsResolveTheModel`): zeus' turnaround IS the cell's latency, while the work that wants the deep tier is what it delegates. Between `zeusModel` and the argv sits the Fable fallback's SPAWN-TIME arm, `jobs.zeusLaunchModel`: `spawnModel` (modelfallback.go) demotes the configured model to `core.FableFallbackModel` when the account the cell is about to bill (its binding, stamped by `bindAccount` before either spawn path reaches the argv, else main) already shows Fable at 100% in the usage snapshot with session, weekly and Opus short of their caps (`opusHasRoom`, the gate the mid-run arm reads); no snapshot row, a reset-past Fable window, or any other window spent leaves it alone. The answer is memoized on the Job for one spawn chain so the argv and the brief's resolved-tier line cannot disagree, and `spawnCommand` stamps the argv's `--model` into the cell dir (`zeus-model`). What is zeus-only is the FALLBACK, not the field: a job's `model:` overrides zeus and its side threads alike (`jobs.threadModel` falls back to `j.Model`, then `DefaultModel`), and a side thread may carry its OWN model, picked in the branch overlay from the four aliases `core.ThreadModels` maps to exact ids (`haiku`/`sonnet`/`opus`/`fable`), stored on the thread row, re-read on every revive, resolved FIRST, and refused outside the four (there, and earlier with a 400 by the API). The brief states zeus' tier as the RESOLVED id rather than the constant's name, which is also why `ReactivateJob` stages a brief where it used to pass `""` (`TestZeusSpawnPathsStageTheBrief`): a resumed session does not retain an earlier run's `--append-system-prompt`, and the brief is the only statement of the crew's `model: opus` in context on EVERY turn — briefless, an Agent call that omits the model can inherit ZEUS' tier. `core.IrisModel` (`claude-fable-5-1`) is the third, with NO fallback function: `jobs.irisSpawnCommand` passes it directly, since iris belongs to no job and no `model:` field can override it; it is its own constant rather than an alias of `ZeusModel` because the two answer different questions (the lead's turnaround versus a Slack triage loop's tier). `k b` is outside all of this: a fork continues an existing session. The crew is a THIRD mechanism, not a `--model`: zeus' brief (internal/jobs/crew.go) and the skills pin every agent it spawns — hephaestus, athena, hermes, all TEAMMATES — to `model: opus`, an Agent-tool tier alias. Net effect: a cell is one Fable lead over an all-Opus crew. All three constants are pinned to exact ids rather than aliases. A CODEX cell's zeus follows the same rule through `core.CodexZeusModel` (`gpt-6-astra`), passed as `-m` by `jobs.codexModelArgs` — always a flag, overridden by the job's `model:` exactly as zeus' claude tier is. The codex LAUNCHER is resolved too: `core.ResolveCodex` walks `$KRAKEN_CODEX` → PATH → `~/.nvm/versions/node/*/bin` newest node first → `~/.local/bin` → `/opt/homebrew/bin` → `/usr/local/bin` (`codexSystemDirs`), probes each with `--version`, and returns the first ABSOLUTE path at or above `codexMinVersion` (0.100.0), which `codexCellArgs` puts as argv[0]; `jobs.codexPreflight` runs the same resolution as `SubmitJob`'s last refusal rung. It exists because `kraken serve`'s launchd PATH carries no nvm dir, so a bare `codex` resolved to homebrew 0.39.0, which exits at startup on the modern config.toml (job 428 died in four seconds). What is additionally pinned is the SPLIT: `DefaultModel` must differ from `ZeusModel`, since collapsing them would retire the lead/crew tier split with every other test green. `IrisModel` is deliberately NOT pinned against either: it equals `ZeusModel` today by coincidence, not by contract.
- **API contract**: any change to JSON served to or accepted from the iOS app/web UI (internal/api/*.go, web/serve.go, internal/jobs/daemon.go, internal/jobs/job.go) lands in the same commit as `ios/API.md`, `ios/Kraken/Models.swift`, and `internal/api/contract_test.go`. `apiContract` (internal/api/board.go) bumps only on breaking changes — a key retyped, renamed, or removed, or a change in who may call a route a shipped client already calls (v7, the request gate) — mirrored by `expectedContract` in `APIClient.swift`; additive keys never bump it.
