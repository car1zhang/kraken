# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

kraken (`k`) is a macOS CLI/TUI for managing live Claude Code and Codex sessions across tmux: list them (`k ls`), watch them (`k v`), jump to one (`k o`), message one (`k s`), read its transcript tail (`k r`), fork it (`k b`), kill it (`k k`), spawn new shells/claudes (`k n`/`k c`). Run `k help` for full usage.

## Commands

- `make build` — build the `kraken` binary. It also **stamps the running build's short SHA** into it (`-ldflags "-X kraken/internal/util.BuildSHA=$(SHA)"`, read back by `util.Build()` and shown on the board's update button), so the package path in that flag must stay in step with `internal/util/build.go`: the linker silently ignores an `-X` it can't resolve, and a wrong path means `Build()` returns `"dev"` forever with nothing anywhere reporting a problem. Building with a bare `go build` (no `make`) has the same effect and is fine — an unstamped binary is only undecorated, never broken.
- `make install` — build + install to `~/.local/bin` (with `k` symlink) + zsh completion. **Never `cp` over the installed binary directly**: macOS SIGKILLs running processes whose backing binary changes (code-signature invalidation). The Makefile copies to a temp name and `mv`s (atomic rename) for this reason. Install also **code-signs** the fresh binary before that `mv` (identity `$(KRAKEN_SIGN_ID)`, else the first keychain codesigning identity; never fatal, never `--options runtime`): a Go binary is ad-hoc signed, so its designated requirement is a hash of its own bytes and every rebuild looked like a brand new app to TCC, re-prompting for the `~/Documents/pluto` grant — a real identity plus the stable `--identifier dev.carl.kraken` makes that grant survive rebuilds. The launchd restart is `launchctl kickstart -k`, not `unload`+`load`: kickstart is one atomic kill-and-relaunch with no window in which the job is unloaded, which matters because the daemon is sometimes the process running this recipe (`k update`) and an `unload` would kill the recipe before its `load`. `install-serve` regenerates the plist to a temp file and only `bootout`+`bootstrap`s when the content actually changed — kickstart relaunches from launchd's cached in-memory definition and never re-reads the plist, so plist edits are otherwise inert until logout.
- `make ios-testflight` — build the iOS app and upload it to TestFlight. A thin alias for `./ios/ship-testflight.sh` (pass flags with `ARGS=`, e.g. `make ios-testflight ARGS=--dry-run`) and deliberately logic-free: the script is the ONE implementation, and `k ship-ios`/the board button call it directly, so anything added here would make a hand-run ship differ from a board-run one. The first run ever needs `ios/ship-testflight.sh --allow-provisioning-updates` by hand — it creates certificates and profiles on the real Apple developer account, which is why no automation can reach it. Setup: `ios/TESTFLIGHT.md`.
- `go test ./...` — run all tests
- `go test -run TestName ./<pkg>` — run a single test (main-package tests: `./cmd/kraken`; skills-embed tests: `.`)
- `go vet ./... && gofmt -l .` — lint

## Architecture

The binary is split into a strict dependency chain of packages, each owning one layer: `cmd/kraken/` (package main: CLI dispatch, `k ls` rendering, the bubbletea viewer, plus the `_k` zsh completion script) + `internal/util/` (stdlib-only helpers) + `internal/store/` (the sqlite layer: `kraken.db` schema + typed accessors) + `internal/core/` (discovery, `Peer`, tmux primitives, claude spawning, transcript reading, usage) + `internal/jobs/` (job files, cells, crew briefs, status derivation, archive, daemon) + `internal/api/` (JSON handlers + wire types, `apiContract`, `api.Register`) + `web/` (embedded SPA in `web/static/`, artifact serving, bind logic, `web.Serve`). The layout rule: `cmd/` and `internal/` are pure Go; `web/` stays top-level because it carries the SPA's static assets, and one Go file stays at repo root — `skills_embed.go`, the module-root `package kraken`, pinned there because `go:embed .claude/skills` can't reach above its package directory (cmd/kraken blank-imports it so its init() wiring runs). The dependency DAG is `util ← store ← core ← jobs ← api ← web`, and `cmd/kraken` imports all of them; importing upward is forbidden (and impossible without an import cycle). The only direct dependency is bubbletea (viewer TUI); all else is stdlib. External state is shelled out to: `tmux`, `ps`, `lsof`, `git`, `gh` (read for PR state, and WRITTEN by the updater's account rescue — see below), `osascript`, `python3` (the doc pipeline's fragment linter and card-wrap substitution run via python3 in cells).

The core type is `Peer` (internal/core/peer.go): one live agent process in a tmux pane, an in-process teammate known only from a team config (`Messageable=false`), or an agent-free shell pane (`Role "shell"`).

Data flow, shared by `k ls`, the viewer, and completion:

1. **Discovery** (internal/core/discover.go): `DiscoverAll()` snapshots tmux panes (`tmux list-panes -a`) and the full process table (one `ps` call), then walks each pane's process subtree for claude/codex processes. Agents in a pane are listed deepest-first: index 0 is the foreground agent — the one `tmux send-keys` actually reaches; deeper ones are nested subagents. Enrichment comes from `~/.claude/sessions/<pid>.json` (session files Claude Code maintains), `~/.codex/session_index.jsonl` + lsof for codex, transcript files under `~/.claude/projects/<munged-cwd>/`, and `git`/`lsof` for branch/cwd. lsof is the slow path — results are memoized in package-level caches (`cwdCache`, `codexSessionCache`) because the viewer polls discovery on a tick.
2. **Refinement + nesting** (internal/core/peer.go): `refineStatus` peeks pane content via `tmux capture-pane` to detect blocked/question prompts; `nestTeams` attaches teammates to their leads using `~/.claude/teams/*/config.json`; `OrderAll` produces the single flat numbering that every selector references.
3. **Selection** (internal/core/select.go): `SelectPeer` resolves a user selector — index, `.` (current pane), exact pane id (`%3`), session-uuid prefix (≥4 chars), or substring match — against that ordering.
4. **Action or render**: actions (internal/core/actions.go, internal/core/branch.go) drive tmux (`send-keys`, `kill-pane`, `new-window`) and ghostty focus via AppleScript, called from cmd/kraken's thin cmd wrappers (cmd/kraken/cmd_actions.go, cmd/kraken/cmd_branch.go); the one exception is `k b`'s `tmux split-window`, issued directly from cmd/kraken/cmd_branch.go. Rendering is cmd/kraken/ls.go (tables, grouping modes, colors) and cmd/kraken/viewer.go (bubbletea TUI that re-runs discovery on a tick and reuses ls.go's group/row builders).

Jobs and cells are a separate subsystem layered on top of the above. Two orthogonal extras sit beside the five states: **archived** jobs (internal/jobs/archive.go) are job files moved into `~/Documents/pluto/archive/` — out of the active namespace entirely (slug freed, invisible to the daemon), numbered `foo-2.job.md` on name conflicts, restorable via the board's unarchive action (state preserved; refused while the slug is taken) and hard-deletable only from the archive. **Reactivation** (the board's reactivate action, internal/jobs/cell.go) resurrects a done job into its original zeus session: kraken stamps zeus' session id into the job file (`session:` frontmatter) from the daemon's first tick after the cell comes up, so a done job can later be resumed with `claude -r` in a recreated worktree at the same path; the `carl/<slug>` branch recycles (reset off the base once fully merged), falling back to `carl/<slug>-rN` (`run:` frontmatter) only when leftover unmerged commits would be orphaned. A job (internal/jobs/job.go) is one `<slug>.job.md` file in `~/Documents/pluto`, parsed strictly into a five-state board model — draft · queued · working · blocked · done — that kraken derives, never hand-writes: `internal/jobs/status.go`'s `deriveState` combines the job file's own `state` with the live-ness and a ROLL-CALL of the cell's claudes (`cellActive`: the zeus pane peer's own status, any nested subagents in its session, and non-lead team members cross-checked against live tmux panes — any one alive-and-running votes the cell into working, else it reads blocked) to decide working vs. blocked, and `internal/jobs/status.go`'s `FindPendingQuestion` pulls any still-open `AskUserQuestion` tool call straight out of zeus' transcript for the web board and iOS app to render as answer buttons. A cell (internal/jobs/cell.go) is one job's runtime: a dedicated git worktree plus a tmux session holding **zeus**, the job's only working agent, in its first pane — there is no separate relay agent and no escalation-bus file; zeus reports status by simply saying it in its own pane, which the board surfaces as the cell's detail line. Beside zeus a cell may hold zero or more **side threads** (internal/jobs/thread.go): carl branches one to ASK about the work — usually about the very block he is staring at — and it comes up as a fork of zeus' session (`--fork-session` under a kraken-minted `--session-id`, named `thread-<slug>-<tid>`) in its own window of that same tmux session, reading the same worktree. Threads are rows in `kraken.db` (`internal/store/threads.go`), and a row is a POINTER, never a transcript: it owns identity, provenance, and the live pane/window, while claude's own transcript — located by `session_id` — is the conversation, so nothing is ever snapshotted and there is no per-job cap. Kill ends the window and closes the row; revive resumes the SAME session in a fresh window; teardown closes every row without deleting one, so a torn-down job's threads stay readable. A thread must never disturb the job it hangs off, which is three exclusions all keyed off thread.go: it never votes in the working/blocked ROLL-CALL (`cellActive` takes the live thread panes as a skip set — a voting thread would hold a blocked job at "working" and hide the very block carl branched to investigate), it can never be elected zeus (`CellZeus` filters both the thread name prefix and the live thread panes — elected, it would feed `stampSession` a thread's session id, suppress the dead-cell alert, and take carl's steer messages), and Stop never interrupts it (`InterruptCell` skips the same panes: Stop means stop the job). Deciding a thread is GONE demands positive evidence, never just a missing name: `Peer.Name` only appears once claude writes its session file, so the daemon's reconcile pass leaves a row alone while it is inside its spawn grace window, while a still-nameless claude sits in its pane, or when the tick's tmux snapshots contradict each other — closing a LIVE row would un-skip its pane in the roll call, orphan kill/send, and let a revive start a second claude on one session id. Zeus' system prompt (internal/jobs/crew.go) is unified — there is no job-level `type` any more (Q14): zeus itself decides, from the job spec text, whether a doc phase runs at all and which of Phase 1's two paths it takes. The brief carries ONLY what no skill can know — identity, the cell's real paths, how carl is reached, the model tier, the hephaestus/athena teammate crew, the self-destruction guardrails, and which skill governs each phase — and points at `.claude/skills/{info,aim,do,pr,dream}` for every procedure rather than restating one; each skill's "Inside a kraken cell" section owns its phase's exact closing line. It is staged as a FILE (`<cell dir>/zeus-brief.md`, with the initial prompt beside it as `zeus-prompt.md`) and referenced from the tmux command with `"$(cat …)"` via `spawnCommand`/`core.ShellReadFileArg`, never passed inline: tmux caps a command at ~16KB and rejects anything longer with a bare `command too long`, which is exactly how a brief that had grown to 17.5KB by inlining the whole `/aim` pipeline wedged every cell spawn. Two tests hold the line — `TestZeusBriefDoesNotRestateSkills` (the brief must not copy a skill) and `TestSkillsOwnTheCellContract` (a skill must not drop what the brief handed it). The **spec path** is `/aim`: research, then the flat artifact set below plus open questions, stopping at the `/do` gate. The **explanation path** is `/info` (read by path from the cell's `.claude/skills/`, since a personal skill of the same name shadows it): research just as deeply, but ship ONE brief `00-overview.md` ending in a "go deeper" menu, then exactly one focused artifact per round carl asks for — never `/aim`'s section-doc floor unasked, and **never any questions rows** (questions are a spec-path tool; an explanation job's list stays empty). What happens next is carl's move, not the job's: when he sends `/do`, phase 2 begins — implement → a manual-test gate (zeus reports "manual test ready" and stops until carl's reply passes it) → `/pr` (opens the PR, reports the URL, and stops — the daemon, not zeus, watches CI and bumps zeus' pane on failing checks or new comments) — delegating slices to hephaestus TEAMMATES that zeus itself manages, reviewing each with three parallel single-dimension athena variants — athena-logic, athena-edge, athena-style; a purely explanatory job never gets a `/do` and never opens a PR — carl accepts it by hand instead (board Done). The pipeline renders its diagrams via per-figure hermes teammates, one per diagram id (`hermes-<diagram-id>`), resumed by name for a lint fix round rather than respawned. Every one of those agents is a TEAMMATE rather than an in-process subagent — an Agent-tool call carrying a `name`, which is what gives it its own tmux pane, a team-config row `nestTeams` hangs under the cell (so carl sees and can attach to it in `k ls`/`k v`), and an address `SendMessage` can resume with its context intact; unnamed subagents are reserved for read-only exploration, which means changing nothing in the repo rather than writing no file at all — such a subagent still writes its own report to a scratch path, since a report that exists only as a chat reply is one the lead may never receive. That promise is enforced, not assumed: `mergeTeammateSettings` (internal/jobs/cell.go) writes `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` and `teammateMode: tmux` into the cell's own `.claude/settings.json` beside the pr-hook entry, merged never clobbered, so the crew does not silently degrade to in-process subagents when the user's personal settings change. Two rules bound the delegation: it must be **earned** — zeus makes small coherent edits itself and reaches for hephaestus only when the work genuinely splits into independent slices, while the athena review runs in parallel every time regardless of who wrote the code — and an agent is torn down on **acceptance**, not on reporting done, since a blocking finding has to go back to the same teammate. Zeus also never prompts: carl does not watch the pane, so an interactive question there is invisible AND blocking; zeus defaults, states the call in its final message, and keeps going, with `AskUserQuestion` a last resort and spawned agents forbidden from asking anything at all. The doc phase produces a flat artifact set, never a single combined file: `00-overview.md` + `10`-`49` diagram cards + `50`+ section docs — there is no flatten step; each artifact is complete and shareable the moment it's written. Phase 2 closes by adding `90-build-report.md` (specified end to end in `.claude/skills/do/SKILL.md`): a ≤1-page record of what actually shipped, every discrepancy between the plan and reality, complications, deferrals, and verification — written on every phase 2, including jobs that never had an artifact set, with "None" spelled out rather than a section dropped. Open questions and carl's per-artifact feedback are rows in `kraken.db` behind `kraken serve`, not files — zeus reads/writes them via cell-side `kraken questions`/`kraken feedback` verbs. All five pipeline skills (`info`, `aim`, `do`, `pr`, `dream`) are repo-owned, checked into `.claude/skills/`, embedded into the binary by `skills_embed.go` (repo root), and materialized into `<cell worktree>/.claude/skills/` at cell creation (`internal/jobs/skills.go`) so zeus can read them by path (personal skills shadow the names). Cells and PRs are many-to-one: the daemon's PR tracker records every PR shipped from the cell branch into the job's kraken-owned `prs:` frontmatter list (url + state, plus two kraken-owned watermark keys per PR — `last-comment-at`, `bumped-sha` — frontmatter-only, never on the wire; a merge is a notification + board chip, NEVER a teardown trigger — teardown lives only behind carl's explicit accept via board Done, and there is no `k reap`), and zeus recycles `carl/<slug>` off origin/main after each merge for follow-up PRs. The daemon (internal/jobs/daemon.go) queues ready jobs into cells, tracks PRs, watches open PRs of active jobs for new comments or failing CI and bumps zeus' pane when either appears, reconciles each working/blocked cell's **colour** into that same pane, and flags dead cells, owning nothing it can't reconstruct from job files plus discovery after a restart. The colour pass (internal/jobs/color.go, `syncCellColor`) is the second thing the daemon types into a live pane unprompted, after the PR watcher's bumps, and it is deliberately the smallest: a job's optional `color:` is one of the eight names Claude Code's own `/color` accepts (`Palette`, in `/color`'s order, with a dark hex, a WCAG-AA light hex, and an xterm-256 slot per entry — the same sixteen hexes are spelled out in `web/static/style.css` and `ios/Kraken/Theme.swift`, kept in step by `TestJobPaletteMatchesCSS`/`...MatchesSwift`), unset means NO colour rather than one auto-assigned, and kraken sends `/color <name>` (never a BARE `/color` — with no argument Claude Code picks one AT RANDOM) only when the wanted colour differs from the `color.applied` watermark, so a `/color` typed by hand survives and nothing is ever reasserted. It is hand-authorable like `model:` (`JobTemplate` offers a commented `# color:` line) and lands in the row through the raw editor's own parse like every other frontmatter field, but the FORM save never writes it: `POST /api/job/color` is the only form-side writer — a one-field route rather than a job-form field, because colour is cosmetic and so is usable on a LIVE cell (the form save's `editableJob` gate covers exactly the states the delivery pass ignores, which would have made the feature unreachable), and because a full-replace form save from a client predating the field would silently clear it. Every job interaction — starting, completing, archiving, reactivating — is CLI-free (Q14): `k`'s own surface is tmux/peer management only, and `kraken serve` is the sole runtime — the scheduler tick loop plus the web UI/API in one process (opens `~/.kraken/kraken.db`, the store `kraken import` one-shot-migrates any legacy file stores into) — `make install` installs it unconditionally. At every cell spawn, RotationGate (internal/jobs/rotation.go) may swap the main login to a healthier `~/.claude-pool` account in auto mode, never blocking or failing the spawn (`k account <slug>` pins manual; `k account auto` releases it).

The **dream loop** closes the feedback circuit that the feedback rows above only open. A nightly pass inside `kraken serve` (internal/jobs/dream.go, hung off the daemon tick and skipped under `--mirror`) fires at most once per local calendar day — the first wall-clock cadence in the binary, gated on a `dream_last_run` kv watermark whose stored LOCAL DATE, not an elapsed duration, is the comparison, so a Mac asleep at midnight fires on the first tick after it wakes instead of skipping the night. It runs whenever the last 24h hold at least one claude session OR at least one feedback row, which in practice is every night, and it creates a `dream-<YYYY-MM-DD>` job row (`internal/jobs/dream.go`'s `CreateDreamJob` — the codebase's first programmatic job creator; every other job is born from the board's `/api/job/create`) whose spec invokes `/dream`. The existing queue pass then starts its cell like any other job's. That cell reads TWO evidence sources: carl's per-artifact feedback, swept cross-job and `ts`-floored via `kraken feedback sweep` (the first caller of `store.ListFeedback`'s long-advertised unscoped sweep) with each row's frozen `snapshot` now served by its own route; and the past day's transcripts, mined by `internal/core/mine.go` — reached from inside the cell through `k mine digest|reduce` (`cmd/kraken/cmd_mine.go`), the one verb in this family that does NOT proxy to `kraken serve`, since it reads Claude-owned files rather than kraken.db rows and so needs no lock and no daemon — in one forward pass that both COUNTS the mechanical signals (tool mix, `is_error` clusters attributed to the failing tool, `[Request interrupted` markers, `<synthetic>` API failures, `turn_duration`) and REDUCES each session to the ~13% of bytes that are decision-relevant (user prose + tool calls + assistant text; thinking, tool results and attachments dropped) — the reduction is what makes the second pass affordable, since a scout then reads ~85KB rather than ~700KB, and it must cover the `<session>/subagents/agent-*.jsonl` sidecars that hold ~24% of all tool calls and that no other reader in the binary opens. Findings corroborate against the `watchlist` table (internal/store/watchlist.go): global state belonging to NO job, so unlike `questions` and `feedback` it carries no `job_id` and no cascade, with `verdict`/`comment`/`commented_at` CARL-OWNED exactly as `questions.answer` is — `UpdateWatchItem` must preserve them, and a repeat of an existing observation folds into its row rather than adding one. The destination rule is the load-bearing invariant and it is structural rather than a redaction filter: **findings never enter git**. A PR carries the hardened diff and nothing else; the evidence, the watchlist and the prompting feedback (the loop's third output — where carl's own prompting sent an agent astray, quoted verbatim) stay local in `kraken.db` and in `00-dream-report.md`, which the board's `DREAM` view renders out of the artifacts table the existing block-event sync already mirrors, so no new persistence path and no file/DB dual-write.


Kraken updates itself. `k update` (cmd/kraken/cmd_update.go) is the one implementation of the sequence — preflight (clean tree, on main, toolchain resolved to absolute paths) → `git fetch` → `git merge --ff-only` (never `pull`, never `stash`, diverged means refuse) → `make build` → optional `go test` (`--test`) → `make install` → launchd restart — writing each phase to `~/.kraken/update.json` (a FILE, not a store row: its writer outlives the `kraken serve` it restarts) behind a whole-run flock, and `--dry-run` reports without touching anything. The fetch is the one step that rescues itself: git authenticates it as whichever **gh account is ACTIVE** (`gh auth git-credential` is the credential helper `~/.gitconfig` names for `https://github.com`), and GitHub answers a private repo an unentitled token asks for with `Repository not found` — so with the wrong account signed in the update dies at its first network call with a message that reads like the checkout pointing at a repo that moved. `jobs.RecoverGHAccount` (internal/jobs/ghauth.go) is the whole remedy: on a fetch failure whose text is credential-shaped, it derives the account it needs from origin's OWNER (never a hardcoded username, same rule as `util.Home()`), runs `gh auth switch --hostname github.com --user <owner>` — `--user`, never the bare form, which needs a prompt nobody is there to answer once three accounts are logged in — reads the active account back to confirm, and the updater retries the fetch exactly once. That read is `gh auth status --json hosts --jq …` rather than the human-readable form for one reason: the plain form exits 1 when any account has authentication issues — an EXPIRED token, which is both a reason git says `Authentication failed` and a reason gh exits non-zero — and `--json` is documented to exit zero regardless, so the answer to "who is active?" survives exactly the case the rescue exists for. Every gate on that path is there to keep a GLOBAL, machine-wide state change from being made for nothing: a fetch failure that isn't credential-shaped (no network, a corrupt object) never reaches gh at all, an ssh or non-github origin is refused since gh's helper only governs `https://github.com` (read through `git ls-remote --get-url`, the form that applies `insteadOf` rewrites, so a remote written as https but dialled over ssh is refused too), an account that is already correct is left alone (case-insensitively — GitHub logins are), and `--dry-run` never reaches the rescue at all, since a flag documented as changing nothing must not re-sign the machine in. When it refuses, the caller reports git's ORIGINAL error, never the refusal — the refusal only explains why the rescue didn't apply. The board's UPDATE button is `POST /api/update` (internal/api/update.go), which does no work itself: it writes `phase=preflight` as its mutex, then spawns `kraken update --detached` with **`SysProcAttr{Setsid: true}`** — without a new session the child sits in the launchd job's process group and `launchctl kickstart -k`, which the child itself triggers, kills it before it can record that it finished. The build tools run under an environment whose PATH is prepended with the resolved `go`'s directory (`toolchainEnv`), because `make build` invokes a bare `go` and launchd's PATH does not lead to one. `jobs.ReadUpdateStatus` downgrades a run whose pid is dead, whose pid never claimed the record within 60s, or which has made no progress for 15 minutes (`updateMaxRun`) to `failed`, so a hung `codesign` or a recycled pid can't wedge the button forever. Separately, the daemon polls `origin/main` at most every 10 minutes (`kickUpdateAvail`) to decorate the button with a "N behind" count, in a fire-and-forget goroutine, skipped under `--mirror`.

Kraken also ships its own phone app. `k ship-ios` (cmd/kraken/cmd_shipios.go) is a deliberate sibling of `k update`, not a new subsystem: same run-record shapes, and the same "the verb owns the record, a script owns the work" split — `ios/ship-testflight.sh` is the one implementation of xcodegen → `xcodebuild archive` → `-exportArchive` → `xcrun altool --upload-app`, exactly as `k update` shells out to `make install`. The verb learns where a run has got to by **scanning the script's stdout** for its documented `KRAKEN-PHASE: <phase>` / `KRAKEN-BUILD: <n>` seam (`shipScanner`, which tees every byte to `~/.kraken/ship-ios.log` unchanged), never by inferring phases from elapsed time — these phases differ in duration by two orders of magnitude. Phases are `idle|preflight|generating|archiving|exporting|uploading|done|failed` in `~/.kraken/ship-ios.json`, behind a whole-run flock at `~/.kraken/ship-ios.lock` that is separate from update's — that lock serializes ship against ship, since two uploads racing to claim one build number is unrecoverable (App Store Connect burns a `CFBundleVersion` permanently). Ship against **update** is a real conflict too, and it is handled by refusal rather than by a lock, because the two runs are *not* disjoint: both drive `~/Developer/kraken`, so an update's `git merge --ff-only` landing mid-`xcodebuild archive` yields an .ipa torn across two commits uploaded under the pre-merge build number. Each preflight reads the other's run record and says no in a sentence (`PreflightShipIOS` refuses while `!UpdateTerminal`, `PreflightUpdate` while `!ShipTerminal`); a shared flock would only make one of them block silently for twenty minutes. `PreflightShipIOS` also refuses off main, exactly as `PreflightUpdate` does, and for one extra reason of its own: the build number is `git rev-list --count HEAD`, and a branch's count can equal one main already uploaded. `jobs.ReadShipStatus` applies the same three staleness rules as update's, but with a 45-minute deadline (`shipMaxRun`) rather than 15: a Release archive plus an upload of tens of megabytes over a bad uplink is legitimately slow. Two things are deliberately unreachable from automation: `--allow-provisioning-updates` (it creates certificates and profiles on the real Apple developer account, so the first run is by hand — `ios/TESTFLIGHT.md`), and the credentials, which come from `ASC_KEY_ID`/`ASC_ISSUER_ID` in the environment or, failing that, `~/.kraken/asc.env` (`jobs.ASCEnviron`, injected into the script's environment) — a file rather than `launchctl setenv` because setenv measurably does not reach a job whose plist declares its own `EnvironmentVariables`, and is lost on reboot besides; they are passed through to the script's environment only, and are never written to the status file, the log, or an event. Preflight resolves `xcodegen` to an absolute path and prepends its directory via `toolchainEnv` for the same launchd-PATH reason the updater does it for `go`. `done` means **uploaded**, not installed: TestFlight still has to process the build before the phone is offered it.

Invariants that shape the code:

- **Verify before acting**: discovery output goes stale, so every destructive/targeted action re-checks the pane still holds the expected agent first (`checkSendTarget`, `verifyKillTarget`, `BranchGuard` in internal/core/actions.go and internal/core/branch.go). Preserve this pattern for new actions.
- `SessionIDGuessed` marks session ids inferred from cwd + newest transcript rather than a session file: fine for display, unsafe as a fork/read target.
- `k b` forks via `claude --fork-session -r <session-id>` in a tmux split, inheriting the source's permission mode from its transcript.
- `k k` refuses to kill the current pane and nested (Depth > 0) agents.

Tests (`cmd/kraken/main_test.go`, `cmd/kraken/viewer_test.go`, root `skills_embed_test.go`, plus a `_test.go` file alongside its source in each of internal/{util,core,jobs,api} and web) cover the pure functions — parsers, ordering, selection, rendering — by constructing `Peer` values directly; nothing shells out, so they run anywhere.

New code goes in the package matching its concern — CLI/rendering in cmd/kraken, tmux/discovery primitives in internal/core, sqlite accessors in internal/store, job/cell lifecycle in internal/jobs, wire handlers in internal/api, HTTP serving in web — and only exports what actually crosses a package boundary. The `util ← store ← core ← jobs ← api ← web` direction is load-bearing: a lower package must never import a higher one, since that would both violate the layering and create an import cycle.

Env knobs beyond the path overrides above: `KRAKEN_SERVE_ADDR` overrides the
localhost base URL a cell's pr-hook/logevent processes POST to
(`jobs.ServeBaseURL`, `jobs/prhook.go`) — defaults to `127.0.0.1:7777`,
overridden for tests or a non-default `kraken serve` port. `KRAKEN_SIGN_ID`
(`Makefile`, install target) picks the codesigning identity `make install`
signs the binary with; unset falls back to the first identity
`security find-identity -v -p codesigning` reports, and no identity at all is
a warning rather than a failed install. `ASC_KEY_ID` and `ASC_ISSUER_ID`
(`internal/jobs/shipios.go`, `ios/ship-testflight.sh`) are the App Store
Connect API credentials `k ship-ios` needs; both must be set or preflight
refuses, they are read from the environment and passed through to the script's
environment only, and their VALUES must never reach `~/.kraken/ship-ios.json`,
`~/.kraken/ship-ios.log`, the event log, or any refusal message — only their
names, and only to say one is missing. The matching private key lives at
`~/.appstoreconnect/private_keys/AuthKey_<key id>.p8`, where `altool` finds it
by convention (so it is never named on a command line either). A ship started
from the board inherits `kraken serve`'s launchd environment, not a login
shell's, so both must be set there too.

## Conventions

- Keep it stdlib-only outside the viewer; new dependencies need a strong reason.
- Data sources owned by other programs (session files, transcripts, codex logs) are read defensively — missing/malformed files degrade to blank fields, never errors.
- **Model policy**: every claude kraken *spawns* — a cell's zeus, `k c`, the board's spawn action — runs on `core.DefaultModel` (`claude-opus-5`), passed explicitly as `--model` via `core.ModelArgs`; kraken never leaves the model to claude's own config, and a job's `model:` field is the only per-spawn override. `k b` is deliberately outside this: a fork continues an existing session rather than starting a new agent. Zeus' crew is the same tier by a separate mechanism: zeus' brief (internal/jobs/crew.go) and the repo-owned skills pin every agent it spawns — hephaestus, athena, hermes, all of them TEAMMATES (Agent-tool calls carrying a `name`, so each gets a real pane; unnamed in-process subagents are reserved for read-only exploration) — to `model: opus`, an Agent-tool tier alias rather than an id, because that tool takes tier names. Net effect: every agent in a cell is Claude Opus 5.
- **API contract**: any change to JSON served to or accepted from the iOS app/web UI (internal/api/*.go, web/serve.go, internal/jobs/daemon.go, internal/jobs/job.go) lands in the same commit as `ios/API.md`, `ios/Kraken/Models.swift`, and `internal/api/contract_test.go`. `apiContract` (internal/api/board.go) bumps only on breaking changes — a key retyped, renamed, or removed — mirrored by `expectedContract` in `APIClient.swift`; additive keys never bump it.
