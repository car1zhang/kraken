# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

kraken (`k`) is a macOS CLI/TUI for managing live Claude Code and Codex sessions across tmux: list them (`k ls`), watch them (`k v`), jump to one (`k o`), message one (`k s`), read its transcript tail (`k r`), fork it (`k b`), kill it (`k k`), spawn new shells/claudes (`k n`/`k c`). Run `k help` for full usage.

## Commands

- `make build` — build the `kraken` binary
- `make install` — build + install to `~/.local/bin` (with `k` symlink) + zsh completion. **Never `cp` over the installed binary directly**: macOS SIGKILLs running processes whose backing binary changes (code-signature invalidation). The Makefile copies to a temp name and `mv`s (atomic rename) for this reason.
- `go test ./...` — run all tests
- `go test -run TestName ./<pkg>` — run a single test (main-package tests: `./cmd/kraken`; skills-embed tests: `.`)
- `go vet ./... && gofmt -l .` — lint

## Architecture

The binary is split into a strict dependency chain of packages, each owning one layer: `cmd/kraken/` (package main: CLI dispatch, `k ls` rendering, the bubbletea viewer, plus the `_k` zsh completion script) + `internal/util/` (stdlib-only helpers) + `internal/store/` (the sqlite layer: `kraken.db` schema + typed accessors) + `internal/core/` (discovery, `Peer`, tmux primitives, claude spawning, transcript reading, usage) + `internal/jobs/` (job files, cells, crew briefs, status derivation, archive, daemon) + `internal/api/` (JSON handlers + wire types, `apiContract`, `api.Register`) + `web/` (embedded SPA in `web/static/`, artifact serving, bind logic, `web.Serve`). The layout rule: `cmd/` and `internal/` are pure Go; `web/` stays top-level because it carries the SPA's static assets, and one Go file stays at repo root — `skills_embed.go`, the module-root `package kraken`, pinned there because `go:embed .claude/skills` can't reach above its package directory (cmd/kraken blank-imports it so its init() wiring runs). The dependency DAG is `util ← store ← core ← jobs ← api ← web`, and `cmd/kraken` imports all of them; importing upward is forbidden (and impossible without an import cycle). The only direct dependency is bubbletea (viewer TUI); all else is stdlib. External state is shelled out to: `tmux`, `ps`, `lsof`, `git`, `osascript`, `python3` (the doc pipeline's fragment linter and card-wrap substitution run via python3 in cells).

The core type is `Peer` (internal/core/peer.go): one live agent process in a tmux pane, an in-process teammate known only from a team config (`Messageable=false`), or an agent-free shell pane (`Role "shell"`).

Data flow, shared by `k ls`, the viewer, and completion:

1. **Discovery** (internal/core/discover.go): `DiscoverAll()` snapshots tmux panes (`tmux list-panes -a`) and the full process table (one `ps` call), then walks each pane's process subtree for claude/codex processes. Agents in a pane are listed deepest-first: index 0 is the foreground agent — the one `tmux send-keys` actually reaches; deeper ones are nested subagents. Enrichment comes from `~/.claude/sessions/<pid>.json` (session files Claude Code maintains), `~/.codex/session_index.jsonl` + lsof for codex, transcript files under `~/.claude/projects/<munged-cwd>/`, and `git`/`lsof` for branch/cwd. lsof is the slow path — results are memoized in package-level caches (`cwdCache`, `codexSessionCache`) because the viewer polls discovery on a tick.
2. **Refinement + nesting** (internal/core/peer.go): `refineStatus` peeks pane content via `tmux capture-pane` to detect blocked/question prompts; `nestTeams` attaches teammates to their leads using `~/.claude/teams/*/config.json`; `OrderAll` produces the single flat numbering that every selector references.
3. **Selection** (internal/core/select.go): `SelectPeer` resolves a user selector — index, `.` (current pane), exact pane id (`%3`), session-uuid prefix (≥4 chars), or substring match — against that ordering.
4. **Action or render**: actions (internal/core/actions.go, internal/core/branch.go) drive tmux (`send-keys`, `kill-pane`, `new-window`) and ghostty focus via AppleScript, called from cmd/kraken's thin cmd wrappers (cmd/kraken/cmd_actions.go, cmd/kraken/cmd_branch.go); the one exception is `k b`'s `tmux split-window`, issued directly from cmd/kraken/cmd_branch.go. Rendering is cmd/kraken/ls.go (tables, grouping modes, colors) and cmd/kraken/viewer.go (bubbletea TUI that re-runs discovery on a tick and reuses ls.go's group/row builders).

Jobs and cells are a separate subsystem layered on top of the above. Two orthogonal extras sit beside the five states: **archived** jobs (internal/jobs/archive.go) are job files moved into `~/Documents/pluto/archive/` — out of the active namespace entirely (slug freed, invisible to the daemon), numbered `foo-2.job.md` on name conflicts, restorable via the board's unarchive action (state preserved; refused while the slug is taken) and hard-deletable only from the archive. **Reactivation** (the board's reactivate action, internal/jobs/cell.go) resurrects a done job into its original zeus session: kraken stamps zeus' session id into the job file (`session:` frontmatter) from the daemon's first tick after the cell comes up, so a done job can later be resumed with `claude -r` in a recreated worktree at the same path; the `carl/<slug>` branch recycles (reset off the base once fully merged), falling back to `carl/<slug>-rN` (`run:` frontmatter) only when leftover unmerged commits would be orphaned. A job (internal/jobs/job.go) is one `<slug>.job.md` file in `~/Documents/pluto`, parsed strictly into a five-state board model — draft · queued · working · blocked · done — that kraken derives, never hand-writes: `internal/jobs/status.go`'s `deriveState` combines the job file's own `state` with the live-ness and a ROLL-CALL of the cell's claudes (`cellActive`: the zeus pane peer's own status, any nested subagents in its session, and non-lead team members cross-checked against live tmux panes — any one alive-and-running votes the cell into working, else it reads blocked) to decide working vs. blocked, and `internal/jobs/status.go`'s `FindPendingQuestion` pulls any still-open `AskUserQuestion` tool call straight out of zeus' transcript for the web board and iOS app to render as answer buttons. A cell (internal/jobs/cell.go) is one job's runtime: a dedicated git worktree plus a single tmux pane running **zeus**, the sole per-job agent — there is no separate relay agent and no escalation-bus file; zeus reports status by simply saying it in its own pane, which the board surfaces as the cell's detail line. Zeus' system prompt (internal/jobs/crew.go) is unified — there is no job-level `type` any more (Q14): every job runs `/aim`, picking spec mode or explain mode itself from what the job spec asks for, then produces the flat artifact set below. What happens next is carl's move, not the job's: when he sends `/do`, phase 2 begins — implement → a manual-test gate (zeus reports "manual test ready" and stops until carl's reply passes it) → `/pr` (opens the PR, reports the URL, and stops — the daemon, not zeus, watches CI and bumps zeus' pane on failing checks or new comments) — delegating slices to hephaestus subagents that zeus itself manages, reviewing each with three parallel single-dimension athena variants — athena-logic, athena-edge, athena-style; a purely explanatory job never gets a `/do` and never opens a PR — carl accepts it by hand instead (board Done). The pipeline renders its diagrams via one-shot, per-figure hermes subagents. The doc phase produces a flat artifact set, never a single combined file: `00-overview.md` + `10`-`49` diagram cards + `50`+ section docs — there is no flatten step; each artifact is complete and shareable the moment it's written. Open questions and carl's per-artifact feedback are rows in `kraken.db` behind `kraken serve`, not files — zeus reads/writes them via cell-side `kraken questions`/`kraken feedback` verbs. All four pipeline skills (`info`, `aim`, `do`, `pr`) are repo-owned, checked into `.claude/skills/`, embedded into the binary by `skills_embed.go` (repo root), and materialized into `<cell worktree>/.claude/skills/` at cell creation (`internal/jobs/skills.go`) so zeus can read them by path (personal skills shadow the names). Cells and PRs are many-to-one: the daemon's PR tracker records every PR shipped from the cell branch into the job's kraken-owned `prs:` frontmatter list (url + state, plus two kraken-owned watermark keys per PR — `last-comment-at`, `bumped-sha` — frontmatter-only, never on the wire; a merge is a notification + board chip, NEVER a teardown trigger — teardown lives only behind carl's explicit accept via board Done, and there is no `k reap`), and zeus recycles `carl/<slug>` off origin/main after each merge for follow-up PRs. The daemon (internal/jobs/daemon.go) queues ready jobs into cells, tracks PRs, watches open PRs of active jobs for new comments or failing CI and bumps zeus' pane when either appears, and flags dead cells, owning nothing it can't reconstruct from job files plus discovery after a restart. Every job interaction — starting, completing, archiving, reactivating — is CLI-free (Q14): `k`'s own surface is tmux/peer management only, and `kraken serve` is the sole runtime — the scheduler tick loop plus the web UI/API in one process (opens `~/.kraken/kraken.db`, the store `kraken import` one-shot-migrates any legacy file stores into) — `make install` installs it unconditionally. At every cell spawn, RotationGate (internal/jobs/rotation.go) may swap the main login to a healthier `~/.claude-pool` account in auto mode, never blocking or failing the spawn (`k account <slug>` pins manual; `k account auto` releases it).

Invariants that shape the code:

- **Verify before acting**: discovery output goes stale, so every destructive/targeted action re-checks the pane still holds the expected agent first (`checkSendTarget`, `verifyKillTarget`, `BranchGuard` in internal/core/actions.go and internal/core/branch.go). Preserve this pattern for new actions.
- `SessionIDGuessed` marks session ids inferred from cwd + newest transcript rather than a session file: fine for display, unsafe as a fork/read target.
- `k b` forks via `claude --fork-session -r <session-id>` in a tmux split, inheriting the source's permission mode from its transcript.
- `k k` refuses to kill the current pane and nested (Depth > 0) agents.

Tests (`cmd/kraken/main_test.go`, `cmd/kraken/viewer_test.go`, root `skills_embed_test.go`, plus a `_test.go` file alongside its source in each of internal/{util,core,jobs,api} and web) cover the pure functions — parsers, ordering, selection, rendering — by constructing `Peer` values directly; nothing shells out, so they run anywhere.

New code goes in the package matching its concern — CLI/rendering in cmd/kraken, tmux/discovery primitives in internal/core, sqlite accessors in internal/store, job/cell lifecycle in internal/jobs, wire handlers in internal/api, HTTP serving in web — and only exports what actually crosses a package boundary. The `util ← store ← core ← jobs ← api ← web` direction is load-bearing: a lower package must never import a higher one, since that would both violate the layering and create an import cycle.

## Filesystem Conventions

Every path in the binary derives from `os.UserHomeDir()` via `util.Home()` — never hardcode `/Users/<name>` (in Go, prompts, or docs), so the same setup works on any Mac whose home directory follows this layout. The directories kraken assumes, and where each is wired in:

| Path | Owner | Code |
|---|---|---|
| `~/Documents/pluto` (job files `*.job.md`, `archive/`) | user's pluto notes convention | `internal/jobs/job.go` (`JobsDir`) |
| `~/Developer` (git checkouts jobs may target) | user convention | `internal/jobs/job.go` (`ResolveRepo`), `internal/jobs/board.go` (`RepoCandidates`) |
| `~/.kraken` (`cells/`, `daemon.json`, `usage.json`, `rotation.json`, `rotation.lock`) | kraken-owned | `internal/jobs/cell.go`, `internal/jobs/daemon.go`, `internal/jobs/usage.go`, `internal/jobs/rotation.go` |
| `~/.kraken/kraken.db` (single SQLite database; env override `KRAKEN_DB_PATH`) | kraken-owned | `internal/store/store.go` (`DBPath`) |
| `~/.kraken/backups` (nightly `VACUUM INTO` backups of kraken.db, newest 7 kept; env override `KRAKEN_BACKUPS_DIR`) | kraken-owned | `cmd/kraken/cmd_serve.go` (`backupsDir`, `runNightlyBackups`) |
| `~/.claude-pool` (`<slug>/` account slots, `cooldowns.json`) | ccp-owned (claude code pool); kraken reads slot creds/identity and writes back rotated tokens after an OAuth refresh; during account rotation it also auto-creates a save-back slot and writes its creds + `account.json` + slot `.claude.json` identity, plus a pool-root `.rotation-inflight` journal (present only while a swap's commit is in flight or stuck) | `internal/core/usagepool.go`, `internal/core/rotation.go` |
| `~/.kraken/uploads` | kraken-owned (per-job image uploads) | `internal/jobs/uploads.go` |
| `~/.kraken/logs` (unified event log, size-rotated JSONL) | kraken-owned | `internal/util/eventlog.go` |
| `<cell worktree>/.claude/settings.json` | kraken-written per-cell hook config (PostToolUse → `kraken pr-hook`), merged not clobbered | `internal/jobs/cell.go` |
| `.claude/skills/` (`info`, `aim`, `do`, `pr` pipeline skills; embedded into the binary via `skills_embed.go` (repo root), materialized into `<cell worktree>/.claude/skills/` at cell creation) | kraken-owned (checked into the repo, embedded at build) | `internal/jobs/skills.go` |
| `~/.claude` (`sessions/`, `projects/`, `teams/`, `.usage-cache.json`) | Claude Code | `internal/core/discover.go`, `internal/core/peer.go`, `internal/core/usage.go` |
| `~/.claude.json` (top-level, sibling of `~/.claude`) | Claude Code-owned; kraken replaces only the `oauthAccount` block during account rotation, paired with the `Claude Code-credentials` keychain entry — the two writes the rotation journal brackets | `internal/core/usagepool.go` (`claudeJSONPath`), `internal/core/rotation.go` |
| `~/.codex/session_index.jsonl` | Codex | `internal/core/discover.go` |
| `~/.config/nvim/lua/config/pluto.lua` | user nvim config (`{{name}}` expansion coupling) | noted in `internal/jobs/job.go` |
| `~/.local/bin` (`kraken` + `k` symlink) | install target | `Makefile` |

When adding a path, express it home-relative through `util.Home()` and add it to this table.

Env knobs beyond the path overrides above: `KRAKEN_SERVE_ADDR` overrides the
localhost base URL a cell's pr-hook/logevent processes POST to
(`jobs.ServeBaseURL`, `jobs/prhook.go`) — defaults to `127.0.0.1:7777`,
overridden for tests or a non-default `kraken serve` port.

## Conventions

- Keep it stdlib-only outside the viewer; new dependencies need a strong reason.
- Data sources owned by other programs (session files, transcripts, codex logs) are read defensively — missing/malformed files degrade to blank fields, never errors.
- **Model policy**: every claude kraken *spawns* — a cell's zeus, `k c`, the board's spawn action — runs on `core.DefaultModel` (`claude-opus-5`), passed explicitly as `--model` via `core.ModelArgs`; kraken never leaves the model to claude's own config, and a job's `model:` field is the only per-spawn override. `k b` is deliberately outside this: a fork continues an existing session rather than starting a new agent. Subagents are the same tier by a separate mechanism: zeus' brief (internal/jobs/crew.go) and the repo-owned skills pin every subagent it spawns — hephaestus, athena, hermes — to `model: opus`, an Agent-tool tier alias rather than an id, because that tool takes tier names. Net effect: every agent in a cell is Claude Opus 5.
- **API contract**: any change to JSON served to or accepted from the iOS app/web UI (internal/api/*.go, web/serve.go, internal/jobs/daemon.go, internal/jobs/job.go) lands in the same commit as `ios/API.md`, `ios/Kraken/Models.swift`, and `internal/api/contract_test.go`. `apiContract` (internal/api/board.go) bumps only on breaking changes — a key retyped, renamed, or removed — mirrored by `expectedContract` in `APIClient.swift`; additive keys never bump it.
