# Aim — Initial Alignment Artifact Set

Create a concrete first artifact set the user can react to: no single flattened doc — a brief overview, standalone diagram cards, and section docs, each openable on its own. Use spec mode for proposed or future systems; use explain mode for existing systems or current behavior. Do enough research to avoid ignorant questions, then write down the current best shape with explicit assumptions, a large set of open questions, and a practical testing or verification plan. The artifact set is an iteration surface, not final architecture.

**Follow-up skill: [[do]] (`/do`)** — once the set is locked, `/do` reads it, resolves any `P0` open questions with the user, and implements it. `/aim` produces the contract; `/do` executes it. When the user is ready to build, point them at `/do` rather than implementing inline.

## Artifact Set Shape

Every set lives in one directory (the **set root**) and is a flat list of files, ordered by numeric name prefix — lexicographic sort is the display order everywhere:

- **`00-overview.md`** — REQUIRED. A brief markdown page (~1 page): the change/system, its approach, its intended goal. The high-level alignment surface — no tables of internals, no diagrams; those live in the cards and section docs below.
- **`10-<id>.html` … `49-<id>.html`** — diagram cards, one per diagram, chosen per-need at your discretion (**≥1 worked-example diagram card required** in spec mode / for build jobs). Each card is a standalone HTML file: the shared diagram CSS + one hermes-rendered SVG + a self-sufficient caption (2-4 sentences: what the figure shows and what to take away, understandable with no other artifact open). UI mockups also live in this band, as their own `1N-<id>.html` card or a single `4N-ui-mockups.html` artifact — built directly by you (never delegated to hermes; see Core Rules).
- **`50-<section>.md` and up** — section docs, at your discretion, mostly for the implementing agent's own use. In spec mode / for build jobs, `50-components.md`, `51-code-map.md`, and `52-testing-plan.md` are REQUIRED; assumptions, constraints, scope, etc. are optional additions in this band. Markdown with tables.

There is no single flattened doc file. Diagram fragments still stage separately (see the delegation rule below) and get mechanically wrapped into cards — you never hand-author or read SVG bodies.

**Where the set lives:**

- In a kraken cell: the set root is `<cellDir>/artifacts/` (a kraken job brief will say so and give you exact paths — its deltas win wherever more specific). Fragments stage in `<cellDir>/doc/fragments/`. Questions are **not a file** — they are rows in `kraken.db`, read and written through the cell-side `kraken questions get/set/add/update/remove` verbs (see Core Rules).
- Standalone/personal use: the set root is `~/designs/<slug>/`. Fragments stage in `~/designs/.fragments/<slug>/` (the legacy fragments convention, kept for standalone use). Questions live in `~/designs/<slug>.questions.yaml` — a sibling of the set root, not inside it.

## Core Rules

- Prefer drafting over interrogating. Ask only blockers before the first draft; otherwise state assumptions and capture uncertainties in the open-questions record.
- **Investigate before asking.** Any question that the codebase, git history, configs, schema, or docs can answer must be researched and answered yourself first — never park a codebase-answerable question in the open-questions record or pose it to the user. Open questions are reserved for genuine user decisions (product intent, priorities, tradeoffs, external constraints) and facts no amount of code-reading can resolve. Before writing any question, ask: "could I answer this with `rg`, by reading a file, checking the schema, or running a query?" If yes, do that instead.
- Research current state before writing codebase-specific specs. Read the relevant `AGENTS.md` files and skim the key implementation files enough to cite real paths and avoid inventing constraints.
- Use progressive disclosure across the set. `00-overview.md` stays very high level (1-3 sentences per subsection — the diagram cards carry the detail); diagram cards each carry exactly one figure's worth of detail; section docs go lowest-level (components, code map, review guide).
- **Two core diagrams, then tunnel.** Most sets need exactly two core diagrams. (1) **Architecture, highest level**: what the components are, what talks to what, and where the boundaries sit. Every box carries a **kind** tag: the concrete runtime/artifact identity, taken from the sanctioned kind list in the Shape Kit section of `.claude/skills/aim/assets/hermes-contract.md` — that section's kind → shape table is the source of truth, and a box's kind determines its silhouette. Never a vague noun like "service" or "layer" unless that's literally what it is; a component you cannot honestly name a kind for falls back to the plain `node` rounded rect with its kind text line intact. Every boundary container is labeled with its boundary type (machine, process, network, package, file-ownership). `50-components.md` (below) carries this same Kind/Boundary requirement into its per-component table. Spec mode ships this as **one combined card**: a current-state panel and a target-state panel stacked in a single figure, sharing one layout so the delta pops (greenfield systems with no current state draw the target panel only — never an empty panel); explain mode ships current state only. This card must be complete at its own altitude — a reader should be able to locate any deeper card inside one of its boxes. (2) **End-to-end flows**: every flow a user/agent/datum can take through the feature, entry to exit, traced with **one concrete worked example** (real names, ids, field values; data drawn in its natural shape; step badges; animated per the animation rules below) — the worked-example and data-in-natural-shape requirements described further down live in this card, not a separate mandated one. Beyond these two: **tunnel cards** that zoom into one architecture box whose internals the reader can't infer and genuinely needs (each names the parent box it expands), plus any other card you judge important for a clear mental model — this is a default, not a hard cap. UI mockups keep their own rules and band (below). Only skip a diagram when it would genuinely show nothing. Also use tables, screenshots, and reference pictures where they reduce ambiguity.
- **Containment: shape inside shape, then `group`, then tunnel.** When one component lives inside another, the parent's own silhouette is the boundary — a component may nest inside another component's silhouette whenever the Shape Kit gives that silhouette a **content well** (a database holding its tables); several rect-looking silhouettes are deliberately leaf-only, so check the kit rather than eyeballing the shape. No dashed container needed. A dashed `group` is for boundaries that are **not** components: ownership, a repo, a network, a machine you are not drawing as a box. Anything past the Shape Kit's **component-nesting depth limit** becomes its own tunnel card instead — deeper than that the innermost box stops being labelable — with the kit's two carve-outs: data `cell`s are exempt (`ui > table > cell` is one component holding one component holding data), and dashed `group`/`region`/`lane` wrappers are boundaries rather than components, so they don't consume a level. Which silhouettes have wells, where their children may sit, and the exact depth limit all live in the Shape Kit section of `.claude/skills/aim/assets/hermes-contract.md`; the brief names the containment, hermes draws it.
- **Animate flow diagrams.** Any diagram that depicts movement — sequence/swimlane flows, request lifecycles, data movement, pipelines, state transitions, rollout timelines — should be animated by default: SMIL `<animateMotion>` dots traveling along edge paths, `stroke-dashoffset` "marching ants" on active edges, staged opacity/pulse highlighting the currently-active node. Purely structural diagrams (data models, code maps, component boundary maps) stay static. Animations must be subtle, looping, and self-contained (SMIL/CSS only — no JS), and every SMIL animation must BEGIN at its resting, fully-visible state (the host card pauses SMIL at t≈0 under reduced motion, so an element that ramps up from `opacity 0` would be permanently invisible to a reduced-motion reader — content loss, not motion suppression). Reduced-motion handling is the HOST CARD's job, never the fragment's: the only in-fragment mechanisms (`<style>`, `style=`) are contract-banned, so hermes must not attempt `prefers-reduced-motion` at all — two hermes per round were spending reasoning proving the old instruction unsatisfiable — and `diagram-card.html` carries the pause.
- **Show worked examples, not just structure.** A system diagram tells the reader what the parts are; an exemplary diagram tells them what actually happens. This is the content of the **end-to-end flow card** from "Two core diagrams, then tunnel" above — not an additional card: one concrete, named instance — a real user flow from start to finish, a sample record/request with actual field values — traced through the system stage by stage, with numbered step badges and the instance's data shown visibly changing between stages. And whenever the set deals in structured data (API responses, matrices, 2D arrays, schedules, grids, regions), add a card showing what an **example of that data means**, rendered in its natural shape — a 2D array as an actual grid of cells with headers, a slot schedule as a day/time strip, a spatial payload as a drawn region — never as raw JSON prose. Keep one consistent example (same user/org/record/values) across all exemplary diagram cards in a set so the reader follows a single story. These are ordinary diagrams pipeline-wise — delegated to the diagram teammates — but the brief must spell out the exact example values to draw (the teammate can't invent realistic data).
- **Mock up every UI change.** When the set proposes or touches UI, include a mockup of each affected screen/component state — inline HTML/CSS blocks styled to resemble the real UI (preferred), annotated screenshots of the current UI, or a picture; SVG only when it genuinely fits. Mockups live in the diagram-card band (`1N-<id>.html` or `4N-ui-mockups.html`) but are built by **you directly** — the Opus design-teammate delegation below applies to SVG diagrams only, never to UI mockups. Show before/after when the change modifies an existing screen. Keep mockups self-contained (inline CSS, no external assets).
- **All diagrams are inline SVG — never Mermaid, never ASCII art.** Follow the SVG conventions cataloged in `.claude/skills/aim/assets/hermes-contract.md` (mirrored in the legacy templates' header comments): `viewBox="0 0 860 H"` with no width/height attributes; a rich shared parts kit styled by the card's stylesheet so every diagram looks consistent — component boxes in a silhouette per kind, with the sparkle as the model-powered mark, plus boundaries, lanes, pills, decision diamonds, actors, grid cells, step/count badges, bars, axes, regions, titles, notes, edges, flow dots (`hermes-contract.md` is the catalog of record; its Parts Index is designed for the teammate to scan and pick from, and its classes must land on the exact elements it prescribes — a box class on a bare `<rect>` instead of its `<g>` wrapper renders unstyled); a card-unique arrow marker id per SVG (e.g. `arrow-target-shape` — marker ids only need to be unique within their own card now, since each diagram is its own standalone file); long labels wrapped with `<tspan>`; ≥12px padding inside boxes. **Every diagram opens with a required in-SVG `.title`** — top-left, stating the figure's takeaway in plain words (never a generic label); `lint_svg.py` fails fragments without one. Diagram teammate briefs **name the path `.claude/skills/aim/assets/hermes-contract.md` and require hermes to Read that file before it writes any markup** — they never paste its contents (paths in this skill are relative to the worktree root — your cwd in a cell — not this skill's own base directory; the parts-kit style contract). The reference beats the paste for three reasons: a thousand-line contract re-typed through a model's context is not verbatim — observed copies silently reworded rules and dropped a clause, so two hermes in one round obeyed two different rulebooks while the file on disk said something else again; the file is already materialized in every cell worktree, i.e. in the teammate's own cwd, so pointing at it costs nothing and is the only copy that can't drift; and the paste re-spends your context per diagram and again per fix round, with up to 6 hermes in flight. Kraken holds itself to exactly this one level up — zeus' own brief is forbidden from restating a skill and is staged as a file rather than inlined, after an inlined pipeline blew past tmux's command ceiling. Hermes composes from that catalog, it never invents markup or color.
- **Colour states what is going on with the thing, never how to feel about it.** A treatment is a factual claim about the element it lands on — which means it can be WRONG, and only you know whether it is true, so the brief must assign the treatment AND name its glyph: hermes applies what you assign, invents neither, and cannot check whether the claim holds. Six treatments:
  - `grey` `∅` — missing · absent · removed (renders dotted; the one treatment that survives greyscale)
  - `red` `✗` — critically wrong: confirmed AND critical
  - `yellow` `⚠` — warning · likely wrong · less critically wrong
  - `green` `✓` — fixed · passing · working
  - `blue` `+` — new · added
  - `purple` `★` — emphasis · unorthodox (reach for it least often)
  - `dim` — out of this figure's story; no glyph

  Two decisive rules: **red vs yellow** — red needs confirmed AND critical, and hesitation itself means unconfirmed, so yellow; **blue vs green** — provenance vs state: new in this change → blue, existed and now works → green (new AND working is blue). **Most boxes carry no treatment at all** — a treated element is the exception. The full table, the three bans, the two exemptions, and the decision procedure live in `.claude/skills/aim/assets/hermes-contract.md` § Colour Semantics; read that before assigning, and LOOK at `.claude/skills/aim/assets/palette-reference.html` whenever a call is not obvious.
- **Diagram ids are unique across the WHOLE set, not just within a card — and must be legal agent names.** A diagram's id names its fragment file (`<fragments-dir>/<id>.svg`), its card file (`<set-root>/10-<id>.html` and siblings), and the teammate that renders it (`hermes-<id>`) — two diagrams sharing an id means two parallel hermes teammates collide on a name and silently overwrite each other's fragment (and later, card). Because the id rides inside an agent name, keep it lowercase `[a-z0-9-]` and **≤ 40 characters**: the Agent tool validates `name` against `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, so a dot, a space, or an over-long id is rejected at spawn time, mid-fan-out, while the fragment and card paths it also names would have been perfectly legal. This is a stronger rule than the arrow-marker-id relaxation above, which only relaxes uniqueness for arrow/path-id prefixes *inside* a single SVG's own markup — diagram ids themselves still need to be unique set-wide.
- **How to wait for an agent's output is specified ONCE, and not here — read it before the fan-out below.** `.claude/skills/do/SKILL.md` step 4, the "How to wait" bullet and every sub-bullet under it: the deferred tools to fetch in one `ToolSearch`, one conjunctive background until-loop over every report path, `-s` not `-f`, end the turn, and — the two a reader stops before if they stop early — what an expiry means and how to tell a slow agent from a dead one. It is the same protocol whichever phase you are in, and every clause in it was paid for by a run that did it the other way. Do not re-derive it: a lead that improvised the wait for three hermes spent **24.3 of that turn's 24.6 minutes** hand-polling `ls`, having fetched `Monitor` and then never called it. This skill fans out further than `/do` does — up to 6 hermes plus research subagents — so it needs the protocol more, not less. One thing to carry across with it: **every path in the wait condition, and every path the delete-before-re-brief rule applies to, is a scratch REPORT path** — never a fragment or any other artifact a teammate will be asked to revise. (Outside a cell that file may not exist. The protocol in one line: fetch `Monitor` and `SendMessage` in one `ToolSearch`, arm ONE background until-loop over every report path using `-s` not `-f`, end the turn, and treat an expiry as "one of them is missing" rather than as a reason to re-arm.)
- **Delegate SVG diagrams to Opus TEAMMATES — design AND render.** You never write or read diagram bodies; no SVG tokens should pass through your context in either direction. For each diagram, spawn a teammate — an Agent-tool call that passes a **`name`** (`hermes-<diagram-id>`, unique set-wide because diagram ids are) along with `model: opus` (Claude Opus 5, the tier alias the Agent tool takes; never sonnet or haiku). Naming it is what makes it a teammate rather than an anonymous in-process subagent: it gets its own pane, and it stays addressable by that name so a later round can resume it with its fragment's context intact. It designs the layout and writes the **complete `<svg>…</svg>` fragment to its own file** under the set's fragments dir (see Artifact Set Shape above), named `<diagram-id>.svg`. The division of labor is fixed: **you decide WHAT to illustrate** (the diagram's purpose, the exact entities/flows/labels, the concrete example values, what to emphasize vs. de-emphasize), **the teammate decides HOW** (layout, which catalog parts to use, animation) — never dictate coordinates, markup, or a shape class in a brief, and never let a teammate invent content. Every box in an assignment is a `box → kind` pair; hermes derives the shape mechanically from the kind via the contract's kind → shape table. A component you cannot honestly name a listed kind for still states its honest kind in text — hermes picks the fallback silhouette for it. Give each teammate: the diagram's purpose, the exact entities/flows/labels to show, the SVG + animation conventions above, the worktree-relative **path** to `hermes-contract.md` with an instruction to Read it in full before writing markup and to compose only from it (never its contents pasted inline — see the rule above) — and the brief must add: if a Read returns a PARTIAL banner, keep issuing offset Reads until end of file before writing any markup. That condition fires today — the contract outgrew a single Read window, and the dropped tail is the load-bearing half (the colour decision procedure, the Ids section, the spacing rules) — so a hermes that stops at the banner composes without them while believing it read the contract (measured: three renderers in one round each rediscovered the same recovery call; "read it in full" with no banner clause was unsatisfiable in one call and nobody said so), a card-unique arrow-marker id and path-id prefix to use (assigned by you, since teammates can't see each other's output — e.g. `arrow-target-shape`, path ids prefixed `ts-`), the exact fragment output path — plus the instruction that **if that file already exists, Read it before writing** (the Write tool refuses to overwrite a file not read this session, every fix-round and respawn brief says "overwrite what is there", and the report format leaves hermes no slot to mention the refusal, so it recovers silently or bypasses the guard with heredocs) — **its own scratch report path** (`/tmp/<slug>-hermes-<diagram-id>-r<N>.md` — this is what you wait on, not the fragment), and **the exact lint command with its flags already filled in** (see the done-test bullet below — the flags are documented in this skill, which hermes never reads, so a command it has to reconstruct is one it runs without them). Every FIRST-AUTHORSHIP hermes brief also carries the incremental-write instruction: **`Write` the fragment's opening section as soon as its layout is decided, then `Edit` the rest in, panel by panel — never compose the whole SVG in your head first.** The brief states it as a REASONING-BUDGET rule, not just an output shape: decide the layout in a short thinking pass and settle everything else inside the edit loop, because a hermes that satisfies the Write/Edit letter after designing the whole figure in one huge pre-Write thinking block has spent the ceiling-death budget without the death (measured: three compliant renderers burned half their cell's entire output in pre-Write thinking, the loudest-briefed one producing the LEAST incremental markup — one Write plus one Edit carrying a whole panel). (First authorship only: a fix-round or respawn brief says Read-then-`Edit`, never a fresh `Write` — an opening-section `Write` on an existing fragment TRUNCATES the one surviving copy of a figure that was already right, and a ceiling death mid-rebuild would leave a stub with no error record anywhere.) A combined two-panel architecture figure — the largest markup this pipeline ever asks for — has died at the 64,000-token output ceiling three consecutive times composing in extended thinking before its first `Write`: 192K tokens and 41 minutes for zero bytes, and an output-ceiling death leaves NO error record anywhere, so the round just reads as one slow teammate. The recovery that finally worked was exactly this instruction, discovered at full price. **One hermes across states**: whenever current and target state are both drawn — the Rule-2 combined architecture card above, or exceptionally separate before/after figures — assign the SAME teammate both states in a single assignment (one brief, both fragments), so styles and component placement match 1:1; never split current and target across two different teammates. That teammate is named for the FIRST of its two fragment ids, and every later round for either fragment addresses that one name — it is the single case where a diagram id does not name a teammate of its own. Batch a draft's diagram teammates into one message so they run in parallel — one fragment file per teammate avoids same-file edit races — but no more than 6 at once: each is a real tmux pane and a full Opus process now, not a free in-process subagent, and a cell that fans out a dozen buries its own pane in `k v`. Render the rest in a second wave. **Hermes** runs `python3 .claude/skills/aim/assets/lint_svg.py <fragment> --marker-id arrow-<id> --prefix <prefix>` after writing its fragment (paths relative to the worktree root — its cwd in a cell) and pastes the linter's output back verbatim in its report; you lint once yourself only AFTER that report arrives, to confirm — never while it is still working (see the done-test bullet below for why). If that confirming run reports anything, `SendMessage` the line-numbered violations as a fix-round brief to **that same `hermes-<diagram-id>`** — it still holds its fragment's context, so never spawn a fresh agent for a fix round (max 2 fix rounds, then debug the fragment source directly yourself). A hermes is therefore NOT done when it reports its fragment written — it is done when EVERY fragment it owns lints clean (or carries an accepted warning, per the done-test bullet); stop it (TaskStop, by its bare name) only then, which for a two-fragment hermes means not until both are settled. Only settled fragments get wrapped into cards — lint-clean, or carrying an accepted warning per the done-test bullet below.
- **One done-test for a fragment, and hermes is what runs it.** `lint_svg.py` exits 0 while printing WARNINGS, so "if it exits non-zero, SendMessage the violations" and "it is done when that fragment lints clean" were two tests that disagreed on exactly the warning case — and that gap cost a full teammate round trip twice, on the same figure, in one night. The first part below is what makes the rest checkable.
    - **Hermes writes a REPORT FILE, and that file — never the fragment — is what you wait on.** `/tmp/<slug>-hermes-<diagram-id>-r<N>.md`, assigned in the brief, written in ONE shot as the last thing it does, for EACH fragment it owns (a hermes drawing current and target owns two, and needs two lint runs and two report sections). This is the one thing that makes the wait protocol below applicable to a diagram round at all: hermes' deliverable is an artifact, not a report, and a fragment is non-empty from its first line of markup — which is precisely the state the old rule called NOT done. A lead that waits on `<id>.svg` wakes before the lint has run and lints into the teammate's fix, which is the 55 ms race below. It is also why the wait protocol's *delete the path before you re-brief* rule attaches to this report path and **never to the fragment**: a fix round tells that same hermes to Read and rewrite its own fragment, so deleting it hands the teammate a missing input and throws away a figure that was already right.
    - **The report holds the command line AND the linter's complete output, verbatim — plus anything that fought back.** A ceiling death, a refused `Write`, a retry, a workaround: the run's cost gets a line even when the artifact came out clean, because "lint clean on the first run" has been reported, truthfully, by a teammate that had died three times and burned 30% of its cell's entire output getting there — the report format had no slot for it, so nobody ever knew. Not a paraphrase and not a verdict: the argv and the bytes. `--marker-id` and `--prefix` are opt-in checks for the two ids you assigned, so a run without them silently skips the only checks specific to that fragment and still prints the same word `clean` — which is why the quoted output alone cannot tell a flagged run from an unflagged one, and the argv has to be there too. Put the exact command, flags filled in, in the brief; the flags are documented in this skill, which hermes never reads.
    - **The done-test is the shape of that output**, which has exactly two: `<fragment>: clean`, printed only when failures and warnings are both zero, or the numbered findings printed instead of it. So `: clean` under a command line carrying both flags IS the pass condition; findings are a fix round owed; neither means the linter was not run, whatever the prose says.
    - **`clean` is the linter's whole opinion, not the contract's.** The linter does not check the contract's 24px-gap minimum or label/box overlap — a fragment with an 8px gap and a label crossing two boxes has linted clean — so the brief tells hermes those two are ITS checks, by eye against the contract, after the lint. And tell hermes to read `lint_svg.py`'s check list before composing: renderers keep rediscovering that tactic independently, and in one round the two who did shipped clean on the first pass while the one who did not owed a second geometry pass.
    - **You do not lint concurrently with it.** Both observed round trips were the lead linting while hermes was already fixing, and losing: one fix-round message went out **55 ms** after hermes' own report, re-quoting warnings that were already gone, and its instruction would have damaged a clean file. Read the report, then lint once yourself to confirm — a fix round is only owed against output you read after it reported.
    - **A warning may be ACCEPTED, and after one fix round it usually should be.** Several warn-tier rules are estimators rather than violations — `TEXT_OVERFLOW` and `SHAPE_TEXT_FIT` are width *estimates* against a silhouette, `GEOM_UNPARSEABLE` is the linter saying it could not read a coordinate, the `HOLDS_*`/`NEST_WELL` family infers containment through wrappers — and the contract says as much of its own colour checks: "a smoke detector in one room, not a rule". The shipped lint fixtures are themselves expected to warn. So a warning that survives one fix round, on a figure you have reason to believe is right, is accepted: say so in the card's caption or the build report, naming the rule and line and why, and wrap the card. Without this the zero-warnings bar plus "only lint-clean fragments get wrapped" makes a false positive an unshippable figure, and the run's only symptom is a card that never appears.
- **Wrap, don't flatten.** Each settled fragment (lint-clean, or carrying an accepted warning per the done-test bullet) becomes its own standalone diagram card at `<set-root>/10-<id>.html`, taking the next free number in `10-49`, assigned by you sequentially (needing more than the band means over-decomposition — merge; never use 3-digit prefixes): copy `.claude/skills/aim/assets/diagram-card.html` and mechanically substitute all three placeholders with a python one-liner using `str.replace` (never `re.sub` — a fragment containing `\1` or `\g` crashes `re.sub`'s replacement parsing), substituting in one pass — never let an earlier replacement's value introduce a later token. HTML-escape `&`, `<`, `>` in the title and caption — they land in markup; NEVER escape the fragment (it is markup). Fill the `{{CARD_TITLE}}` token (occurs twice: the `<title>` and the `<h1>`) and the `{{CAPTION}}` token (occurs once, in the `<figcaption>`) first, then substitute the literal `<!-- DIAGRAM: {{DIAGRAM_ID}} -->` placeholder comment with the fragment file's raw contents. **Title and caption ride in `sys.argv`, never inlined into the `-c` string**: a caption is natural English, apostrophes are the norm, and one apostrophe inside a quoted `-c` program is a `SyntaxError` — leads keep rediscovering this and falling back to a script file at the cost of a Write and a re-run. The working form: `python3 -c "import pathlib, html, sys; t = pathlib.Path('.claude/skills/aim/assets/diagram-card.html').read_text(); t = t.replace('{{CARD_TITLE}}', html.escape(sys.argv[1])).replace('{{CAPTION}}', html.escape(sys.argv[2])).replace('<!-- DIAGRAM: {{DIAGRAM_ID}} -->', pathlib.Path(sys.argv[3]).read_text()); pathlib.Path(sys.argv[4]).write_text(t)" "<title>" "<caption>" <fragment-path> <out-path>` — the title and caption double-quoted (escape any `"` or `$` inside them; a longer program still goes to a `.py` file run by path). All three replacements are global — never hand-edited. Verify the output contains `<svg` and does NOT contain `{{CARD_TITLE}}`, `{{CAPTION}}`, or `<!-- DIAGRAM:` — if either check fails, the wrap failed; do not ship the card. There is no derived build file and no flatten step: each card is complete and shareable the moment it's wrapped. To **edit** an existing diagram, `SendMessage` its `hermes-<diagram-id>` teammate to Read and rewrite its own fragment file, re-lint, then re-run the wrap substitution on that one card — no extraction needed.
- **`solo: true` on a kraken job means no teammates and no subagents at all.** Skip the diagram pipeline entirely — no hermes teammates, no `10-<id>.html` diagram cards — and write prose-only section docs plus `00-overview.md` by hand. The worked-example diagram card requirement above does not apply when there are no diagram cards to begin with.
- Prefer tables over lists for structured sections such as components, assumptions, scope, testing plans, review guides, checklists, and questions. Use lists only for short prose-like bullets or when ordering is the point.
- **Never hard-wrap prose in an artifact.** One paragraph — and one bullet, and one table row — is ONE source line, however long; wrapping is the renderer's job, never the author's. A mid-sentence line break renders as a broken paragraph on the board, and it is a repeat complaint from carl ("please get rid of them and remember not to do"). This binds every markdown artifact the set ships, and every teammate brief that asks for one.
- **Questions: rows in `kraken.db` inside a cell, `questions.yaml` standalone — never in any artifact.** In a kraken cell, questions are **not a file** — they are rows, managed through cell-side CLI verbs that proxy HTTP to `kraken serve` (the same channel the pr-hook already uses): `kraken questions get <slug>` (full list — **re-read on every resume**, since answers arrive as silent row updates, the same contract as the old silent file edits), `kraken questions set <slug>` (bulk upsert-by-qid of the zeus-owned fields from a JSON list on stdin; deletes rows not present; preserves kraken-owned `answer`/`answered-at` on surviving rows), and `kraken questions add|update|remove <slug> ...` for per-question ops — where `add` and `update` take ONE JSON question object on stdin (piped, same as `set`; there are no `--field`/`--value` flags, and a flag form invented from the verb name is a usage error) and `remove` takes `<slug> <qid>` as arguments. All writes validate loudly — a bad qid shape or importance is a 400 on stderr with a non-zero exit, never a silently-dropped line. On any verb failure (validation error, connection refused because serve is down), surface the stderr and retry after fixing the input; never proceed as if the write landed and never silently drop questions. Outside a cell (standalone use), the file convention stands: a sibling `~/designs/<slug>.questions.yaml` (see Artifact Set Shape), format:
  ```yaml
  questions:
    # one item per question; single-line values; importance P0|P1|P2
    - id: Q1
      text: include model name in title?
      context: affects k ls width
      importance: P0
      recommendation: yes, abbreviated
  ```
  track answers in the conversation and update the file yourself in this mode.

  Both modes share the same fields and ids: `id` (`Q<digits>`, e.g. `Q1`), `text`, `context`, `importance` (`P0`|`P1`|`P2`), `recommendation`, plus `answer`/`answered-at` which **kraken owns exclusively** — you must never write or set those yourself. **Every question gets a stable, globally-numbered id** (`Q1`, `Q2`, …) — do not restart numbering per topic. Whenever you pose open questions to the user in chat (in the draft summary, during iteration, or via AskUserQuestion), reference them by these ids (e.g. "Q3: …") so answers map unambiguously back to the record. Keep ids stable across iterations: a resolved question's entry is removed (its id is not reused), new questions take the next unused id. Every entry must be a genuine user decision or a fact the codebase cannot answer — if you have not yet tried to answer it from the code, you are not ready to list it. Questions answered during research become Current State, Assumptions, or resolved decisions in the relevant artifact, not open-question entries.
- Keep spec and design separate. Spec defines what, why, scope, constraints, architecture shape, data concepts, and unresolved decisions. Exact APIs, algorithms, migrations, and file-by-file implementation plans belong in a dedicated design pass instead — an `/architect` or `/design` personal skill if one exists in this session, otherwise a design doc or section written by hand.
- When the user asks for a decoupled/composable system, describe capabilities, contracts, ownership boundaries, and composition principles without locking low-level implementation details.
- Leave many open questions. Prefer too many precise questions over a falsely complete set.
- Include testing early. Every component should have a brief unit/integration/e2e testing plan when applicable, and `52-testing-plan.md` should carry an overall testing plan. **Write both for the test AUTHOR, not for the implementer** — in `/do` these are the brief input for the agents that write the tests blind, and those agents never see the implementation, so a plan phrased as "check the new helper handles this" is unusable while one phrased as an obligation of the component ("a half estimate is refused; neither number is stored") is exactly what they need. State what must be true, never how the code will end up arranged.
- After writing or editing the set, share the **`00-overview.md`** path plus the set root so the user can open any card or section doc directly — never run `open` (or otherwise launch a browser) yourself. Sets are purely local files — no cloud/Artifact publishing.

## Workflow

### 1. Frame The Request

Restate intent in 2-4 bullets:

- what outcome the user wants
- what system or workflow is affected
- what constraints are already known
- what is explicitly out of scope or deferred, if known

### 2. Research Enough Context

For repo work:

- Read the relevant root/module `AGENTS.md`.
- **`git fetch` origin's default branch first, and diff your base against it, before writing any cross-component claim.** A set written against a stale base states the retired architecture as current — one spec stated a transport as the current route while origin/main had already replaced it with a native screen, and the miss surfaced four hours later as an unplanned 800-line slice. A cell branch is routinely several PRs behind by the time `/aim` runs.
- Use `rg` to find the active entrypoints, types, and existing docs.
- Inspect enough files to understand current behavior, existing abstractions, and naming.
- Cite important local files in the artifacts where useful.

Before drafting, do a question-resolution pass: jot down every uncertainty the set will need to resolve, then split them. For each, decide whether it is **codebase-answerable** (a path, an existing behavior, a type, a config value, a schema column, an env flag, how a current flow works, whether something already exists) or a **genuine user decision** (intent, scope, priority, tradeoff, external constraint). Investigate and answer all codebase-answerable ones now — with `rg`, file reads, schema/config lookups, git history, or a quick query — and fold the findings into the draft (as current-state prose, assumptions backed by evidence, or resolved decisions). Only genuine user decisions survive into the open-questions record. When unsure which bucket a question is in, spend a search to find out before defaulting to asking.

For broad or multi-area investigations, fan out parallel researcher subagents to resolve the codebase-answerable questions concurrently rather than serially. Two rules, and both apply to any researcher you expect a FILE back from — a one-fact lookup answered in a sentence needs neither. **Name each one's output file in its brief**, one exact scratch path outside the repo, with the chat reply a short summary plus that path: a findings document that exists only as a chat reply is one that arrives truncated or not at all. **And spawn it with an agent type that can actually write one** — `general-purpose`, or any type whose roster includes `Write`, and never `Explore`. `Explore`'s roster excludes `Write` and `Edit`, so a brief saying "write your findings to `<path>`" is unsatisfiable by construction — and an agent in that position does not report the problem, it rationalises ("enforced read-only mode", "my configuration prohibits creating files") while the lead waits on a file that is never coming. Read-only means the REPO, not the filesystem, so tell it *write nothing under the repo*, and add the line *if you have no `Write` tool, write the file with a Bash heredoc (`cat > <path> <<'EOF'`)*. The same contract, stated at more length and with the failures that produced it, is in `.claude/skills/do/SKILL.md` step 4.

Stop research when the first draft can be written responsibly and no codebase-answerable question remains unresolved. Deep tracing belongs in research/design unless the set would otherwise be misleading.

### 3. Choose Mode And Set Up The Set Root

Choose one mode before writing:

- **Spec mode**: use when the artifacts propose a new system, feature, refactor, migration, or future behavior.
- **Explain mode**: use when the artifacts describe an existing/current system, current code behavior, an incident-relevant workflow, or how to review/debug something that already exists.

**If the set root already holds artifacts from an earlier phase of the same job — most commonly an `/info` overview that this `/aim` run is following — move them aside before writing yours.** Both skills claim `00-overview.md`, the set root sits under no VCS, and the overwrite is unrecoverable except by reconstruction from context; two cells lost their `/info` deliverable exactly this way in one night. Rename the existing file to a free numbered slot (e.g. `60-info-overview.md`), note the move in your overview, and only then write.

Create the set root (see Artifact Set Shape for the exact path in a cell vs. standalone) and write artifacts directly into it — there is no HTML template to copy and fill in for `00-overview.md` or the section docs; write them as plain markdown following the structure in Draft The Artifacts below. Diagram cards DO start from a template: copy `.claude/skills/aim/assets/diagram-card.html` (paths relative to the worktree root — your cwd in a cell) per diagram, per the wrap rule in Core Rules.

Use a descriptive slug for the set root based on the feature/system, not a vague name like `doc`.

> **Legacy fallback.** `.claude/skills/aim/assets/spec-template.html` and `explain-template.html` — the old single-file, fill-in-the-blanks templates — still exist on disk for personal, non-cell, single-file use if you explicitly want one flattened doc instead of a set. They are not the primary flow; do not reach for them unless asked.

If the user explicitly wants the established repo design template, read/copy from `designs/TEMPLATE.design.md` or `designs/TEMPLATE.design.html`, but write the resulting artifacts under the set root above.

If a personal `/feature` skill exists in this session and invoked this one, use spec mode and that feature flow's expected structure.

### 4. Draft The Artifacts

Write `00-overview.md` first (very concise — 1-3 sentences per subsection): the change/system, goal, current state, target shape / approach, and a one-line pointer to the diagram cards and section docs that carry the detail. Both modes share the same underlying progression; explain mode replaces proposed goals with current-system explanation and verification guidance:

1. **`00-overview.md`**: goal, current state, target shape / approach, data model / core concepts — each 1-3 sentences, diagrams referenced but not embedded.
2. **Diagram cards (`1N`-`4N`)**: the two core diagrams per "Two core diagrams, then tunnel" (Core Rules) — one combined current/target architecture card (spec mode; current-state only in explain mode), every box kind-tagged, and one end-to-end worked-example flow card — plus tunnel cards into any architecture box whose internals genuinely need expanding, and UI mockups when the change touches UI.
3. **Section docs (`5N` and up)**: `50-components.md` (one fill-in table per component, **Kind** row first — the concrete runtime/artifact identity per the kind vocabulary in "Two core diagrams, then tunnel" (Core Rules) — then responsibility, inputs, outputs, side effects, **boundary** naming its boundary type (machine, process, network, package, file-ownership), unit/integration/e2e test plans — required for spec mode/build jobs), `51-code-map.md` (where things live, review guide, known touch points — required), `52-testing-plan.md` (overall unit/integration/e2e/manual/observability testing plan — required); optionally `53-assumptions.md`, `54-scope.md`, `55-constraints.md`, or similar at your discretion.
4. **Open questions**: every open question, per the format in Core Rules (`kraken.db` rows in a cell, `questions.yaml` standalone).

Draft prose and tables first, noting each diagram's id and intended content as you go (never embedded into `00-overview.md` — the overview has no figure slots), then fan out the Opus `hermes-<diagram-id>` teammates for all of them in parallel (each designs and renders its full SVG to its own fragment file — see the delegation rule in Core Rules), then wrap each into its numbered card. Build any UI mockup cards yourself while the diagram teammates run — mockups are never delegated.

For componentized systems, make `50-components.md` emphasize:

- **Kind** stated first for every component — the concrete runtime/artifact identity, named with a kind from the sanctioned kind list in the Shape Kit section of `.claude/skills/aim/assets/hermes-contract.md` (the same vocabulary the diagrams use, and the kind that determines the component's silhouette there)
- independently callable stages
- typed inputs/outputs or conceptual contracts
- side-effect boundaries, with the **boundary type** named (machine, process, network, package, file-ownership)
- idempotency/retry expectations
- observability hooks
- how components can be composed or skipped
- where shared code can be reused without coupling the whole pipeline
- per-component test coverage at unit, integration, and e2e levels

For codebase specs, always include a `51-code-map.md` with:

- active runtime entrypoints
- existing adapters/helpers to reuse
- files that contain source-of-truth types
- files to review first
- tests or fixtures that explain expected behavior
- likely diff surfaces, clearly marked as tentative when the set is not locked

### 5. Assemble And Share

There is no derived build file — each artifact is complete and self-contained the moment it's written or wrapped. After a round of edits:

- Wrap any newly settled fragments into their numbered cards (Core Rules) — lint-clean, or carrying an accepted warning.
- Share the set: `00-overview.md`'s path plus the set root, so the user can open any card or section doc directly. Do not open anything yourself — the user opens files from the shared paths.

### 6. Iterate

After writing the first draft in either mode:

- Share the `00-overview.md` path and the set root again.
- Summarize the most important assumptions and the highest-risk open questions, citing each by its stable id (e.g. "Q1: …", "Q4: …").
- When asking the user to resolve questions (in chat or via AskUserQuestion), always lead with the id so their answers map back to the record.
- Wait for user edits or direction before moving into architecture/design.
- On each iteration, update the relevant artifact directly (overview, a section doc, or a card via its fragment + rewrap), and update the open-questions record to remove resolved entries and add new ones — in a cell, via `kraken questions set/add/update/remove` (never write `answer`/`answered-at` yourself); standalone, edit `questions.yaml` directly.

### 7. Hand Off To /do

Once the set is locked (P0 open questions resolved or explicitly deferred, structure stable, user signals readiness to build), point the user at [[do]] (`/do`) as the implementation step. `/do` reads the set, walks the user through any remaining `P0` questions, and writes the code. Do not implement inline from this skill — the set is the contract, `/do` is the executor.

## Inside A Kraken Cell

When a kraken job brief sends you here, these deltas apply — the brief wins wherever it is more specific, and it is the only place the cell's real paths appear:

- **The set root is the brief's SET ROOT** (`<cellDir>/artifacts/`) and fragments stage in the brief's fragments dir (`<cellDir>/doc/fragments/`). That artifacts dir is the only board-visible directory: an artifact written anywhere else does not exist as far as carl is concerned.
- **A sibling job's artifacts survive its cell's teardown as flat copies in `~/Documents/pluto/`** (archived jobs: `~/Documents/pluto/archive/`), each file prefixed `<slug>-<id>.` — so when the job spec points at another job's artifacts and that job's `~/.kraken/cells/<...>/artifacts/` dir is gone, look there BEFORE re-deriving anything. A 248-line recipe written explicitly for one cell's job, carrying warnings about that job's exact entity, sat preserved there the whole time a 152K-token subagent reconstructed it from commits — the preserved location appears nowhere in a cell's own paths, so this line is the only way a cell learns it exists.
- **The section-doc floor is mode-scoped.** In spec mode `50-components.md`, `51-code-map.md`, and `52-testing-plan.md` are REQUIRED, plus the end-to-end flows diagram card that carries the worked example. In explain mode they are as-needed instead (components/code-map when useful), with no testing-plan requirement, and the diagram cards are encouraged, not required.
- **Questions are rows, and they are a SPEC-path tool only.** Use the `kraken questions` verbs in Core Rules. An `/info` explanation job never creates any — its list stays empty — and no job of any shape spams carl with questions it could have answered by reading the code. Bake open questions in with recommended defaults; never block waiting on an answer.
- **The phase ends with one line, then you stop.** When the set is ready, say exactly:

  `doc ready for review: <set root>/00-overview.md (+N diagrams, M sections, K questions)`

  followed by the open P0s in the same line, and STOP (end the turn). Use `0` where a count is zero — never omit the clause. Kraken derives blocked from your silence and shows your last words on the board.
- **`/do` is carl's move, not yours.** Phase 2 begins only when he sends `/do` in your pane. Never declare the job done — accepting or merging is his call.
- Never run `open` (there is no browser in a cell); the board renders the artifacts.
- `solo: true` on the job means no teammates and no subagents at all — see the solo rule in Core Rules.

## Mode Guidance

### Spec Mode

Use spec mode for systems that do not exist yet, changes to existing systems, migrations, refactors, product behavior proposals, and implementation alignment sets. Section docs should cover goals, non-goals, success metrics, assumptions, testing plan, and questions.

### Explain Mode

Use explain mode for systems that already exist or behavior the user wants to understand. Focus on what exists, why it exists, how data flows, how components interact, where code lives, how to debug/review it, what tests or traces verify it, and what remains uncertain. Do not propose changes unless the user asks; put possible follow-ups in the open-questions record or a notes section doc.

Explain mode here is the **full artifact set** for an existing system — reach for it when the user explicitly wants that. For an ordinary "how does X work?", `/info` is the lighter path: the same depth of research, but one brief overview first and deeper artifacts only where the reader asks, with no open-questions record at all (questions are /aim's, never /info's).

## Spec / Design Boundary

Spec territory:

- user-visible behavior
- lifecycle/stage behavior at a conceptual level
- high-level architecture and conceptual data models
- component responsibilities and composition boundaries
- code map and review guide for orientation
- acceptance criteria
- constraints and tradeoffs
- success metrics
- open questions
- assumptions
- test strategy

Design territory:

- database schema
- exact API signatures
- class/function names
- detailed control flow
- migration SQL
- file-by-file task breakdown

If the spec starts needing exact interfaces, mark them as open questions or move to a dedicated design pass (a personal `/architect` skill if one exists in this session, otherwise a hand-written design doc).
