# Do — Implement An Artifact Set

Take the artifact set produced by [[aim]] earlier in this conversation — `00-overview.md`, its diagram cards, and its section docs — and implement it. The set is the source of truth for scope, components, constraints, and testing. Before writing code, resolve any `P0` entries in the set's open-questions record with the user; after the code is verified, write `90-build-report.md` — the brief record of what shipped and where reality diverged from the plan.

## Preconditions

- An `/aim` artifact set must exist for this conversation: a set root directory (standalone: `~/designs/<slug>/`; in a kraken cell: `<cellDir>/artifacts/`) containing `00-overview.md`. The open-questions record is optional and lives outside the set: standalone, a sibling `~/designs/<slug>.questions.yaml`; in a cell, rows in `kraken.db` read with `kraken questions get <slug>`. A missing file or an empty list just means no open questions were raised (an `/info` explanation job never has any by design). Older conversations may instead have a single flattened `~/designs/<slug>.spec.html` / `.explain.html` from the legacy template flow (or `.spec.md` / `.explain.md`) — treat that file itself as the doc in that case.
- If no such artifact exists in this conversation:
  - Do **not** start implementing.
  - Tell the user: "No /aim artifact found in this conversation — run /aim first, then /do."
  - Stop. Do not infer a spec from prior chat messages alone; the artifact set is the contract.

## Workflow

### 1. Locate And Read The Set

- Identify the most recent `/aim` set root mentioned in this conversation (or the explicit path the user passes as an argument).
- Read `00-overview.md` in full, then every `.md` file in the set root other than `00-overview.md` in full (covers `5N-*.md` and any `6N+` section docs), then the open-questions record in full (standalone: `questions.yaml` if it exists; in a cell: `kraken questions get <slug>`). The set is the source of truth — do not rely on chat memory of what it said. (Diagram cards are supporting detail; skim captions/titles rather than reading every SVG body.)
- If working from a legacy single-file doc instead, read it in full the same way.
- The open-questions record is OPTIONAL: a missing `questions.yaml` (or an empty `kraken questions get`) means zero open questions for this set — skip straight to implementation (do not refuse or treat it as an error).
- If any section doc this workflow names (`50-components.md`, `51-code-map.md`, `52-testing-plan.md`) — or one referenced elsewhere in the set (e.g. by `51-code-map.md`'s review guide) — is absent, say so explicitly and fall back to `00-overview.md` plus whatever section docs do exist — never invent content to fill the gap. A solo set legitimately has none of the three named docs; that is not an error.

### 2. Resolve P0 Open Questions

- Collect every open-questions entry with `importance: P0` and no answer yet.
- For each unresolved P0, ask the user with `AskUserQuestion`. Group related questions into one call (up to 4 questions per call).
- An entry that already has an answer (and `answered-at`) is a **decision, not a question** — never re-ask it; treat the answer as settled and cite it if relevant. In a kraken cell those two fields arrive as silent row updates from carl answering on the board, never as pane messages — re-run `kraken questions get <slug>` before this step to pick up anything answered since the set was last read.
- If there are no unresolved P0 entries, skip straight to implementation.
- Do **not** ask P1/P2 questions unless the user requests it — state assumptions for those if they block progress, and surface them after implementation.

### 3. Record Newly Resolved Decisions

- After P0 answers come in outside a cell (where there's no board to append `answer`/`answered-at` for you), edit `questions.yaml` yourself: remove the resolved entry and note the decision in the relevant section doc (an `Assumptions`/`Decisions` note) instead. Leave P1/P2 entries untouched.
- In a kraken cell, never write `answer`/`answered-at` yourself — that's kraken's job once carl answers from the board.

### 4. Plan The Implementation

- Build a TaskCreate plan grouped by `50-components.md`'s component table. One task per component is a good default — that is the planning unit, not automatically a delegation unit (see the fan-out rule below).
- Honor the set's scope/non-goals/constraints section doc(s) strictly — do not expand scope.
- Use `51-code-map.md` (where things live, review guide) as the file-targeting guide. Verify those paths still exist before relying on them.

**The next six bullets apply only when you DELEGATE.** Work you keep for yourself — including every `solo: true` job, where there is no crew at all — skips to step 5, where the un-delegated path has its own instruction. There is no point freezing a contract against yourself.

- **Freeze the contract BEFORE you dispatch anyone — `50-contract.md` in the set root.** Whoever implements a slice must not also be the one who decides what that slice was supposed to do, so the requirement is written down first, by you, and both sides are held to that same text. One table per slice: **symbol · signature · obligations · owner**, where obligations are the behavioural claims the slice must satisfy, one short line each ("bumps NEITHER `rev` NOR `updated_at`", "both numbers or neither — a half estimate is refused"). It is symbol-level rather than conceptual — name `tokenGroup.commit` as readily as `core.SumTokensDelta` — but the symbol must be one the test file can actually reach, and that differs by language. Go and Python tests reach unexported names in their own package, and Swift reaches `internal` through `@testable import` (this repo sets `ENABLE_TESTABILITY` and every file in `ios/KrakenTests/` uses it), so none of the three needs help; its real limit is `private`/`fileprivate`, which `@testable` does NOT reach. **TypeScript is the one with no escape hatch at all** — an unexported symbol is unreachable from any other file, test included — so there the export is part of the frozen signature and must be written into it. The test of a good contract is one question — **could someone write a compiling test from this alone, with no access to the implementation?** If not, it is not frozen yet. Write it even when Phase 1 never ran and the job spec is one paragraph; that is the case that needs it most. You own amendments; a teammate never edits it. **On a repeat `/do` for the same slug** — a follow-up PR off the recycled branch — earlier rounds' blind tests are still in the repo and still asserting, so the new contract must re-state every obligation they pin, or those tests fail against a contract that no longer claims what they test. Re-cover them, or delete the ones the change deliberately obsoletes; leaving them to fail teaches everyone to ignore a red suite.
- **Dispatch the implementer and the test authors in ONE message.** The implementer gets the contract, its file targets, and **no test list** — it implements and never writes a test for the spec (a regression pin for a defect it fixes is fine: the implementer tests bugs, the authors test requirements). In the same message, **one** logic author and **one** edge author for the whole fan-out, however many slices there are — they get the contract, `50-components.md`'s per-component test plans, `52-testing-plan.md` when the doc phase produced one, and an explicit instruction not to read the implementation files. **Concurrency is the mechanism, not a courtesy**: when they start there is nothing to look at, so blindness is a property of the schedule rather than a promise nobody can audit. Split by dimension — logic authors the stated invariants and happy paths, edge authors boundaries, error paths, and refusals. They **author but do not run**: tests written against code that does not exist yet fail for uninteresting reasons, so they report the file written and wait.
- **Give each author its own test file, and its own identifiers inside it.** File ownership stops an edit race, which is all it stops — two blind authors in one Go package share a declaration space, so both writing `func mkCase(...)` fails the whole package's test binary and takes every unrelated test in it down too. So: prefix every package-level identifier a test file declares with its dimension (`contractMkCase`, `edgeMkCase`). Names, by language, because a blind author cannot check what the runner collects and a file that is silently never collected reports as a pass:

    | | test author's file |
    |---|---|
    | Go | `<subject>_contract_test.go` · `<subject>_edge_test.go` |
    | Python | `test_<subject>_contract.py` · `test_<subject>_edge.py` — and put it where that repo's runner already looks (`testpaths`/`python_files` in `pytest.ini` or `pyproject.toml`, or the paths CI passes), NOT beside the module: the filename matches everywhere, the LOCATION is what decides collection |
    | TypeScript | `<subject>.contract.test.ts` · `<subject>.edge.test.ts` — vitest collects only `*.{test,spec}.*`, so an underscore name is never run |
    | Swift | `<Subject>ContractTests.swift` · `<Subject>EdgeTests.swift` — and regenerate the xcodeproj before the join, or the file sits outside the target |

    If the file already exists from an earlier round, **append — never replace it**. Earlier rounds' blind tests are regression coverage, and reading a test file is not reading the implementation.
- **Signal the run only when EVERY implementation slice is done.** One barrier for the whole fan-out, not per slice: a slice's tests routinely touch a symbol another slice owns, so a per-slice run reports failures that are just the other half of the work missing, and the noise trains everyone to ignore the signal. When the last slice reports, `SendMessage` both authors to run their suite and report results. If a slice never reports, the barrier never fires — treat it exactly as the expiry case above: find out whether that teammate died, then re-brief it or proceed without it and say which.
- **Then arbitrate every failure, against the contract text — and do this BEFORE any review round.** The order is not stylistic: reviewing means reading the implementation, and an author that has read it cannot un-read it, so every author must finish arbitrating its own tests while still blind. Three verdicts. **Arbitrate one ASSERTION at a time, not one test at a time** — a single test routinely asserts several things at once ("a half pair is refused, nothing is stored, and the response is 400"), and a test whose assertions land on different rows has no verdict as a whole. Take the assertion that actually failed; if more than one did, or if one assertion bundles a stated obligation with an unstated extra, split them and run each through the table on its own. Then start from what the contract SAYS about that assertion — the observability check below is scoped to what that answer turns up, not asked ahead of it:

    | Does the contract… | Verdict | Action |
    |---|---|---|
    | state the obligation the test asserts — including a signature the code drifted from | **code bug** | Fix brief to the implementer |
    | state the opposite, or place that obligation explicitly elsewhere | **test bug** | Fix brief to the authoring agent, quoting the contract line: drop the assertion or move it |
    | say nothing about it, and the answer is not a product decision — the author asserted a requirement nobody set | **test bug** | Fix brief citing the silence. The author may answer once by deriving the assertion from an obligation that IS stated; if it does, that re-classifies as a **code bug** and goes to the implementer. Otherwise the assertion is dropped |
    | say nothing about it, and the answer is a genuine product decision | **contract defect** | File a question row with your stated default, amend `50-contract.md` to that default, re-brief both sides, and keep going — do not wait on the answer |

    **Then one further check, and only on row 1** — where the test asserts exactly what the contract states, so the assertion is right and something else must be wrong: **can that STATED obligation be observed from the symbols the contract names?** If not, or if the test cannot compile against a contract the code did honour, it is a **contract defect**: amend `50-contract.md` to name a symbol that exposes it, re-brief both sides, and re-run. The scoping is the whole of it, in both directions. Ask observability about the *contract's* obligation and it catches a real gap in the frozen surface; ask it about the *test's* assertion and it swallows rows 3 and 4, because an assertion nobody ever specified need not be observable from symbols chosen without it in mind — and the verdict it would hand you is `contract defect`, which writes the author's invention into the contract as a requirement. Keeping it off row 2 matters for the same reason in reverse: there the assertion contradicts the contract and is wrong whether or not anything can observe it, so letting an unobservable obligation re-classify it would leave a wrong assertion red with nobody owning it. If a row-2 contract also turns out to name no reader for its obligation, that is a contract improvement worth making — after the test bug is fixed, not instead of it.

    Every branch ends in an action that makes the suite green or the assertion gone; a verdict that leaves a red test with no owner is not one of them. The row-3 appeal is the corrective for the one judgment here that is genuinely hard — "is the contract silent on this, or does it follow from something it does say?" — and it is what keeps a wrong reading from silently deleting real coverage. Silence otherwise splits by whether anyone could have decided it in advance, and routing it to `contract defect` by reflex writes an invented requirement into the contract, which is the author defining the requirement just as surely as reading the code would be.

    Two compile failures are neither: a **name collision or a missing import** in the test file is a mechanical fix by the owning author, and code that **deviates from a frozen signature** is a `code bug` — read that row first, because a compile failure routed to `contract defect` by default would have you amend the contract to match whatever the implementation happened to do, which is the implementation defining the requirement and is exactly what this arrangement exists to prevent.

    A **fix brief cites the contract obligation, never the failing assertion** — cite the test and the test becomes the requirement. A fix brief to the implementer never authorises a change to a test file: while the authors are still blind, only the authoring agent edits its own file, and only on a `test bug` verdict (after they are sighted, see the paragraph below). On a `test bug` that author may contest once, but only by quoting a contract line; an appeal that argues without citing the contract is not one. And **never resolve a contract defect by sending an author to read the implementation** — that is the single move that destroys the property, and a blind test that will not compile is the design working (the contract was ambiguous and said so in minutes) rather than failing. Re-run the suite after every fix, and cap it: two rounds per failure, then work the contract text directly yourself. **The blind suite stays live for the rest of the job**, not just for this phase — a review-round fix, or any later change, can turn a green blind test red, and when it does it re-enters this same table rather than being edited to fit. Arbitration is one-shot only in the sense that the AUTHORS stop being blind after it; the tests do not stop being the requirement. One thing changes once they are sighted: a `test bug` verdict after that point is **yours to apply** — you drop or correct the assertion yourself, citing the contract. Not because you are less sighted than the author (you wrote the contract and ran the review, so you are more so), but because you are the contract's author and the arbiter of every other verdict: handing the pen to the agent whose own assertion is in question is what the split exists to prevent, and it is no better late than it would have been early.
- **A round where every blind test passes first time has failed, and it looks exactly like success.** It means the contract was written from code that already existed, or the tests were written loose, or someone peeked. Say so in `90-build-report.md` rather than banking it.
- Fan components out to teammates — `Agent` calls that each pass a `name`, so each gets its own pane and stays addressable by name — when the work genuinely runs in parallel: components that touch disjoint files and don't depend on each other's output. A change that is one coherent edit, however many files it spans, is faster done directly than briefed out; file count is not the test, independence is. Unnamed in-process subagents are for read-only exploration only — never for an agent that writes a file **into the repo** or judges another agent's output. "Read-only" is about the repo, not the filesystem: a researcher still writes its own report to a scratch path, per the output-file rule below.
- **Every brief names the agent's output file, before that agent starts.** Give each teammate — an implementation slice and each of the three single-dimension review variants alike — one exact scratch path outside the repo (`/tmp/<slug>-<agent-name>.md` is a fine default; never a path inside the worktree, since a report is not part of the change), and tell it plainly: the full findings go in that file, and the chat reply is a one-line pointer to it. This is not bookkeeping. The teammate→lead reply channel truncates a long message and is not reliably readable by the lead at all — reviews have arrived empty, been scraped back out of the reviewers' own panes with `tmux capture-pane`, and forced a mid-flight "write it to a file instead" correction that made three reviewers re-serialise a review they had already finished. The **review** briefs need this most: three variants report at once and a findings list is the longest thing any of them writes, and a contract improvised per spawn is one that ends up in five briefs out of six — the sixth being the one that costs a round trip.
- **A brief may only assert what you checked this session — same rule as a code comment, and it is broken most often in briefs.** Step 5 already forbids a comment that claims something you did not verify; the same sentence in a BRIEF is worse, because the agent has no way to check it and every reason to trust it. Two shapes to watch. A number lifted from a counter or a tool schema is a HYPOTHESIS, so write it as one ("the digest reports X; verify before building on it") — leads have handed teammates measured-sounding figures that were off by 20x and premises for events that never happened, and the teammate then spends its first calls disproving its own assignment. And an anomaly goes over as a QUESTION, not a claim: "say what that shape means" gets you the real cause, "confirm that X" gets you X. This bites hardest in a fix-round brief, whose justification text is often written straight into the repo — a false fact there ships unless a reviewer happens to measure it.
- **Then wait on that file existing, not on a guessed duration.** The output file appearing is the real completion condition — wait for it, then read it; do not treat the chat reply as the report. Never sleep a guessed number of seconds hoping the work is in by then: a guess is either dead time or a read of a report that isn't written yet, and blind waits have outlived the session that started them.
- **How to wait: ONE background until-loop over every report path — then end your turn.** A hand-rolled poll burns a turn per check, and a blind `sleep` is refused: a standalone long sleep, or one that OPENS a compound command, comes back `Blocked: standalone sleep 25 …`. (Put anything in front of it and it runs — that is a gap in the check, not permission. The rule stands on the argument above it: a guess is either dead time or a premature read.) The refusal names both affordances — `Monitor` with an until-loop, and `Bash` with `run_in_background: true` — and a sleep INSIDE the loop is the sanctioned form, not the banned one.
    - **Fetch the tools first, in one call.** `Monitor`, `SendMessage` and `TaskStop` are all DEFERRED, absent from the default roster — which is the whole reason leads fall back to `ls`-in-a-loop and to sleeps the harness then refuses: an agent that never goes looking does not know they exist. `ToolSearch("select:Monitor,SendMessage,TaskStop")` at the top of the fan-out, before you need any of them. `SendMessage` is how a fix round reaches the same teammate; `TaskStop` is Clean Up Agents below. `TaskList` is deliberately NOT in that list — it answers neither question this step or that one asks of it, and the reasons are below and in Clean Up Agents.
    - **Wait for the whole fan-out in one watch, not one per agent.** `until [ -s a ] && [ -s b ] && [ -s c ]; do sleep 15; done; echo READY` — three review variants report at once, and three separate watches wake you on the FIRST arrival, which reads as the round being complete when two thirds of it is missing. One conjunctive watch gives one wake, and its expiry means "at least one is missing", which is the diagnostic you actually want. That reason bounds the rule: wait for the whole set when you need the whole set before you can act, which is always true of a review round. If the slices are independent and you would act on each arrival, wake per arrival — but `echo READY <path>` so an arrival is never mistaken for the round. Use `-s`, not `-f`: `-f` is true at byte zero, and the heredoc fallback in the read-only-researcher bullet below creates the file before it fills it.
    - **Pick either affordance; write the call out.** Both work — `Bash` with `run_in_background: true` is the harness's own recommendation for a single notification, and `Monitor` gives you an event stream you can widen. `description`, `timeout_ms` and `persistent` are all REQUIRED alongside `command`, and the `timeout_ms` default is only 5 minutes — shorter than most review rounds — so never leave it unset: `Monitor({command: 'until [ -s a ] && [ -s b ]; do sleep 15; done; echo READY', description: 'athena r1 reports', timeout_ms: 1800000, persistent: false})`. Never `persistent: true`: it ignores `timeout_ms`, and the expiry is the signal.
    - **Then end the turn.** Neither affordance blocks — both return immediately and wake you when the loop exits — so do not read the report in the turn you armed the watch; there is nothing there yet. The loop's condition must be the REAL one, the report paths themselves; a loop on a sentinel that cannot exist (`until [ -f /tmp/never-exists ]`) is the blocked sleep again wearing the shape of the fix, and it burns the whole timeout while telling you nothing.
    - **Treat expiry as news, and check the PANE.** An agent can die having written nothing — an output ceiling hit mid-answer is one observed way — so "the file has not appeared" has two meanings, and a watch that only re-arms cannot tell them apart; a lead that keeps re-arming waits until something else kills it. On expiry, `ls` the paths to see which are missing, then look at those agents' panes with `k ls`: it maps each pane to the agent's NAME and status, which is the whole question, and a teammate IS a pane — its absence is the only positive evidence of death. (Order matters: a finished teammate's pane is gone too, so it is missing report PLUS missing pane that means died. Raw `tmux list-panes -a` is a weak fallback for when `k` is unavailable — a teammate's pane title is its agent TYPE, not its name, so three athenas are three identical rows: it can tell you how many are alive, never which.) `TaskList` cannot answer this — it lists the `TaskCreate` plan board, whose status is self-reported, so an agent that died mid-answer leaves a task reading `in_progress` forever. Then either re-brief them or proceed without them and say which.
    - **Waiting quietly is safe — but that cover is the TEAMMATE's, not the wait's.** Inside a cell the working/blocked roll-call counts the teammate's own live pane, not just yours (`cellActive`, internal/jobs/status.go), so while a teammate is actually running the board reads the job as working however silent you are — and when the teammate dies the cell falls to blocked and the daemon flags it, so going quiet is the safer failure too. A spin loop to look busy is pure spend. But a watch armed on a long build or test run with NO teammate alive has nothing to vote for it: the cell reads blocked and the daemon pings carl for a job that is fine, so for those say what you are waiting for in the pane before you go quiet.
- **Three rules make that condition honest. The first is yours; the other two belong in the brief you just wrote. Never wait on a path that could already exist**: the agent names are constants and the fix protocol is to re-brief the SAME `athena-<variant>` that flagged, so a reused path is already there from the previous round — wait on it and the lead reads a review written before the fix landed, then re-reports a finding that is already resolved. Suffixing the round (`/tmp/<slug>-<agent-name>-r2.md`) handles that within one run, but round numbers restart, and a repeated `/do` on one slug (a follow-up PR off the recycled branch) reuses the same slug and the same names — so the rule that actually holds is: **delete the path immediately before you spawn or re-brief**, and only then start waiting. That is one command and it is correct in every case, including the ones a naming scheme misses. **The report is written in ONE shot, as the last thing the agent does** — a file built up by a Write and then two Edits satisfies "exists" at its first byte, which hands the lead a half-written review: exactly the truncated-report failure this whole contract exists to prevent. **And every agent writes its file even when it has nothing to say** — "no blocking findings" is a result, and it is the most common one; if a clean round wrote nothing, a clean round and a dead agent would be the same observation, and the lead would wait on a file that is never coming.
- **A read-only researcher is forbidden the REPO, not the filesystem — and you have to give it a way to write.** An unnamed in-process subagent spawned to explore rather than to change anything is briefed "write nothing under the repo" — never "do not write any files", which reads as a ban on its own report and has stranded a several-hundred-line findings document in a chat message. It gets the same scratch output path every other agent gets. But the wording is only half of it, and the other half is the half that keeps failing: **spawn it with an agent type that actually has `Write`.** `Explore` does not have one — its roster is every tool EXCEPT `Write`/`Edit` — so a brief that says "write your full report to `<path>`" is unsatisfiable by construction, and the agent does not report that as a problem: it rationalises. Observed refusals, each invented independently, all from briefs that used exactly the phrasing above — *"this session runs in enforced read-only mode"*, *"per my read-only constraint"*, *"my configuration prohibits creating files"*, *"no write tools available"*. The lead then waits on a file that is never coming, and 30-40KB of findings arrive as chat instead, or not at all. So: use `general-purpose` (or any type whose roster includes `Write`) for a researcher you expect a report from, and add one line to the brief — *if you have no `Write` tool, write the file with a Bash heredoc (`cat > <path> <<'EOF'`); "read-only" bars the repo, not your own report.* A researcher with no way to write is a named teammate's job instead.
- **Every teammate runs on Opus** (`model: opus` — Claude Opus 5): the mechanical component tasks the set already pins down as much as the judgment-heavy ones (ambiguous integration points, cross-cutting refactors, design gaps the set left open). Never drop a teammate to sonnet or haiku to save tokens, and never leave the model unset. The lead agent is on Opus too — it plans, reviews teammate output, and integrates.

### 5. Implement

- **Where the per-component test plans go depends on whether you delegated.** When you did, `50-components.md`'s unit/integration/e2e plans are the **test authors'** brief input rather than the implementer's checklist — they went into the test authors' briefs in step 4, and what the implementer is held to is `50-contract.md`. **When you implement a slice yourself — including every `solo: true` job — you write its tests from those plans, exactly as before**, because there is no author to write them and an un-delegated slice must not ship untested. On a repeat `/do` for a slug that delegated last time, earlier rounds' blind tests are still in the repo and still asserting — a follow-up is usually small enough to keep for yourself, which is exactly when this is easy to miss — so re-cover what they pin or delete the ones the change deliberately obsoletes, never leave them failing — "deliberately" is the word doing the work, since without it this reads as permission to delete any test your change happens to break; note in the build report that authorship was not split for it, since you were both parties and the separation the split buys is simply absent.
- Match the project's existing conventions; do not introduce new abstractions the set did not call for.
- Mark each TaskCreate task complete as soon as it is done.
- **A comment may assert a fact about anything outside itself only if you checked it in this session.** Not "it is probably true", not "it reads like the sort of thing that would be true" — you ran the `grep`, the `git show`, the test, in the same turn you wrote the sentence. This is the single most expensive habit the review round catches, and it is a habit of the *comment*, not the code: in one job 25 of ~32 blocking findings across six review rounds were comments asserting something false, usually written minutes earlier, while the code they described was fine. The lead's own summary: *"nearly every finding across six rounds has been a comment asserting something false … The code has been fine."* Actual examples, each caught in review: a claim that tmux is "a sheet action here" on iOS, where the app has no tmux action at all; a stated fact about how `ViewThatFits` picks a branch, given as the justification for hand-writing a `Layout`, which was backwards; three claims in one CSS comment about which rules a class carries, true of a sibling class and not that one. **Two things make this specific rather than a plea for care.** First, the repo's house voice is the cause: comments here explain WHY, including what a thing replaced and what broke before, and an agent imitating that voice with no access to the history will *generate* the history — the style is load-bearing and stays, so the evidence rule is what has to carry the weight. Second, a fix in the same round can *make* a neighbouring comment false, so re-read the comments around every line you change, not just the ones you wrote. If you cannot check a claim, describe what the code does and stop there; a comment that explains less is free, and one that explains wrongly is read as precedent.
- **Never write an incident history for something that never happened.** A defect caught in review, in an uncommitted tree, has no incident. One job wrote *"shipped for 69 archived jobs"* into a test comment for a bug that was caught pre-commit; the next maintainer would have read it as a post-mortem of a real outage and cited it. Say what the guard prevents, not a story about the time it didn't.

### 6. Verify Against The Set

- Run `52-testing-plan.md`'s checks that are practical locally (unit tests, type checks, targeted integration tests).
- For UI changes, drive the feature in a browser before reporting done — and drive it: click, type, navigate every surface the change touches, and say which interactions you performed. A page that renders is not a feature that works, and "I loaded it" satisfies the letter of this step while establishing nothing.
- **Browser mechanics, so you do not rediscover them.** Drive only the surfaces your change touches, and never a destructive one against live state — the kraken dev board proxies to the real `kraken serve` and the real `kraken.db`, so Done, Archive, Stop, Reactivate and Update act on other people's live jobs; exercise those against a job you made for the test, or read-only (open the confirm, do not confirm), and say under Verification what you could not drive safely. Browser work is the LEAD's step and singular: the MCP server drives one browser with one profile, so two agents doing it at once interleave on the same tab and read as flaky UI. Use the `playwright` tools, not `claude-in-chrome` — that one drives carl's own Chrome through an extension whose per-site permission nobody is present to grant — and load them in one `ToolSearch` call. (`/aim` and `/info` say "there is no browser in a cell"; that is about `open` launching carl's desktop browser with nobody watching, not about this one.) Two refusals are worth knowing before you hit them, because the workaround for each is a line. **`file:` URLs are blocked** — `browser_navigate` refuses the scheme outright, so serve the directory instead: `python3 -u -m http.server 0 --bind 127.0.0.1 --directory <dir>` under `run_in_background: true`, and READ BACK the port it prints (`Serving HTTP on 127.0.0.1 port 54321`) — a fixed port that is already taken dies with `Address already in use`, which backgrounded is invisible, and you then verify whatever another cell is serving. The `-u` is load-bearing rather than decoration: without it CPython block-buffers stdout when it is not a TTY, so with an ephemeral port the one line that tells you the port never reaches the log at all. **A screenshot may only be written inside the worktree** — the allowed roots are the worktree and its `.playwright-mcp/`, so `/tmp`, your scratchpad and `<cellDir>/artifacts/` (a sibling of the worktree, not under it) are all refused. Omit `filename` and the shot lands in `.playwright-mcp/` on its own; the tool result names the path it wrote, so copy from that rather than assuming it. `.playwright-mcp/` is gitignored in kraken but not in most repos a cell targets — copy out what carl should see, then `git check-ignore -q .playwright-mcp/ || rm -rf .playwright-mcp/` before the PR step — `check-ignore` exits 1 when the path is NOT ignored, so that one line is the whole guard and is a no-op in the repos that do ignore it. Do not add it to the target repo's `.gitignore` (that is a change to the repo, not to your change), and never write `.git/info/exclude` — in a worktree that resolves to the shared common dir and edits carl's main checkout.
- If a check is not runnable locally, say so explicitly.

### 7. Write The Build Report

Always write **one brief artifact** recording what actually happened: `90-build-report.md` in the
set root (in a kraken cell: `<cellDir>/artifacts/90-build-report.md`). The `90` band sorts it last,
after the overview, the cards, and the section docs. Write it even when the implementation went
exactly to plan, and even when there was no `/aim` set to begin with (a job spec implemented
directly is still a plan reality can diverge from).

Keep it to a page. It is a record of the *delta between plan and reality*, not a second copy of the
set — link to `00-overview.md` rather than restating it. Sections, in order:

| Section | Content |
|---|---|
| What shipped | One row/bullet per component or slice, each naming the files it landed in. Terse. |
| The join | How many blind tests were authored, how many failed on the first run, and the verdict for each (code bug / test bug / contract defect). Zero failures is a finding, not a clean bill — say so. When nothing was delegated, one line saying so is the content; never drop the row. |
| Discrepancies vs. the plan | **The point of this artifact.** Every place reality diverged from the set (or the job spec): what the plan said, what you did instead, and why. Wrong assumption in the spec, an API that doesn't work as described, a component that turned out unnecessary, a boundary drawn in the wrong place — all of it. If nothing diverged, write "None" as an explicit line; never omit the section. |
| Complications | What fought back and how it was resolved or worked around — flaky/blocked tests, missing fixtures, ordering constraints, an unrelated bug hit on the way. Include ones you resolved; they are the cheap warning for the next person. |
| Deferred | Scope deliberately left out, each with the reason and what it would take. Includes P1/P2 questions that stayed open. |
| Verification | What was actually run and its result, plus anything that could not be run locally. |

Uncomfortable findings belong here in plain words: a spec section that turned out wrong, a
decision that made the implementation awkward, an estimate that was off. A build report that reads
like the plan was perfect is a report that isn't worth writing.

### 8. Report Back

- One short summary in chat: what shipped, which P0 answers shaped it, what verification was run,
  and the headline discrepancy if there was one.
- Link `90-build-report.md` and `00-overview.md` — do not re-summarize either in chat.

### 9. Clean Up Agents

Stop each agent as soon as its output is ACCEPTED — an implementation slice once the join has produced no `code bug` against it **and** the review round has cleared it, not the moment it reports done, since a blocking finding has to go back to that same teammate. Both gates come after the barrier, which fires only when the LAST slice reports; a slice stopped before then leaves nothing to send an early `code bug` back to. By the time verification passes and the report is written, tear down anything still resident:

- **Teammates (named `Agent` spawns)**: stop each still-running teammate with `TaskStop`, addressing it by its bare name (or `name@team` if the name is ambiguous across teams). That releases its tmux pane. There is no team-delete step — a team with no live members is already gone.
- **Unnamed background subagents / tasks (Agent, Workflow)**: stop any that are no longer needed with `TaskStop`, addressing them by task id — the id from the spawn result, or from the task notification one fires when it stops. **`TaskList` cannot see a background agent**, and this is measured rather than argued — called with thirteen unnamed scouts live, it answered `No tasks found`. It lists the `TaskCreate` plan board, which is a different thing that happens to share the word (the same reason step 4 says it cannot tell a dead agent from a slow one). Nor are the stop notifications a reliable inventory on their own: an agent that dies mid-answer may never fire one, and an unnamed subagent has no pane, so the `k ls` fallback step 4 leans on does not apply to it either. So **write the ids down as you spawn** — in your scratch dir, not only in context, which a compaction or a resumed session will not preserve. Nothing anywhere will re-derive them for you.
- Do this even when implementation failed or was cut short — a partial run must not leave orphaned agents behind.
- Exception: if a teammate is mid-way through work the user explicitly asked to keep running (e.g. a long verification job), say so in the report instead of killing it.

## Inside A Kraken Cell

When a kraken job brief sends you here, these deltas apply — the brief wins wherever it is more specific, and it is the only place the cell's real paths appear:

- **There may be no artifact set at all.** Skipping the doc phase is a kraken job's default: when Phase 1 never ran, the JOB SPEC is the contract and it is what you implement, exactly as written. The Preconditions refusal above applies to standalone `/do`, not here — a cell with no set root is the normal case, not an error.
- **The crew is the brief's crew, and the crew are TEAMMATES.** Implementation slices go to teammates named hephaestus — which write no tests for the spec — with athena-logic and athena-edge authoring those tests blind from `50-contract.md` and athena-style joining them for the three-dimension review. The brief owns that contract end to end — what makes an agent a teammate, when delegating is worth it at all, when an agent is torn down, and the solo case — so read it there rather than re-deriving it here; this bullet exists only to say that /do's generic fan-out guidance above is superseded by it inside a cell. What the brief does NOT carry is the output-file contract above: every hephaestus and athena brief still names its agent's scratch report path, and you still wait on that file rather than on a sleep — in a cell the lead's own pane is the channel carl reads, so a review that exists only as a truncated chat reply is lost to both of you.
- **Write `90-build-report.md` into the brief's SET ROOT** (`<cellDir>/artifacts/`), per Write The Build Report above. It is written on EVERY phase 2, including a job that never had an artifact set — a job spec is still a plan reality can diverge from.
- **Stop at the manual-test gate.** After the tests and linters pass and the report is written, say:

  `manual test ready: <urls + what to try>`

  and STOP (end the turn). Do not proceed to a PR on your own — carl's reply is what passes the gate.
- **When his reply passes it**, shut any test services down and follow `.claude/skills/pr/SKILL.md` in your worktree for branch and PR conventions — read it BY PATH; do NOT invoke `/pr` by name, since a personal skill of that name would shadow it.
- Never declare the job done — accepting or merging is carl's move, never yours.

## Boundaries

- /do is for implementing an existing doc, not for re-spec'ing. If the user wants scope changes mid-implementation, update the doc first (or hand back to [[aim]]) before continuing to code.
- /do does not create branches, commits, or PRs unless the user asks. Follow repo git conventions (or a personal `git` skill, if one exists in this session) for branches and commits, and use [[pr]] for PRs.
- If the doc is in explain mode (describes an existing system), /do should generally do nothing — explain docs document current state, not future work. Confirm with the user before treating an explain doc as an implementation target.
