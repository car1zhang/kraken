# Do — Implement An Artifact Set

Take the artifact set produced by [[aim]] earlier in this conversation — `00-overview.md`, its diagram cards, and its section docs — and implement it. The set is the source of truth for scope, components, constraints, and testing. Before writing code, resolve any `P0` entries in the set's open-questions record with the user; after the code is verified, write `90-build-report.md` — the brief record of what shipped and where reality diverged from the plan.

## Preconditions

- An `/aim` artifact set must exist for this conversation: a set root directory (standalone: `~/designs/<slug>/`; in a kraken cell: `<cellDir>/artifacts/`) containing `00-overview.md`. The open-questions record is optional and lives outside the set: standalone, a sibling `~/designs/<slug>.questions.yaml`; in a cell, rows in `kraken.db` read with `kraken questions get <slug>`. A missing file or an empty list just means no open questions were raised (an `/info` explanation job never has any by design). Older conversations may instead have a single flattened `~/designs/<slug>.spec.html` / `.explain.html` from the legacy template flow (or `.spec.md` / `.explain.md`) — treat that file itself as the doc in that case.
- If no such artifact exists in this conversation:
  - Do **not** start implementing.
  - Tell the user: "No /aim artifact found in this conversation — run /aim first, then /do."
  - Stop. Do not infer a spec from prior chat messages alone; the artifact set is the contract.

## Workflow

### 1. Locate And Read The Set

- Identify the most recent `/aim` set root mentioned in this conversation (or the explicit path the user passes as an argument).
- Read `00-overview.md` in full, then every `.md` file in the set root other than `00-overview.md` in full (covers `5N-*.md` and any `6N+` section docs), then the open-questions record in full (standalone: `questions.yaml` if it exists; in a cell: `kraken questions get <slug>`). The set is the source of truth — do not rely on chat memory of what it said. (Diagram cards are supporting detail; skim captions/titles rather than reading every SVG body.)
- If working from a legacy single-file doc instead, read it in full the same way.
- The open-questions record is OPTIONAL: a missing `questions.yaml` (or an empty `kraken questions get`) means zero open questions for this set — skip straight to implementation (do not refuse or treat it as an error).
- If any section doc this workflow names (`50-components.md`, `51-code-map.md`, `52-testing-plan.md`) — or one referenced elsewhere in the set (e.g. by `51-code-map.md`'s review guide) — is absent, say so explicitly and fall back to `00-overview.md` plus whatever section docs do exist — never invent content to fill the gap. A solo set legitimately has none of the three named docs; that is not an error.

### 2. Resolve P0 Open Questions

- Collect every open-questions entry with `importance: P0` and no answer yet.
- For each unresolved P0, ask the user with `AskUserQuestion`. Group related questions into one call (up to 4 questions per call).
- An entry that already has an answer (and `answered-at`) is a **decision, not a question** — never re-ask it; treat the answer as settled and cite it if relevant. In a kraken cell those two fields arrive as silent row updates from carl answering on the board, and the daemon also types a `[kraken question-watch — automated notice, not a reply from carl]` line into your pane when one lands — so a cell parked on a question ends the turn and waits for that bump rather than heartbeat-polling the rows. The notice is a machine's: it is not a gate reply, and it is NOT a "later pane steer" for the staleness gate below — it announces the answer, it cannot supersede it. The bump is best-effort (it needs a live cell and can lag or miss), so still re-run `kraken questions get <slug>` before this step to pick up anything answered since the set was last read. Two staleness gates before treating an answer as settled, both measured the expensive way: an answer standing on a question whose TEXT you rewrote after it was given is an answer to the OLD question (`questions update` upserts by qid under the standing answer, and nothing marks it stale — a cell obeyed one and built a whole wave carl had already steered past), and an answer older than a later pane steer on the same subject is superseded by the steer — the pane is the newer channel. In both cases the answer is history, not a decision: act on the steer, or re-ask.
- **A question's context can go stale the same way its answer can — re-verify any premise in it that names the world outside this cell before acting on the question's default.** The staleness gates above cover the answer; nothing covered the question's own premises, and the measured cost was a duplicate feature: a P1's context asserted a sibling job was "a draft" to be retired, the sibling had shipped that exact feature fifteen hours before the `/do` arrived, and the cell built it again on the recommended default — with the falsifying evidence on its own screen, in a `kraken ls` it had run for a different question. A premise that names another job, another cell, or a PR is a claim about state that moves without telling you; `kraken ls` and the PR list are the one-command checks, run them before the default is acted on.
- If there are no unresolved P0 entries, skip straight to implementation.
- Do **not** ask P1/P2 questions unless the user requests it — state assumptions for those if they block progress, and surface them after implementation.

### 3. Record Newly Resolved Decisions

- After P0 answers come in outside a cell (where there's no board to append `answer`/`answered-at` for you), edit `questions.yaml` yourself: remove the resolved entry and note the decision in the relevant section doc (an `Assumptions`/`Decisions` note) instead. Leave P1/P2 entries untouched.
- In a kraken cell, never write `answer`/`answered-at` yourself — that's kraken's job once carl answers from the board.

### 4. Plan The Implementation

- Build a TaskCreate plan grouped by `50-components.md`'s component table. One task per component is a good default — that is the planning unit, not automatically a delegation unit (see the fan-out rule below).
- Honor the set's scope/non-goals/constraints section doc(s) strictly — do not expand scope.
- Use `51-code-map.md` (where things live, review guide) as the file-targeting guide. Verify those paths still exist before relying on them.

**The next six bullets apply only when you DELEGATE.** Work you keep for yourself — including every `solo: true` job, where there is no crew at all — skips to step 5, where the un-delegated path has its own instruction. There is no point freezing a contract against yourself.

- **Freeze the contract BEFORE you dispatch anyone — `50-contract.md` in the set root.** Whoever implements a slice must not also be the one who decides what that slice was supposed to do, so the requirement is written down first, by you, and both sides are held to that same text. One table per slice: **symbol · signature · obligations · owner**, where obligations are the behavioural claims the slice must satisfy, one short line each ("bumps NEITHER `rev` NOR `updated_at`", "both numbers or neither — a half estimate is refused"). It is symbol-level rather than conceptual — name `tokenGroup.commit` as readily as `core.SumTokensDelta` — but the symbol must be one the test file can actually reach, and that differs by language. Go and Python tests reach unexported names in their own package, and Swift reaches `internal` through `@testable import` (this repo sets `ENABLE_TESTABILITY` and every file in `ios/KrakenTests/` uses it), so none of the three needs help; its real limit is `private`/`fileprivate`, which `@testable` does NOT reach. **TypeScript is the one with no escape hatch at all** — an unexported symbol is unreachable from any other file, test included — so there the export is part of the frozen signature and must be written into it. The test of a good contract is one question — **could someone write a compiling test from this alone, with no access to the implementation?** If not, it is not frozen yet. For Python that question includes the IMPORT SHAPE of any callee an obligation names: `patch()` targets where the name is *looked up*, so whether the caller binds it at module level or imports it inside the function decides the patch target, and a contract that froze the symbol but not that fact sent two blind authors to the same wrong target independently — 10 of 38 first-run failures, one unstated sentence. State it beside the obligation that names the callee, or in a note under that slice's table (along with any harness fixture quirk a mock-based suite will hit with it). Two more checks before the freeze. A contract that states concrete expected VALUES — a match table, a lookup matrix — has those values EXECUTED against the stated fixture before it freezes: a table derived by reading is a hypothesis, a frozen one has been 33% wrong, and labelling wrong values as "the ones a naive implementation gets wrong" invites the implementer to bend the code until the table passes. And a matcher or formatter whose input CONCATENATES fields gets at least one fixture where those fields collide (equal, overlapping, one containing another) — fixtures where every entity's fields are distinct are exactly the case where a doubled-field bug cannot appear, and one shipped past three reviewers that way. A contract line about the test ENVIRONMENT ("in tests there is no `OPENAI_API_KEY`") is a hypothesis like the value tables, and it travels worse: briefs copy it forward as "rely on this", and a contract's word outranks a brief's. Measured, the fact was false on the machine (a credential file the loader also reads), the author that obeyed it shipped blind tests making live paid API calls, and the author that distrusted it and isolated `HOME` was the one that got it right — so write environment obligations as ISOLATION requirements the test must enforce ("the test isolates HOME and the key"), never as descriptions of what the environment supposedly holds. Write it even when Phase 1 never ran and the job spec is one paragraph; that is the case that needs it most. You own amendments; a teammate never edits it. **On a repeat `/do` for the same slug** — a follow-up PR off the recycled branch — earlier rounds' blind tests are still in the repo and still asserting, so the new contract must re-state every obligation they pin, or those tests fail against a contract that no longer claims what they test. Re-cover them, or delete the ones the change deliberately obsoletes; leaving them to fail teaches everyone to ignore a red suite.
- **Dispatch the implementer and the test authors in ONE message.** The implementer gets the contract, its file targets, **no test list** — it implements and never writes a test for the spec (a regression pin for a defect it fixes is fine: the implementer tests bugs, the authors test requirements) — and **an explicit instruction not to read the blind test files before the join has arbitrated them**. The authors' no-read clause alone guards only one direction: an implementer that reads the tests resolves every contract silence to whatever the fixture happens to assert, and when the contract is then amended to match, the chain is contract silent → implementer reads test → implements to it → contract rewritten from the test — the exact collapse the fix-brief rule below names, arriving through the unguarded door (measured: a store slice resolved a formatting silence from the blind fixture's double-spaces, and the contract was amended to agree). Seeing a compiler diagnostic that quotes a blind test file is not reading it — in Go the blind files share the implementer's package, so its own build output can leak their lines; report the diagnostic, do not open the file. **The implementer's verify-as-you-go commands must EXCLUDE the blind suites too**: a brief that bans reading the blind files and then orders `pytest` over the directory holding them hands the implementer their failure output, and a failure names the fixture's stubbing — one implementer redesigned its change to fit what a blind failure revealed about the stubs, without opening a file, which is sighted authorship through the back door. Scope the implementer's own checks to its regression pins and the pre-existing suite; the blind suites run at the JOIN, by the authors, on your signal. **That scoping is FLAGS in the command, never a judgment the implementer applies**: `--ignore=<each blind file>` written out beats "run the wider suite selection you judge affected" every time, because the judged selection reaches the directory holding the blind files — measured in one cell where two implementer briefs written in the same message differed by exactly this clause, and the slice with the flags was the only one whose blind pass was uncontaminated. The compiler-diagnostic carve-out is narrower in Python than it reads: a pytest failure quotes the ASSERTION SOURCE LINE and the expected value — the whole requirement — so the carve-out covers diagnostics that arrive unbidden from a properly-scoped run, never a deliberate re-run of the blind files by name to read their failures. And the implementer's DOC-file edits are a read channel in reverse: a `CLAUDE.md`/`AGENTS.md` updated mid-round with prose describing the unlanded implementation lands in the blind authors' auto-injected context, where they cannot decline it — measured, disclosed by the author it reached. Doc-file updates land AFTER the join, or those files join the no-read set. In the same message, **one** logic author and **one** edge author for the whole fan-out, however many slices there are — they get the contract, `50-components.md`'s per-component test plans, `52-testing-plan.md` when the doc phase produced one, and an explicit instruction not to read the implementation files. **That no-read clause names the byte routes, not the Read tool** — stated as "reads" plus a file list, agents parse it as a ban on `Read` alone: in one measured cell both blind authors ran `grep … --include='*.go' | grep -v "_test.go"` (a filter whose whole target is the implementation) and the implementer edited two no-read test files with `perl -pi` chosen precisely because Edit would have required reading them first. So the clause says: `grep`/`sed`/`awk` over those files, `git show`/`git diff` of them, and any in-place rewrite of them are all reads — and any accidental contact is DISCLOSED in the report, because two of those three agents disclosed and one did not, and an undisclosed graze reads identical to a clean silence. **Concurrency is the mechanism, not a courtesy**: when they start there is nothing to look at, so blindness is a property of the schedule rather than a promise nobody can audit. Split by dimension — logic authors the stated invariants and happy paths, edge authors boundaries, error paths, and refusals. **Both sides' briefs convey the contract by quotation or pointer and add NO expected outcomes of the lead's own**: a dispatch brief that walks the edge list pairing each case with its verdict ("is_zero beats zone; unverified beats both", "pairs absent from a non-degraded set get NO exception") is the join signal's no-diagnosis rule broken one step earlier — the authors transcribe the lead's answers instead of deriving assertions from obligations, and a 25/25-green join built that way has certified exactly the behaviour a sighted review then flagged BLOCKING. The schedule keeps the authors blind to the CODE; only the brief's restraint keeps them blind to your conclusions. They **author but do not run**: tests written against code that does not exist yet fail for uninteresting reasons, so they report the file written and wait. And the "a contract silence is join evidence, not something to work around" instruction covers EVERY silence, not just a failing import: authors who hit an unstated return shape or parameter list have improvised tolerant multi-shape probes around them, and a tolerant probe on an unfrozen seam converts the contract gap into a false PASS — three tests in one measured join were green only because the probe swallowed the shape mismatch. Assert one answer, strictly, and let the join arbitrate the failure.
- **Give each author its own test file, and its own identifiers inside it.** File ownership stops an edit race, which is all it stops — two blind authors in one Go package share a declaration space, so both writing `func mkCase(...)` fails the whole package's test binary and takes every unrelated test in it down too. So: prefix every package-level identifier a test file declares with its dimension (`contractMkCase`, `edgeMkCase`). Names, by language, because a blind author cannot check what the runner collects and a file that is silently never collected reports as a pass:

    | | test author's file |
    |---|---|
    | Go | `<subject>_contract_test.go` · `<subject>_edge_test.go` |
    | Python | `test_<subject>_contract.py` · `test_<subject>_edge.py` — and put it where that repo's runner already looks (`testpaths`/`python_files` in `pytest.ini` or `pyproject.toml`, or the paths CI passes), NOT beside the module: the filename matches everywhere, the LOCATION is what decides collection |
    | TypeScript | `<subject>.contract.test.ts` · `<subject>.edge.test.ts` — vitest collects only `*.{test,spec}.*`, so an underscore name is never run |
    | Swift | `<Subject>ContractTests.swift` · `<Subject>EdgeTests.swift` — and regenerate the xcodeproj before the join, or the file sits outside the target |

    If the file already exists from an earlier round, **append — never replace it**. Earlier rounds' blind tests are regression coverage, and reading a test file is not reading the implementation.
- **Signal the run only when EVERY implementation slice is done.** One barrier for the whole fan-out, not per slice: a slice's tests routinely touch a symbol another slice owns, so a per-slice run reports failures that are just the other half of the work missing, and the noise trains everyone to ignore the signal. When the last slice reports, `SendMessage` both authors to run their suite and report results — and the join signal carries **no diagnosis**: a heads-up that pre-classifies a likely failure ("if a patch target doesn't exist, that's mechanical, not a code bug") seeds still-blind authors with the lead's verdict before arbitration, and the table below is then applied to a conclusion it did not produce. If a slice never reports, the barrier never fires — treat it exactly as the expiry case above: find out whether that teammate died, then re-brief it or proceed without it and say which.
- **Then arbitrate every failure, against the contract text — and do this BEFORE any review round.** The order is not stylistic: reviewing means reading the implementation, and an author that has read it cannot un-read it, so every author must finish arbitrating its own tests while still blind. Three verdicts. **Arbitrate one ASSERTION at a time, not one test at a time** — a single test routinely asserts several things at once ("a half pair is refused, nothing is stored, and the response is 400"), and a test whose assertions land on different rows has no verdict as a whole. Take the assertion that actually failed; if more than one did, or if one assertion bundles a stated obligation with an unstated extra, split them and run each through the table on its own. Then start from what the contract SAYS about that assertion — the observability check below is scoped to what that answer turns up, not asked ahead of it:

    | Does the contract… | Verdict | Action |
    |---|---|---|
    | state the obligation the test asserts — including a signature the code drifted from | **code bug** | Fix brief to the implementer |
    | state the opposite, or place that obligation explicitly elsewhere | **test bug** | Fix brief to the authoring agent, quoting the contract line: drop the assertion or move it |
    | say nothing about it, and the answer is not a product decision — the author asserted a requirement nobody set | **test bug** | Fix brief citing the silence. The author may answer once by deriving the assertion from an obligation that IS stated; if it does, that re-classifies as a **code bug** and goes to the implementer. Otherwise the assertion is dropped |
    | say nothing about it, and the answer is a genuine product decision | **contract defect** | File a question row with your stated default, amend `50-contract.md` to that default, re-brief both sides, and keep going — do not wait on the answer |

    **Then one further check, and only on row 1** — where the test asserts exactly what the contract states, so the assertion is right and something else must be wrong: **can that STATED obligation be observed from the symbols the contract names?** If not, or if the test cannot compile against a contract the code did honour, it is a **contract defect**: amend `50-contract.md` to name a symbol that exposes it, re-brief both sides, and re-run. The scoping is the whole of it, in both directions. Ask observability about the *contract's* obligation and it catches a real gap in the frozen surface; ask it about the *test's* assertion and it swallows rows 3 and 4, because an assertion nobody ever specified need not be observable from symbols chosen without it in mind — and the verdict it would hand you is `contract defect`, which writes the author's invention into the contract as a requirement. Keeping it off row 2 matters for the same reason in reverse: there the assertion contradicts the contract and is wrong whether or not anything can observe it, so letting an unobservable obligation re-classify it would leave a wrong assertion red with nobody owning it. If a row-2 contract also turns out to name no reader for its obligation, that is a contract improvement worth making — after the test bug is fixed, not instead of it.

    Every branch ends in an action that makes the suite green or the assertion gone; a verdict that leaves a red test with no owner is not one of them. The row-3 appeal is the corrective for the one judgment here that is genuinely hard — "is the contract silent on this, or does it follow from something it does say?" — and it is what keeps a wrong reading from silently deleting real coverage. Silence otherwise splits by whether anyone could have decided it in advance, and routing it to `contract defect` by reflex writes an invented requirement into the contract, which is the author defining the requirement just as surely as reading the code would be.

    Two compile failures are neither: a **name collision or a missing import** in the test file is a mechanical fix by the owning author, and code that **deviates from a frozen signature** is a `code bug` — read that row first, because a compile failure routed to `contract defect` by default would have you amend the contract to match whatever the implementation happened to do, which is the implementation defining the requirement and is exactly what this arrangement exists to prevent. **Compile-gate the test files FIRST, before either author runs a suite** — blind authors cannot run anything, so mechanical compile errors (an unused variable, a typo) ship as a class, and in Go both authors' files share one package: either one's compile error takes down the package's whole test binary, blocking the OTHER author's run. Route each mechanical error to its owning author as a mechanical fix, not an arbitration. And an author blocked by a sibling's compile error reports it and waits — never blanks the sibling's file out (an overlay mapping it to an empty stub) to get its own suite running: a join reported over half the blind suite is a partial answer wearing a green shape, and the lead re-runs it anyway. "Reports it and waits" means **reports it in the chat reply and ENDS THE TURN** — never a guessed-duration poll loop on the sibling's file (two agents in one wave each invented `for i in $(seq …); do grep -q … && exit 0; sleep 15; done` and both worked only by luck), and never an alias or shim around the missing symbol (a `sys.modules` alias mapping the old name to the new module converts a cross-slice dependency into a false green). The barrier is the lead's machinery; a blocked agent has no wait affordance and should not improvise one — one brief said exactly "report that state honestly and finish" and the agent polled anyway, so say it as the ONLY option, in the brief of any slice that names a cross-slice dependency.

    A **fix brief cites the contract obligation, never the failing assertion** — cite the test and the test becomes the requirement. A fix brief to the implementer never authorises a change to a test file: while the authors are still blind, only the authoring agent edits its own file, and only on a `test bug` verdict (after they are sighted, see the paragraph below). On a `test bug` that author may contest once, but only by quoting a contract line; an appeal that argues without citing the contract is not one. And **never resolve a contract defect by sending an author to read the implementation** — that is the single move that destroys the property, and a blind test that will not compile is the design working (the contract was ambiguous and said so in minutes) rather than failing. The mirror move is equally banned: a contract silence is never resolved by the implementer reading the blind tests to learn the answer — that is the same collapse run from the other side, and the dispatch bullet above bars the read outright. Re-run the suite after every fix, and cap it: two rounds per failure, then work the contract text directly yourself. **The blind suite stays live for the rest of the job**, not just for this phase — a review-round fix, or any later change, can turn a green blind test red, and when it does it re-enters this same table rather than being edited to fit. Arbitration is one-shot only in the sense that the AUTHORS stop being blind after it; the tests do not stop being the requirement. One thing changes once they are sighted: a `test bug` verdict after that point is **yours to apply** — you drop or correct the assertion yourself, citing the contract. Not because you are less sighted than the author (you wrote the contract and ran the review, so you are more so), but because you are the contract's author and the arbiter of every other verdict: handing the pen to the agent whose own assertion is in question is what the split exists to prevent, and it is no better late than it would have been early.
- **A round where every blind test passes first time has failed, and it looks exactly like success.** It means the contract was written from code that already existed, or the tests were written loose, or someone peeked — or, the fourth cause, the contract specified the MECHANISM at implementation granularity (exact DDL, buffer constants, seek-and-discard steps), so author and implementer shared a mechanically complete oracle and blindness bought nothing a compile check would not; a lead reaching for "the contract was written tight" as the reassuring alternative is naming this cause and misfiling it as absolution — it is a finding about the contract, and the next contract states obligations at the level of observable behaviour instead. Two more causes, both measured on nights when nobody peeked and the contract was honest. **A shared external oracle**: on a parity port of a live donor module, contract and implementation both derive from the donor, so the blind suite re-pins donor-shaped behaviour rather than discriminating the new design — on such a port the suite's value is regression pinning, the REVIEW carries the discovery load, and it is scoped to the seams that deviate from the donor (the measured defects were exactly there: one in the frozen contract's novel seam, one in a seam the lead's own amendments created). **A private oracle the implementer rebuilt**: an implementer that reconstructs the contract's own fixture-facts table as an out-of-repo probe suite — or drives a headless browser against its own build — has run the blind suite early, as the wrong party; two implementers did this independently from one "do NOT run the repo's runner" sentence, and the 100%-green join was pre-converged rather than adversarial. The private probe is not banned outright (one caught a real rendering defect nothing else could see), but it is DISCLOSED in the implementer's report, so the join's pre-convergence is priced at the join instead of reconstructed afterwards. And one fixture-level blindness with no alarm on it: **a fixture that SEEDS the state it is meant to probe cannot see the absent case** — both blind authors pre-seeded a watermark their fixtures then held across ticks, so the first-run path (absent watermark, the round's worst defect) was invisible to 245 green tests and neither author disclosed it as a silence, because "watermark edges" reads as edge VALUES of a present watermark. The edge author's dimension list names first-run / absent / never-initialised state explicitly, and the join asks each author which states its fixtures CONSTRUCT, not only which they assert. The mechanism cause has a second-order form with no alarm on it: **when the contract also prescribes how the TEST DOUBLE behaves, the double inherits the algorithm's blind spot** — a fake specified from the same mental model that produced the pager omitted the one boundary re-read the bug lived in, both blind authors built exactly what they were told, and an 84-test green join certified a pager that could never reach its cap in production. State the fake's obligations as observable behaviour too, and when a review does catch a defect the suite missed, require the fix's test to PROVE DISCRIMINATION: the previously-broken implementation must fail it (one cell did exactly this — "the r2-broken shrinking pager now fails 2 of 5 B3 tests" — and that sentence is the only evidence the regression guard is real). The same proof applies to any test whose whole purpose is to pin ONE guard: delete the guard (in the isolated copy, per step 5's baseline rule) and confirm the test goes red — a reviewer running exactly that counterfactual is the only thing that has caught an INERT green test, and the inert shape is specific enough to name: **a test that asserts by RAISING inside a fake is inert against any code path wrapped in a broad `except Exception` with a fallback default** — the code swallows the `AssertionError` and returns the fallback, the test stays green with the guard deleted, and it survived a full suite run plus every linter while pinning the one behaviour carl had explicitly steered for. Assert on a recorded call flag instead, or fail through a `BaseException`-derived escape (`pytest.fail`'s `Failed` is one). Say so in `90-build-report.md` rather than banking it. The same discount applies per slice: **a green join over a KNOWN contract silence is not evidence about the silent part.** When an author reports pre-run that a slice freezes no symbol for some obligations — put that in writing and hold the dispatch until the contract is amended, because a slice with no frozen symbol fails the compiling-test question above and is not dispatchable — a 0-code-bug join for that slice says nothing about those obligations, and one such join was followed by seven real defects in exactly the rows the authors had flagged as unpinnable. **The authors' join reports get the same read-in-full treatment the review bullet below gives verdicts — a keyword grep is not reading them**: the disclosed silences are the only thing that makes a green join interpretable, and each one gets an explicit disposition (amend the contract; pin it at the join — a pin authored by the DISCLOSING author, re-briefed while still blind, since a lead-authored pin is a sighted test and is recorded as one in `90-build-report.md`; or record it there as unpinned). One lead consumed 27.9 KB of author reports through two greps and one 30-line window — the first grep matched nothing because its alternation ran without `-E` — missed five of one author's seven disclosed silences including an explicit recommendation that the lead pin one obligation with a direct assertion at the join (never done), and Read every review verdict in full the same session, because the rule said verdicts and said nothing about join reports. Reading in full carries one more obligation: **a report's OPERATIONAL lines get a disposition exactly as its findings do.** A teammate's "ruff is not on PATH in this cell; the venv is absent" is a one-line fixable blocker, and a lead that read the report, acted on every finding, and skipped that line paid for it ten hours later with an extra PR-time lint commit over both blind suites — the reading protocol treats a report as a findings list, and the environment line falls straight through it.
- Fan components out to teammates — `Agent` calls that each pass a `name`, so each gets its own pane and stays addressable by name — when the work genuinely runs in parallel: components that touch disjoint files and don't depend on each other's output. A change that is one coherent edit, however many files it spans, is faster done directly than briefed out; file count is not the test, independence is. **Disjoint file lists are not independence**: a slice that renames or creates a symbol another slice's first import needs has a hard build-order dependency however clean the file split looks — sequence the rename slice ahead of its consumers, or give the consumer's brief the report-unverifiable-and-stop instruction from the join bullet below as its only option (measured: a consumer slice armed two half-hour poll loops on the other agent's file and aliased the old module name in `sys.modules` to get anything to import at all). Unnamed in-process subagents are for read-only exploration only — never for an agent that writes a file **into the repo** or judges another agent's output. "Read-only" is about the repo, not the filesystem: a researcher still writes its own report to a scratch path, per the output-file rule below.
- **A teammate starts in YOUR shell's current cwd, not the worktree root — so return the shell to the root before any spawn.** The Bash tool's cwd persists, and an Agent call inherits it: a lead that had `cd`'d into `ios/` for a build spawned a teammate whose brief said "relative to your cwd, the worktree root" while its actual cwd was `…/ios` — the mandated first Read failed, and its transcripts filed under a sibling project dir. Same brief template, teammates spawned 38 minutes apart, two different truths, decided by where the lead's shell happened to be. **The stakes are the hook envelope, not just paths**: `.claude/settings.json` binds by cwd, so a teammate spawned from a subdirectory runs with NO bash-lint, no recall hook, none of the cell's guardrails — measured: the one reviewer of five spawned from `api-service` was the one session where an unquoted `echo ===` truncated a probe silently (`is_error: false`, second half dropped), twice, and the evidence behind two BLOCKING findings was gathered through those truncated probes. Make the return-to-root a step in the SAME message as the spawn (`cd <worktree root>; pwd` immediately before the Agent calls), not a habit — the one measured escape was a late single spawn 10 hours after a fan-out that had done this correctly.
- **Every brief names the agent's output file, before that agent starts.** Give each teammate — an implementation slice and each of the three single-dimension review variants alike — one exact scratch path outside the repo (`/tmp/<slug>-<agent-name>.md` is a fine default; never a path inside the worktree, since a report is not part of the change), and tell it plainly: the full findings go in that file, and the chat reply is a one-line pointer to it. This is not bookkeeping. The teammate→lead reply channel truncates a long message and is not reliably readable by the lead at all — reviews have arrived empty, been scraped back out of the reviewers' own panes with `tmux capture-pane`, and forced a mid-flight "write it to a file instead" correction that made three reviewers re-serialise a review they had already finished. The **review** briefs need this most: three variants report at once and a findings list is the longest thing any of them writes, and a contract improvised per spawn is one that ends up in five briefs out of six — the sixth being the one that costs a round trip. Beside the report path, give each agent its own scratch DIRECTORY (`/tmp/<slug>-<agent-name>/`) for working files: two reviewers dispatched in one message have written different benchmark programs to the same hard-coded `/tmp` path in a live overwrite race, and two more rebuilt the same from-scratch font parser six minutes apart because a measurement of the ENVIRONMENT has no shared home — blindness is about the implementation, not about environment facts, so when a round will need one expensive measurement, take it yourself and put it in every brief, or name one reviewer its owner.
- **A brief conveys a contract obligation by QUOTING the contract line, or citing it by file:line — never by restating it in the slice's language.** A restatement is a second source of truth, and when a multi-language contract's one shared rule was hand-restated into each slice's brief, the two restatements disagreed — so the divergence the contract exists to prevent entered one level ABOVE the code, in the lead's own words, while the frozen artifact sat correct the whole time. An implementer that catches its brief contradicting the contract should trust the contract and say so. The measured leak is the AMENDMENT round: fix briefs quote correctly, while the summary a lead writes when re-briefing three teammates on what just changed is wall-to-wall paraphrase — and one of three paraphrases got a coercion rule wrong, an author dutifully pinned the paraphrase, and the lead arbitrated its own sentence as a test bug ("the fault is mine"). An amendment summary quotes the amended contract lines, exactly as a first brief does — and it quotes ONLY the contract text, never the author's own disclosure or test number, because "your test 51's key shape is unchanged" and "your test stands" are pre-classified verdicts delivered to still-blind authors, the join-signal rule broken one message earlier (measured alongside a 140-test zero-semantic-failure join).
- **The Bash tool is zsh on macOS, and every brief that includes shell work says so.** The measured aborts, each rediscovered silently by agent after agent: an unquoted glob (`--include=*.py`) dies with `no matches found` — that COMMAND never runs (even a `rm -f`: NOMATCH fires before rm sees the flag) and an `&&` chain stops there, though later `;`-separated commands do still run — and a skimming agent records the abort as a false "no files match"; any UNQUOTED word beginning with `=` — a bare `===SECTION===`, a plain `echo ===`, a wordless run of sixteen `=` — is equals-expanded and kills the compound AFTER printing its first half, so the dropped second half is invisible behind a page of legitimate output and the only symptom is a ~20-character `(eval): == not found` tail on kilobytes of good payload, which reads as success to anyone who only needed the first half. QUOTING is the entire fix — `echo "==="` is safe (measured: dozens of quoted `=`-separators run clean on days the unquoted ones all abort), and the rule is the mechanism, not the example shape: agents pattern-matching on `===SECTION===` have re-typed `echo ===` and the long bare run without recognizing either; `path` as a variable name wipes PATH (`fpath` clobbers the function search path the same way); `timeout(1)` does not exist (use a background watch, not a wrapper that kills the verification it wraps) — and `timeout … 2>/dev/null | wc -l` is the worst form, because the `command not found` is swallowed, the pipeline exits through its last stage, and the probe returns a silent FALSE ZERO with `is_error: false`, which then ships as "0 files match" (the bare unpiped form at least exits 127). So: quote every glob, quote any separator that starts with `=` (or open with another character), never leave a `grep`/`sed` that may legitimately match nothing as the LAST command of a `;`-compound — a tail no-match exits 1 with every wanted byte already printed, so the caller re-runs a command that had already succeeded and error counters record a failure that wasn't; put it earlier or close with `; true` — and prefer absolute paths — whether cwd persists across calls is HARNESS-DEPENDENT (measured both ways in two cells on one night: one shell kept the previous call's `cd` so a repeated `cd api-service` failed from inside it, the other reset to the worktree root between calls so a relative path went nowhere), so a relative path is a bet on which behaviour this session has, and nested layouts (`core/core/...`) alias the loss into failures shaped exactly like "this file does not exist". **What goes in a BRIEF is the fixed forms, never the abstract rule**: a brief saying "quote every glob" measured 0-for-3 on the very shape it names (three reviewers so briefed each typed an unquoted `--include=*.py` anyway), compressed briefs shed the `timeout`/`path=`/cwd clauses first, and one lead wrote six shell-heavy briefs with no dialect sentence at all (ten hook blocks, two shapes, six agents) — so every brief that includes shell work carries this line verbatim rather than a paraphrase: *Shell is zsh on macOS: quote every argument containing `*` `?` `[` `(` — `--include='*.py'`, a bare path glob (`'internal/cmd/*.go'`), a parenthesized API name (`'textselection(_:)'`) all abort the whole command unquoted — write `echo "==="` (quote any word starting with `=`), `timeout N cmd` does not exist (use a background watch), never name a loop/read variable `path` or `fpath` (`while read sid path` wipes PATH for the rest of the run), use absolute paths (an earlier call's `cd` may still be in effect, or the cwd may have reset — a relative path is a bet either way), and never end a `;`-compound with a grep/sed that may match nothing (close with `; true`).* The glob clause is stated as the CHARACTER SET deliberately: briefs that showed only the `--include=` example measured broken by a bare path glob and by Swift selector syntax the same night — shapes the example literally permits. The cwd clause is worded around the `cd`, not around "instability", deliberately: "cwd is not stable" reads as "random, so be careful", agents then use relative paths that work for dozens of calls and silently break after someone `cd`s — 14 of one cell's 26 Bash errors were this exact drift, in BOTH directions (`cd api-service` re-issued from inside it, root-relative paths issued from inside `api-service`, one of which double-prefixed a git pathspec and killed a commit).
- **A brief that orders a gate run names the exact interpreter or binary path, EVERY round.** A cell worktree has no venv and no node_modules, so `python3 -m pytest` hits `ModuleNotFoundError` and the agent detours into venv archaeology — several agents per cell, rediscovered independently every time. Worse than the wasted calls: an agent that gives up and builds a throwaway `/tmp` venv then runs the gate against pip-resolved versions, and a gate run in a different dependency set is not the repo's gate however identical its counts. First-round briefs tend to carry the path (`~/Developer/monolith/api-service/.venv/bin/python -m pytest …`); the measured failure is the RE-brief dropping it — compressed fix-round briefs shed exactly this clause, so restate it every time. The path must be an ABSOLUTE path to a binary in a venv that EXISTS — never `poetry run <tool>` from a fresh worktree, which does not fail loudly: a venv-less `poetry run` silently CREATES an empty venv and the tool then emits phantom missing-import errors instead of "no environment", so every agent in the fan-out detours into interpreter archaeology (measured: five teammates spent a quarter to a third of their tool calls on it after both implementer briefs named a `poetry run` command, and one gave up and hand-built its own pyright project in /tmp). Where this collides with the make-target preference below, the tiebreak is: run the command YOURSELF first — a make target that works from the worktree is named as-is, and one that needs a venv the worktree lacks is named with the absolute interpreter substituted in, saying so. A brief that names a command is asserting the command works — same rule as the bullet below. And the BUILD ENVIRONMENT is shared even where file ownership is partitioned: venv creation and removal, dependency installs, and any other toolchain mutation belong to you or to ONE named agent, stated in every brief — two teammates with disjoint file lists have deleted and rebuilt the same `.venv` in opposite directions minutes apart, each correct in isolation, the survivor's test run working only by ordering luck. And when the repo has a make target for the gate, name THAT (`make lint-check`) rather than hand-expanding it: one brief named the right target and then supplied an expansion missing the `--preview` flag the Makefile passes, the reviewer ran the expansion, and a false "ruff clean" reached the shipped build report before CI failed on it. **A gate command that `cd`s is written as a SUBSHELL — `(cd <pkg> && <gate>)` — never a bare `cd <pkg> && <gate>`**: the bare form relocates the shell for every later relative path, and it is the one cwd-drift writer the dialect line's "use absolute paths" clause cannot reach, because the drift's author is the sanctioned command rather than the agent (measured: every session in one cell drifted this way, and the lead's retired-symbol sweep — a whole-repo `rg` with no path argument — then ran from the drifted directory, answered "sweep is clean" over a package it never searched, and shipped 110 CI failures). The subshell costs one pair of parentheses; the same rule goes into every brief that carries a `cd`-shaped gate command. And a sweep whose EMPTINESS is the finding names its root explicitly (`rg <pattern> <absolute repo root>`): a no-path grep is a silent partial answer from wherever the shell happens to be. The interpreter clause has one more measured leak: briefs that order NO gate at all — a blind author's "author but do not run" — still get an interpreter sentence, because an agent that writes code wants a syntax check before calling the file done and will otherwise burn calls hunting for one (measured three cells in one night: authors with no interpreter line fell back to hand-rolled `awk` linters and `/tmp` venv archaeology while the implementer beside them, whose brief named the path, never stumbled). Say "if you want a lint or syntax check, this is the binary: <abs path>; do not go looking for another", or say plainly that no check is available and the join runs them.
- **A brief may only assert what you checked this session — same rule as a code comment, and it is broken most often in briefs.** Step 5 already forbids a comment that claims something you did not verify; the same sentence in a BRIEF is worse, because the agent has no way to check it and every reason to trust it. Two shapes to watch. A number lifted from a counter or a tool schema is a HYPOTHESIS, so write it as one ("the digest reports X; verify before building on it") — leads have handed teammates measured-sounding figures that were off by 20x and premises for events that never happened, and the teammate then spends its first calls disproving its own assignment. And an anomaly goes over as a QUESTION, not a claim: "say what that shape means" gets you the real cause, "confirm that X" gets you X. This bites hardest in a fix-round brief, whose justification text is often written straight into the repo — a false fact there ships unless a reviewer happens to measure it. **A command line in a brief is a fact like any other: run it first, or label it unverified.** An unrun `xcodebuild … -only-testing:KrakenTests/<FileName>` cost three agents independent diagnosis rounds, because `-only-testing:` takes `Target/ClassName` and this skill's own filename + identifier-prefix rules GUARANTEE the class names differ from the file name — so the flag can never match; name the classes, not the file. (`/aim` already holds itself to this: hermes gets the lint command "with its flags already filled in".) The environment claims a brief makes come from the same trap wearing a different probe: **a pipeline's exit status is its LAST stage's, so a probe piped through `| head` or `| wc` before `&&`/`||` answers unconditionally** — `ls <path> 2>/dev/null | head -2 >/dev/null && echo present || echo MISSING` prints `present` for a path that does not exist (the dialect line's `timeout … | wc -l` false ZERO is this same mechanism; this is the false PRESENT twin, and a lead that knew the first typed the second anyway). Test existence with `[ -d <path> ]` / `[ -e <path> ]`, nothing piped. And shape any environment assertion a brief must carry as a HEDGED claim with a named owner — "node_modules exists; do not reinstall unless something is genuinely missing, and say so if you do" — which is the measured difference between a false brief fact costing a two-call detour and costing a fan-out-wide environment hunt.
- **Then wait on that file existing, not on a guessed duration.** The output file appearing is the real completion condition — wait for it, then read it; do not treat the chat reply as the report. Never sleep a guessed number of seconds hoping the work is in by then: a guess is either dead time or a read of a report that isn't written yet, and blind waits have outlived the session that started them.
- **How to wait: ONE background until-loop over every report path — then end your turn.** A hand-rolled poll burns a turn per check, and a blind `sleep` is refused: a standalone long sleep, or one that OPENS a compound command, comes back `Blocked: standalone sleep 25 …`. (Put anything in front of it and it runs — that is a gap in the check, not permission. The rule stands on the argument above it: a guess is either dead time or a premature read.) The refusal names both affordances — `Monitor` with an until-loop, and `Bash` with `run_in_background: true` — and a sleep INSIDE the loop is the sanctioned form, not the banned one. The ban extends to BRIEFS you write: "re-check once after a few minutes" in a teammate's instructions induces the exact guessed-duration sleep this bullet forbids, owned by an agent the rule never reaches — a reviewer so briefed backgrounded two sleeps whose re-checks reported after its verdict was already written, buying nothing. Give the teammate the CONDITION to re-check on ("when the edit lands", "when the report file exists"), never a duration.
    - **Fetch the tools first, in one call.** `Monitor`, `SendMessage` and `TaskStop` are all DEFERRED, absent from the default roster — which is the whole reason leads fall back to `ls`-in-a-loop and to sleeps the harness then refuses: an agent that never goes looking does not know they exist. `ToolSearch("select:Monitor,SendMessage,TaskStop")` at the top of the fan-out, before you need any of them. `SendMessage` is how a fix round reaches the same teammate; `TaskStop` is Clean Up Agents below. `TaskList` is deliberately NOT in that list — it answers neither question this step or that one asks of it, and the reasons are below and in Clean Up Agents.
    - **Wait for the whole fan-out in one watch, not one per agent.** `until [ -s a ] && [ -s b ] && [ -s c ]; do sleep 15; done; echo READY` — three review variants report at once, and three separate watches wake you on the FIRST arrival, which reads as the round being complete when two thirds of it is missing. One conjunctive watch gives one wake, and its expiry means "at least one is missing", which is the diagnostic you actually want. That reason bounds the rule: wait for the whole set when you need the whole set before you can act, which is always true of a review round. If the slices are independent and you would act on each arrival, wake per arrival — but `echo READY <path>` so an arrival is never mistaken for the round. Use `-s`, not `-f`: `-f` is true at byte zero, and the heredoc fallback in the read-only-researcher bullet below creates the file before it fills it.
    - **Pick either affordance; write the call out.** Both work — `Bash` with `run_in_background: true` is the harness's own recommendation for a single notification, and `Monitor` gives you an event stream you can widen. `description`, `timeout_ms` and `persistent` are all REQUIRED alongside `command`, and the `timeout_ms` default is only 5 minutes — shorter than most review rounds — so never leave it unset: `Monitor({command: 'until [ -s a ] && [ -s b ]; do sleep 15; done; echo READY', description: 'athena r1 reports', timeout_ms: 1800000, persistent: false})`. Never `persistent: true`: it ignores `timeout_ms`, and the expiry is the signal.
    - **Then end the turn.** Neither affordance blocks — both return immediately and wake you when the loop exits — so do not read the report in the turn you armed the watch; there is nothing there yet. The loop's condition must be the REAL one, the report paths themselves; a loop on a sentinel that cannot exist (`until [ -f /tmp/never-exists ]`) is the blocked sleep again wearing the shape of the fix, and it burns the whole timeout while telling you nothing.
    - **`ScheduleWakeup` is not a third affordance — never arm it as a belt-and-braces heartbeat.** Its wake payload is a generic autonomous-loop brief whose stated goal ("get the PR ready to merge", commit-and-push guidance) contradicts the cell's stop-gates, so the tick arrives carrying a different job contract into a cell that is correctly parked — one lead so parked was told by its own heartbeat to advance the PR, the tick died on a network error, and the cell sat dead ~18 minutes until carl intervened; measured across two cells in one night, no heartbeat ever delivered a wake the armed watch had missed. The two affordances above plus the daemon's own bumps are the only wake sources a cell needs; if a heartbeat is already armed, `ScheduleWakeup({stop: true})` ends it — "armed" meaning you have positive evidence one exists: you armed it this session, or a tick actually arrived. Absent that evidence the stop is not a precaution to take, and it is never one to repeat: an answer saying there was no pending wakeup to cancel means there was nothing to stop and never will be until something arms one, so never call it again on that answer — a lead parked at a gate ran nine identical no-op stop calls, one per idle ping, each a full turn re-read of a multi-million-token cached context, with the tool saying so every time.
    - **Treat expiry as news, and check the PANE.** An agent can die having written nothing — an output ceiling hit mid-answer is one observed way — so "the file has not appeared" has two meanings, and a watch that only re-arms cannot tell them apart; a lead that keeps re-arming waits until something else kills it. On expiry, `ls` the paths to see which are missing, then look at those agents' panes with `k ls`: it maps each pane to the agent's NAME and status, which is the whole question, and a teammate IS a pane — its absence is the only positive evidence of death. Two mechanics of that probe, both paid for: in a monolith cell spell it `kraken ls`, never `k` — a guardrail there blocks `k` as a kubectl alias and kills the WHOLE compound it appears in, so a bundled probe's silence is indistinguishable from a negative result; and run the probe as its own command, bundled with nothing a guardrail might refuse. A nudge to a silent teammate needs positive evidence of death first, and always carries "if you already delivered, reply with the report path — do NOT re-do the work": a nudge that landed seconds after delivery has made a reviewer rewrite a finished review against a tree that had moved, so the file on disk and the review the lead acted on were different documents. (Order matters: a finished teammate's pane is gone too, so it is missing report PLUS missing pane that means died. Raw `tmux list-panes -a` is a weak fallback for when `k` is unavailable — a teammate's pane title is its agent TYPE, not its name, so three athenas are three identical rows: it can tell you how many are alive, never which.) `TaskList` cannot answer this — it lists the `TaskCreate` plan board, whose status is self-reported, so an agent that died mid-answer leaves a task reading `in_progress` forever. Then either re-brief them or proceed without them and say which. Four reachability facts bound what that probe may conclude, each one measured the expensive way. **An `idle (available)` notification is neither a completion signal nor a probe trigger** — idle fires at every turn boundary, the armed watch already covers the report paths, and probing the paths on an idle ping RACES the very write it is checking for: a lead's flat "your report file does not exist yet" nudge has landed seconds AFTER the file did, and every reviewer so accused then chased the same invented sandbox theory and re-serialized a finished report. When an idle ping arrives and the watch has not fired, say nothing and end the turn; a nudge is only ever earned by the watch EXPIRING, and it asks ("if you already delivered, reply with the path"), never asserts. **Check a notification's own timestamp against your dispatch time before acting on it**: a reused teammate name can deliver a queued ping from a PREVIOUS run of that name, `TaskStop` does not cancel a stopped teammate's pending ping (it arrives on your next idle edge, hours later, and its text becomes your visible last words), and a stale ping acted on has produced a false "your edit is incomplete" correction to a teammate that had finished cleanly. **A live pane showing `question` in `k ls` may be sitting on Claude Code's session-limit modal.** Inbound SendMessages are QUEUED behind it, not lost — a pane held one for half an hour and delivered it within 60ms of the modal clearing — and dismissing it (`tmux send-keys -t <pane> Enter`) releases that whole backlog into a window that is still exhausted, where each message dies on a rate-limit reply within a second (measured: nine such deaths across three reviewers in one round). The modal exists BECAUSE the window ran out, so dismissal is the move AFTER the window has reset or an account swap has landed, never a fix for the limit itself — and since the backlog it releases is stale briefs, follow the dismissal with one message saying which of the queued asks still stand. **And `TaskStop` is terminal**: a stopped name is unreachable, not idle — a send to it bounces — so work discovered after acceptance (an answered question changing a label on an accepted artifact) goes to a FRESH spawn with a Read-then-Edit brief, which is a reason to hold acceptance until nothing pending can still change the artifact.
    - **Waiting quietly is safe — but that cover is the TEAMMATE's, not the wait's.** Inside a cell the working/blocked roll-call counts the teammate's own live pane, not just yours (`cellActive`, internal/jobs/status.go), so while a teammate is actually running the board reads the job as working however silent you are — and when the teammate dies the cell falls to blocked and the daemon flags it, so going quiet is the safer failure too. A spin loop to look busy is pure spend. But a watch armed on a long build or test run with NO teammate alive has nothing to vote for it: the cell reads blocked and the daemon pings carl for a job that is fine, so for those say what you are waiting for in the pane before you go quiet.
- **Three rules make that condition honest. The first is yours; the other two belong in the brief you just wrote. Never wait on a path that could already exist**: the agent names are constants and the fix protocol is to re-brief the SAME `athena-<variant>` that flagged, so a reused path is already there from the previous round — wait on it and the lead reads a review written before the fix landed, then re-reports a finding that is already resolved. Suffixing the round (`/tmp/<slug>-<agent-name>-r2.md`) handles that within one run, but round numbers restart, and a repeated `/do` on one slug (a follow-up PR off the recycled branch) reuses the same slug and the same names — so the rule that actually holds is: **delete the path immediately before you spawn or re-brief**, and only then start waiting. That is one command and it is correct in every case, including the ones a naming scheme misses. **The report is written in ONE shot, as the last thing the agent does** — a file built up by a Write and then two Edits satisfies "exists" at its first byte, which hands the lead a half-written review: exactly the truncated-report failure this whole contract exists to prevent. **And every agent writes its file even when it has nothing to say** — "no blocking findings" is a result, and it is the most common one; if a clean round wrote nothing, a clean round and a dead agent would be the same observation, and the lead would wait on a file that is never coming. **A teammate's final chat message is NOT a delivery channel — what you receive is a contentless `idle (available)` ping — so never close a brief with "your final message is your report"**: three reviewers so briefed each complied exactly, authored complete reports nobody received, and the lead spent five of its nine SendMessages nudging them to author everything a second time; the report is the FILE, and the chat reply is one line naming its path.
- **A review round closes on verdicts, not on your own satisfaction — and the tree holds still while it runs.** This binds every review fan-out, delegated or solo-authored — the solo case is the riskiest, since the lead is then both author and closer. Four rules, each the fix for a measured way a round got closed by something other than the reviewer's judgment of the final tree. (1) From dispatching a review fan-out until every variant's verdict lands, the worktree is FROZEN — yours and the crew's: no edit, and no fix brief out mid-round (one lead made 14 repo edits in the 2 minutes between a round's first and last verdicts, leaving the later verdicts describing a tree that no longer existed and the reviewers silently re-diffing to cope). The freeze ends at the last verdict, at a death you have positively established per the expiry bullet above — then proceed and say which dimension went unreviewed — or at a carl steer that RETIRES the round's subject outright: reviewers finishing full reports on an artifact carl killed six seconds after the round was armed is the measured cost of having no such exit, so when the steer makes the round's subject moot, stop the reviewers, record the round as abandoned-with-reason in `90-build-report.md`, and re-dispatch against what survives (a steer that merely ADDS work does not qualify — fold it after the round closes as before). (2) A verdict is the reviewer's own written CLEAR/BLOCKING in its report file, and you READ that file in full before acting on it: a keyword grep is not reading it (a `grep "STILL-OPEN\|Still open"` missed a verdict spelled `STILL OPEN` and three flagged residuals shipped unfixed, two still in main a day later), an idle notification is not it (idle fires at every turn boundary), and the tail of the file can be the PREVIOUS round's verdict (a lead `tail`'d a review file, read the prior BLOCKING verdict's closing lines, and treated the reviewer as answered). (3) `TaskStop` follows the verdict, never your fix: a reviewer asked to confirm a change is stopped only after its confirmation lands — two reviewers stopped 8 and 19 seconds after being asked to confirm, one with BLOCKING as its last written word, closed a round whose reviewer of record never cleared it, and the pane then told carl "both CLEAR". (4) A post-verdict edit reopens the round for the dimensions it touches, and ONLY those — shared test infra changed after sign-off ships reviewed by nobody, and "0 blocking findings" then describes a tree older than the one that ships. Treat the FIX pass itself as the highest-regression change in the cell and apply each prescribed fix MINIMALLY: in one measured cell the only two blocking findings across six rounds were both regressions the fix passes introduced while applying non-blocking findings — once by restructuring a neighbouring doc comment the fix was never asked to touch, once by applying a reviewer's prescribed markup change verbatim that the reviewer had never rendered (a reviewer that prescribes a RENDERING change measures the rendered result before prescribing it; the tools it needed were available the whole round and reached for only in the confirm pass, after the defect shipped). One carve-out, priced by measurement: applying a reviewer's own NON-BLOCKING text fix — a comment wording, a doc line, anything with no behavioural surface, taken verbatim or trivially — is recorded in `90-build-report.md` and does not reopen, because a reopen per prose nit turns the text dimension into a self-feeding loop (three consecutive style rounds in one cell found only defects the previous fix round's own prose edits had created, at a full re-dispatch each); an edit that touches behaviour, or that rewords a claim in YOUR words rather than the reviewer's, still reopens. The reopened round runs on the settled tree and closes when its re-run returns no blocking finding; record the round count in `90-build-report.md`. The carve-out's escape hatch is the loop arriving as BLOCKING prose: the loop is driven by NEWNESS, not severity — every fix round writes new comments, new comments are new surface for the next comment-accuracy pass, and a cell has run three consecutive BLOCKING rounds each targeting only prose the previous fix round wrote (round 3's reviewer correcting its own round-2 wording), every round individually legitimate. So when a round's only blocking findings are comment claims on prose that fix rounds themselves introduced, the SECOND such round is the last full re-dispatch: after it, apply the reviewer's comment fixes verbatim under the non-blocking carve-out and record the chain in `90-build-report.md` — a third round of dispatching a reviewer against its own previous fix's wording is the self-feeding loop wearing blocking severity. "Verbatim" has one gap the common case falls straight into: a reviewer that NAMES a prose defect without prescribing replacement text ("this sentence now contradicts the Makefile" with no wording offered) leaves nothing to apply verbatim, and by rule (4)'s letter any authored reword reopens. The lead's MINIMAL authored fix to a textless prose finding lands under the same carve-out, quoted into `90-build-report.md` so the reword is auditable — rule (4)'s reword clause governs edits the reviewer never asked for, not the smallest edit that satisfies an ask the reviewer left textless. All four govern phase 2 up to the PR — a post-PR CI or review-comment fix is `pr/SKILL.md`'s business, not a reopen. What you report to carl is the round as it happened: a round that returned blocking findings which were then fixed is reported as exactly that, never as "verified clean".
- **The output-file contract does not survive re-delegation on its own.** An agent that was itself correctly briefed — report path, heredoc fallback, write-nothing-under-the-repo — drops those clauses when it writes a brief for its OWN children, and the grandchild's findings strand in a chat reply or never get written, one hop below everything this section fixed. So any brief that permits its agent to spawn further agents says the contract passes down verbatim — every spawned agent gets its own named output file under the same scratch namespace, and the same repo bar — or forbids re-delegation outright. Naming is part of it: an agent below the lead never passes `name:` on an Agent call — the current harness refuses the parameter below the lead outright ("teammates cannot spawn teammates"), and where an older harness accepted it, the named spawn became the LEAD's teammate, unstoppable by its spawner, its idle notifications landing in the lead's pane unattributed; its children are its own anonymous subagents, or the work goes back to the lead to spawn properly.
- **A single-dimension review brief's numbered checks stay inside its named dimension.** Briefs that say "review one dimension only" and then order the full `go vet`/`gofmt`/test-suite gate "and report the output verbatim" produce three reviewers running three identical suites and the lead reading the same output three times — the fan-out pays for its one distinguishing property, independence of perspective, and then discards it. The suite run is the lead's own verification step (step 6), never a reviewer's checklist item. And a dimension is only as good as the SOURCE its brief hands it: every review brief names the frozen contract by absolute path, and the style/compliance variant additionally gets the repo's CLAUDE.md named the same way — briefed without them, one style reviewer hunted for the contract at paths that don't exist and reviewed comment truthfulness without the one artifact those comments' claims answer to, and another listed CLAUDE.md under "Files read", never opened it (zero reads in the transcript, zero body text in context), and issued compliance verdicts whose only source was the lead's own brief asserting the conclusion — the reviewer verified the lead's premise back to the lead. A compliance finding cites the rule it checked, quoted or by file:line, which is what makes an echo distinguishable from a check. Two variants reporting the SAME defect at different severities is not a wash, either: the round's verdict is the HIGHER one, or the build report records why not — measured, one reviewer's only BLOCKING was its sibling's non-blocking item 2 under an ACCEPT, and the round closed correctly only because the stricter variant happened to be the one that blocked.
- **Every review brief defines the verdict bar in one sentence, verbatim: *BLOCKING means you would not ship the tree as it stands; CLEAR means every remaining item is optional.*** Left undefined, each reviewer invents its own bar and the round-closing machinery keys on a word that means different things per reviewer — two reviewers in one measured round found the IDENTICAL two regressions and filed opposite verdicts, one reasoning that lost feedback was not board-breaking over a defect its own report described as total for an input modality. Severity taste is not the test; shippability is. A finding a reviewer would fix before shipping is BLOCKING however small it looks.
- **A read-only researcher is forbidden the REPO, not the filesystem — and you have to give it a way to write.** An unnamed in-process subagent spawned to explore rather than to change anything is briefed "write nothing under the repo" — never "do not write any files", which reads as a ban on its own report and has stranded a several-hundred-line findings document in a chat message. It gets the same scratch output path every other agent gets. But the wording is only half of it, and the other half is the half that keeps failing: **spawn it with an agent type that actually has `Write`.** `Explore` does not have one — its roster is every tool EXCEPT `Write`/`Edit` — so a brief that says "write your full report to `<path>`" is unsatisfiable by construction, and the agent does not report that as a problem: it rationalises. Observed refusals, each invented independently, all from briefs that used exactly the phrasing above — *"this session runs in enforced read-only mode"*, *"per my read-only constraint"*, *"my configuration prohibits creating files"*, *"no write tools available"*. The lead then waits on a file that is never coming, and 30-40KB of findings arrive as chat instead, or not at all. So: use `general-purpose` (or any type whose roster includes `Write`) for a researcher you expect a report from. For an UNNAMED subagent's report file the heredoc is now the PRIMARY route, not a fallback: the harness refuses an unnamed subagent's `Write` of a report file every time ("Subagents should return findings as text, not write report files" — measured 14 of 14 one night and again the next), so a try-Write-first brief makes it generate the whole report as a doomed payload and re-emit it verbatim (~81K output tokens a night, measured); say *write your report with `cat > <path> <<'EOF'` — your `Write` works for notes but is refused for the report; "read-only" bars the repo, not your own report.* NAMED teammates are the other half and keep `Write` (0 refusals measured): for them the heredoc stays a fallback for a refused `Write` only — briefed wider, half a review fleet shipped reports through heredocs with `Write` working — because a heredoc routes report PROSE through Bash, where a text-matching guardrail hook blocks the whole write when the findings QUOTE a banned command (measured twice in one round; that hazard is why the brief also says: if the heredoc is hook-blocked, report the refusal and stop, never reword the findings to pass).
- **Every teammate runs on Opus** (`model: opus` — Claude Opus 5): the mechanical component tasks the set already pins down as much as the judgment-heavy ones (ambiguous integration points, cross-cutting refactors, design gaps the set left open). Never drop a teammate to sonnet or haiku to save tokens, and never leave the model unset. The LEAD's own tier is a separate axis and never an argument for lowering a teammate's — your brief states yours, and it is not necessarily your crew's; a lead deliberately placed on a faster tier is placed there precisely because the deep work is the part it delegates.

### 5. Implement

- **Where the per-component test plans go depends on whether you delegated.** When you did, `50-components.md`'s unit/integration/e2e plans are the **test authors'** brief input rather than the implementer's checklist — they went into the test authors' briefs in step 4, and what the implementer is held to is `50-contract.md`. **When you implement a slice yourself — including every `solo: true` job — you write its tests from those plans, exactly as before**, because there is no author to write them and an un-delegated slice must not ship untested. On a repeat `/do` for a slug that delegated last time, earlier rounds' blind tests are still in the repo and still asserting — a follow-up is usually small enough to keep for yourself, which is exactly when this is easy to miss — so re-cover what they pin or delete the ones the change deliberately obsoletes, never leave them failing — "deliberately" is the word doing the work, since without it this reads as permission to delete any test your change happens to break; note in the build report that authorship was not split for it, since you were both parties and the separation the split buys is simply absent.
- Match the project's existing conventions; do not introduce new abstractions the set did not call for.
- **A steering item phrased as a question gets an answer, never an implementation.** "when a new run happens, the current one kills itself right?" is a request for a yes/no, even sitting numbered between two build items — one cell answered "yes, already true" and then ALSO built a rendering feature the question implied, which absorbed most of two review rounds and produced both of the window's blocking findings, billed back as one of "your items". Answer it in your reply; if the honest answer implies work worth doing, name it as an offer and build it only when carl converts it into an ask.
- **A destructive command runs ALONE, in its own call, after you re-read it — never inside a compound, and never with its stderr silenced.** Destructive means anything that removes or overwrites state you did not just create: `rm`/`rmdir`, `find … -delete`, `git checkout/restore -- <path>`, and every `--apply`/`--write`/`--prod` invocation of a mutating script. Two measured shapes, both caught only by luck: a `find .codex/… -name "*.py" -delete` bundled into a six-clause cleanup compound deleted 15 TRACKED files it could not distinguish from generated ones (surfaced only because a `git status` happened to be bundled into the NEXT command), and a 400K-row production `--apply` ran behind a typo'd `cd … 2>/dev/null;` whose silenced failure meant the script path resolved by pure chance. A `find -delete` also needs its match list printed first (`find … -print`) in a separate call — `find` cannot tell tracked from generated, so you look before it deletes.
- **Edit repo files with the Edit tool, never through Bash — the ban is the ROUTE, not one idiom.** A python heredoc's `read_text()/str.replace()/write_text()`, `sed -i`, `perl -pi`/`-0pi`, an `awk > tmp && mv` — every Bash-route in-place rewrite of a repo file is the same banned move, because agents pattern-match the named example and read the unnamed twin as permitted: briefed with the python shape alone, two implementers in one cell reached for `perl -0pi` twenty-seven seconds apart, and a lead used `sed -i` four times the same night. The Bash route fails SILENTLY: an `assert old in t` that dies mid-script leaves the file unwritten while the compound command goes on to print your own hand-written "applied" banner and a test suite run green against the UNMODIFIED file — measured twice in one session, `is_error: false` both times, four review fixes reported landed with zero landed. `Edit` fails the turn loudly when its `old_string` no longer matches, which is the whole difference. **This ban goes into every implementation brief verbatim**, exactly as the shell line above does: it lives in a section only the lead reads, leads faithfully forward the zsh clause and drop this one, and the crew then uses the banned idiom on repo files — measured across two cells in one night: four of seven agents in one (a rewrite whose replacement matched ZERO times printed `A 0 B 1 C 1`, wrote the file anyway, exited 0), and an implementer in the other made nine Bash-route mutations minutes after its own lead had spent 106K tokens replaying transcripts precisely because Bash-route edits are what a naive Write/Edit replay cannot see. And "repo files" means any git checkout, scratch worktrees included: a lead that used Edit for all 41 worktree edits switched wholesale to `read_text()/replace()/write_text()` the moment it started a second PR in a scratch baseline — the ban reads as a property of the cell worktree, and it is a property of the idiom. The verbatim-in-brief requirement covers **every brief whose agent writes a repo file — blind test authors included, not "implementation briefs"**: in one cell the two implementer briefs spelled the banned shapes out and produced zero violations, while the two author briefs compressed to the abstract rule and one author used the python-heredoc idiom on its own test file the same hour. One caveat on `Edit` itself, because this bullet sells it as the loud-failure route: **that guarantee does not cover deletions.** A `replace_all` whose `new_string` is empty has no anchor and no failure mode — deleting a token always "succeeds" — and one such edit consumed the newlines around seven match sites, splicing adjacent lines into syntax errors that only a same-turn lint caught. A delete-a-token edit carries surrounding context in both strings (`"  # noqa: E402\n"` → `"\n"`), or runs one site at a time.
- Mark each TaskCreate task complete as soon as it is done.
- **A comment may assert a fact about anything outside itself only if you checked it in this session.** Not "it is probably true", not "it reads like the sort of thing that would be true" — you ran the `grep`, the `git show`, the test, in the same turn you wrote the sentence. This is the single most expensive habit the review round catches, and it is a habit of the *comment*, not the code: in one job 25 of ~32 blocking findings across six review rounds were comments asserting something false, usually written minutes earlier, while the code they described was fine. The lead's own summary: *"nearly every finding across six rounds has been a comment asserting something false … The code has been fine."* Actual examples, each caught in review: a claim that tmux is "a sheet action here" on iOS, where the app has no tmux action at all; a stated fact about how `ViewThatFits` picks a branch, given as the justification for hand-writing a `Layout`, which was backwards; three claims in one CSS comment about which rules a class carries, true of a sibling class and not that one. **Two things make this specific rather than a plea for care.** First, the repo's house voice is the cause: comments here explain WHY, including what a thing replaced and what broke before, and an agent imitating that voice with no access to the history will *generate* the history — the style is load-bearing and stays, so the evidence rule is what has to carry the weight. Second, a fix in the same round can *make* a neighbouring comment false, so re-read the comments around every line you change, not just the ones you wrote. If you cannot check a claim, describe what the code does and stop there; a comment that explains less is free, and one that explains wrongly is read as precedent. One sub-shape is generated by a recognisable trigger rather than by drift: **a comment authored to explain why leftover surface is still there is evidence you reverted half of something.** An implementer that backed out a design change reverted the caller and kept the parameter, then wrote a docstring inventing "an override for a caller that resolves the campaign after building the context" — no such caller existed, and the comment was written in the same turn as the half-revert, specifically to make surviving dead code look intentional. When you back out a design, back out its surface with it; the urge to justify a leftover is the signal to delete it instead.
- **When you create, move or rename code the set CITES, you update the citation in the same change.** The set's artifacts link into the repo — `path:line` tokens in the mds (`51-code-map.md` is nothing but those), and `data-code` attribute values on the already-rendered diagram fragments — and every one of them is a claim about where code lives that your change can silently falsify. A stale citation is worse than none: it opens the wrong file with the reader's full confidence, and nothing in the pipeline re-checks it, because the lead verified each ref once, before hermes was ever briefed. So after the code lands, grep the set root for the paths you touched and fix what moved. The two surfaces take different edits. A `path:line` token in a markdown artifact is an ordinary `Edit`. A `data-code` value on a fragment is an **attribute-only** `Edit` — changing that one string and nothing else is sanctioned for you, and it is the sole exception to "you never write diagram bodies"; report the fragments you touched so the lead re-lints them and re-wraps the affected cards. Anything beyond the attribute value — a box that should now say something different, a component that moved, an edge that no longer exists — is a change to what the diagram DEPICTS and goes back through `hermes-<diagram-id>`, never through your own hand on the markup.
- **When a change retires a meaning — a symbol, a column, a phrase, a rule — grep the whole repo for its remaining references ONCE, before any review round.** Fix the class in one sweep; reviewers surfacing leftover references one at a time is the most expensive possible form of that grep, and one retirement spent four review rounds on instances a single grep would have listed.
- **Pre-fix verification uses an isolated copy, never `git stash`, and a probe file never lands in the worktree.** Verifying that a test fails without the fix means reconstructing the unfixed tree OUTSIDE the shared one: `git show HEAD:<path>` the changed files into a scratch dir, or — when a probe must compile against unexported symbols — stage the probe file in scratch and map it into the package with `go test -overlay` (a JSON file mapping the in-package path to the scratch copy). Never `git stash` in a worktree other agents share: it sweeps their uncommitted work, and it is a twice-recorded destructive incident in this setup. And never write a probe into the shared package "briefly": two agents' probes have collided in one package while the suite ran over the same tree, and `git status` cannot distinguish never-written from written-and-deleted, so the agents' own "worktree left clean" reports were false. For a whole-suite baseline — proving failures pre-existing rather than asserting it — the clean form is a throwaway `git worktree add` at pristine HEAD with the cell's venv symlinked in, run, compared, removed: measured working, and it never touches the shared tree. **This bullet's rules go into every implementer brief verbatim, exactly as the dialect line and the Edit-tool ban do**: stated only here, they reach the lead and nobody else — three implementers in one cell each invented a baseline method from scratch, one landing on the sanctioned worktree, one on a literal `git stash` in the shared tree, and one on seven throwaway probe files written into the shared package that the lead never learned existed. The brief line: *never `git stash` (mutating forms are hook-blocked in cells); never write a probe or scratch file into the repo; baseline via `git show HEAD:<path>` into scratch or a throwaway `git worktree add`.*
- **Never write an incident history for something that never happened.** A defect caught in review, in an uncommitted tree, has no incident. One job wrote *"shipped for 69 archived jobs"* into a test comment for a bug that was caught pre-commit; the next maintainer would have read it as a post-mortem of a real outage and cited it. Say what the guard prevents, not a story about the time it didn't.

### 6. Verify Against The Set

- Run `52-testing-plan.md`'s checks that are practical locally (unit tests, type checks, targeted integration tests).
- **Your verification gate is the CI command, over the CI scope, on the CI merge base.** Every axis you narrow is an axis CI fails on after the PR opens: a targeted file list instead of the package (measured biting three times in one cell), a type check that skips the test files, a suite run against the cell branch's stale base instead of latest main — five distinct narrow-scope misses in one job, each on a different axis, so no single habit covers them. Run what CI runs, from where CI runs it. And when a gate that was green all build goes red at PR time, **re-run the exact known-good invocation — environment variables included — before dismissing the failures as environmental.** A lead ran the same pyright binary its implementer had run six times clean, without the `PYTHONPATH` prefix that made it clean, got 47 import errors, and shipped calling them "env noise": the label was right about the cause and wrong about the conclusion, and the type gate never actually ran on the merged tree. The known-good argv was sitting verbatim in the teammate's own reports; the lead's verification gate deserves the same run-the-exact-command rule the join already forces on briefs.
- **Never filter a suite's output through `head`.** `go test ./... | grep -v "^ok" | head -5` reported GREEN over a red suite: the five-line window filled with benign log noise and the `FAIL` line fell outside it — and a package is noisy exactly when something is wrong, so the truncation inverts the answer precisely when it matters (cost: a review round dispatched as "fixed and frozen" that both reviewers returned BLOCKING on the red tree). Use the count form (`… 2>&1 | grep -cv "^ok"` — a count cannot truncate; a non-zero count is the signal to read the FULL output, since test-free packages and stray log lines count too) or read the full output directly.
- For UI changes, drive the feature in a browser before reporting done — and drive it: click, type, navigate every surface the change touches, and say which interactions you performed. A page that renders is not a feature that works, and "I loaded it" satisfies the letter of this step while establishing nothing.
- **A taste-gated change goes in front of carl BEFORE the review fan-out.** When the acceptance criterion is how it looks, sounds or feels — cursor art, a colour, a sound kit, anything carl phrased "let's try" — the deciding input is his eyes, and a review round run first is paid for on an artifact he may retire on sight: four cells in one night ran the full pipeline (implement → gate → review rounds → pins) on visual changes carl then reversed or retired at first look, one ending byte-identical to where it started, and in two of them carl reached for the surface himself, asking mid-run for a running instance, because the pipeline had no step that showed him. Drive it, put the URL or screenshot in front of him at the manual-test gate's early form, and dispatch the review on whatever survives his look. The review still runs — after the taste decision, not before it.
- **Browser mechanics, so you do not rediscover them.** Drive only the surfaces your change touches, and never a destructive one against live state — the kraken dev board proxies to the real `kraken serve` and the real `kraken.db`, so Done, Archive, Stop, Reactivate and Update act on other people's live jobs; exercise those against a job you made for the test, or read-only (open the confirm, do not confirm), and say under Verification what you could not drive safely. Browser work is the LEAD's step and singular: the MCP server drives one browser with one profile, so two agents doing it at once interleave on the same tab and read as flaky UI. Use the `playwright` tools, not `claude-in-chrome` — that one drives carl's own Chrome through an extension whose per-site permission nobody is present to grant — and load them in one `ToolSearch` call. (`/aim` and `/info` say "there is no browser in a cell"; that is about `open` launching carl's desktop browser with nobody watching, not about this one.) Two refusals are worth knowing before you hit them, because the workaround for each is a line. **`file:` URLs are blocked** — `browser_navigate` refuses the scheme outright, so serve the directory instead: `python3 -u -m http.server 0 --bind 127.0.0.1 --directory <dir>` under `run_in_background: true`, and READ BACK the port it prints (`Serving HTTP on 127.0.0.1 port 54321`) — a fixed port that is already taken dies with `Address already in use`, which backgrounded is invisible, and you then verify whatever another cell is serving. The `-u` is load-bearing rather than decoration: without it CPython block-buffers stdout when it is not a TTY, so with an ephemeral port the one line that tells you the port never reaches the log at all. **A screenshot may only be written inside the worktree** — the allowed roots are the worktree and its `.playwright-mcp/`, so `/tmp`, your scratchpad and `<cellDir>/artifacts/` (a sibling of the worktree, not under it) are all refused. Omit `filename` and the shot lands in `.playwright-mcp/` on its own; the tool result names the path it wrote, so copy from that rather than assuming it. `.playwright-mcp/` is gitignored in kraken but not in most repos a cell targets — copy out what carl should see, then `git check-ignore -q .playwright-mcp/ || rm -rf .playwright-mcp/` before the PR step — `check-ignore` exits 1 when the path is NOT ignored, so that one line is the whole guard and is a no-op in the repos that do ignore it. Do not add it to the target repo's `.gitignore` (that is a change to the repo, not to your change), and never write `.git/info/exclude` — in a worktree that resolves to the shared common dir and edits carl's main checkout.
- If a check is not runnable locally, say so explicitly.

### 7. Write The Build Report

Always write **one brief artifact** recording what actually happened: `90-build-report.md` in the
set root (in a kraken cell: `<cellDir>/artifacts/90-build-report.md`). Like every md artifact, it opens with a one-liner stating its main message — the headline delta between plan and reality, or "shipped as planned" when that is the truth — before any section, so a reader who stops there still has the point. Never hard-wrap its prose: one paragraph — and one bullet, and one table row — is ONE source line, however long; a mid-sentence line break renders as a broken paragraph on the board, and it is a repeat complaint from carl. The `90` band sorts it last,
after the overview, the cards, and the section docs. Write it even when the implementation went
exactly to plan, and even when there was no `/aim` set to begin with (a job spec implemented
directly is still a plan reality can diverge from).

Keep it to a page. It is a record of the *delta between plan and reality*, not a second copy of the
set — link to `00-overview.md` rather than restating it. Sections, in order:

| Section | Content |
|---|---|
| What shipped | One row/bullet per component or slice, each naming the files it landed in. Terse. |
| The join | How many blind tests were authored, how many failed on the first run, and the verdict for each (code bug / test bug / contract defect). Zero failures is a finding, not a clean bill — say so. **The row states WHO authored the tests** — the blind authors, or "no delegation: the lead wrote both halves" — because a round with no blind tests at all looks exactly like success (every gate green, the review still fans out), and `authored: 0` alone reads like a filled-in row rather than the absence of the split. When nothing was delegated, that one line is the content; never drop the row. |
| Discrepancies vs. the plan | **The point of this artifact.** Every place reality diverged from the set (or the job spec): what the plan said, what you did instead, and why. Wrong assumption in the spec, an API that doesn't work as described, a component that turned out unnecessary, a boundary drawn in the wrong place — all of it. If nothing diverged, write "None" as an explicit line; never omit the section. |
| Artifacts invalidated | Every phase-1 artifact the implementation CONTRADICTED — a diagram card still depicting a design this phase deleted, an overview claim the code now falsifies — with what each now claims wrongly. The flat set makes every card independently shareable, which is exactly what makes a stale one dangerous, and the most expensive artifacts (rendered diagrams) are the ones a reversal is most tempting to leave un-retouched: a measured design inversion left two diagram cards depicting the discarded half, listed as current in the overview, with the build report's own Discrepancies section describing the inversion and never naming them. Re-check the diagram cards' claims against the shipped design before writing this row; "None" spelled out when the set survived intact. |
| Complications | What fought back and how it was resolved or worked around — flaky/blocked tests, missing fixtures, ordering constraints, an unrelated bug hit on the way. Include ones you resolved; they are the cheap warning for the next person. |
| Deferred | Scope deliberately left out, each with the reason and what it would take. Includes P1/P2 questions that stayed open. **Each row is self-contained — never a bare finding ID.** Review reports live in `/tmp` and evaporate; a Deferred row reading "review residuals R2-5/R7, N4" dereferences to nothing once they do, and ~50 optional findings have gone unrecoverable exactly this way. Quote what each deferred item IS in the row itself, or copy the accepted-but-deferred findings into the set root, which outlives the machine's tmp sweep. |
| Verification | What was actually run and its result, plus anything that could not be run locally. |

Uncomfortable findings belong here in plain words: a spec section that turned out wrong, a
decision that made the implementation awkward, an estimate that was off. A build report that reads
like the plan was perfect is a report that isn't worth writing.

Two truthfulness rules, both from measured failures, because this is the one artifact NO review round covers — the athenas review the code diff, the report is written after they are torn down, and a false claim in it is read by carl and by every later job as fact. First, every factual claim in it gets the same evidence bar as a code comment: checked this session, in the raw, not recalled — a report has claimed the manual-test gate verified things it did not, and understated limit stalls its own transcript records. Second, when anything changes after the report is first written — a revert, a late steer, a fix round — re-READ the whole report and correct it as a document, never by grepping it for sentences that mention the changed thing: a post-revert patch pass that hunted the narrative for cursor sentences fixed six sections and missed the one bullet stating what the shipped tests assert, which still says the reverted behaviour today.

### 9. Clean Up Agents

Stop each agent as soon as its output is ACCEPTED — an implementation slice once the join has produced no `code bug` against it **and** the review round has cleared it, not the moment it reports done, since a blocking finding has to go back to that same teammate. Both gates come after the barrier, which fires only when the LAST slice reports; a slice stopped before then leaves nothing to send an early `code bug` back to. By the time verification passes and the report is written, tear down anything still resident:

- **Teammates (named `Agent` spawns)**: stop each still-running teammate with `TaskStop`, addressing it by its bare name (or `name@team` if the name is ambiguous across teams). That releases its tmux pane. There is no team-delete step — a team with no live members is already gone.
- **Unnamed background subagents / tasks (Agent, Workflow)**: stop any that are no longer needed with `TaskStop`, addressing them by task id — the id from the spawn result, or from the task notification one fires when it stops. **`TaskList` cannot see a background agent**, and this is measured rather than argued — called with thirteen unnamed scouts live, it answered `No tasks found`. It lists the `TaskCreate` plan board, which is a different thing that happens to share the word (the same reason step 4 says it cannot tell a dead agent from a slow one). Nor are the stop notifications a reliable inventory on their own: an agent that dies mid-answer may never fire one, and an unnamed subagent has no pane, so the `k ls` fallback step 4 leans on does not apply to it either. So **write the ids down as you spawn** — in your scratch dir, not only in context, which a compaction or a resumed session will not preserve. Nothing anywhere will re-derive them for you.
- **Armed watches are residents too.** A background until-loop or Monitor watch that was waiting on a round outlives it silently — stop it when the round it watched closes, alongside the agents it watched. An orphaned watch's late "stopped, no completion record" notice is not free: notifications queue indefinitely, and one flushed sixteen hours later into a session whose cache had long expired, costing a full ~930K-token context re-cache to say "no action". The watch ids are background task ids like any other: write them down as you arm them, same rule as the spawn ids above.
- Do this even when implementation failed or was cut short — a partial run must not leave orphaned agents behind.
- Exception: if a teammate is mid-way through work the user explicitly asked to keep running (e.g. a long verification job), say so in the report instead of killing it.

## Inside A Kraken Cell

When a kraken job brief sends you here, these deltas apply — the brief wins wherever it is more specific, and it is the only place the cell's real paths appear:

- **There may be no artifact set at all.** Skipping the doc phase is a kraken job's default: when Phase 1 never ran, the JOB SPEC is the contract and it is what you implement, exactly as written. The Preconditions refusal above applies to standalone `/do`, not here — a cell with no set root is the normal case, not an error.
- **The crew is the brief's crew, and the crew are TEAMMATES.** Implementation slices go to teammates named hephaestus — which write no tests for the spec — with athena-logic and athena-edge authoring those tests blind from `50-contract.md` and athena-style joining them for the three-dimension review. The brief owns that contract end to end — what makes an agent a teammate, when delegating is worth it at all, when an agent is torn down, and the solo case — so read it there rather than re-deriving it here; this bullet exists only to say that /do's generic fan-out guidance above is superseded by it inside a cell. What the brief does NOT carry is the output-file contract above: every hephaestus and athena brief still names its agent's scratch report path, and you still wait on that file rather than on a sleep — in a cell the lead's own pane is the channel carl reads, so a review that exists only as a truncated chat reply is lost to both of you.

## Boundaries

- /do is for implementing an existing doc, not for re-spec'ing. If the user wants scope changes mid-implementation, update the doc first (or hand back to [[aim]]) before continuing to code.
- /do does not create branches, commits, or PRs unless the user asks. Follow repo git conventions (or a personal `git` skill, if one exists in this session) for branches and commits, and use [[pr]] for PRs.
- If the doc is in explain mode (describes an existing system), /do should generally do nothing — explain docs document current state, not future work. Confirm with the user before treating an explain doc as an implementation target.
