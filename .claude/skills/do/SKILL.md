# Do — Implement An Artifact Set

Take the artifact set produced by [[aim]] earlier in this conversation — `00-overview.md`, its diagram cards, and its section docs — and implement it. The set is the source of truth for scope, components, constraints, and testing. Before writing code, resolve any `P0` entries in the set's open-questions record with the user; after the code is verified, write `90-build-report.md` — the brief record of what shipped and where reality diverged from the plan — and open the PR (step 8). Every `/do` ends with a PR, and every revision after it is a commit pushed to that same PR.

## Preconditions

- An `/aim` artifact set must exist for this conversation: a set root directory (standalone: `~/designs/<slug>/`; in a kraken cell: `<cellDir>/artifacts/`) containing `00-overview.md`. The open-questions record is optional and lives outside the set: standalone, a sibling `~/designs/<slug>.questions.yaml`; in a cell, rows in `kraken.db` read with `kraken questions get <slug>`. A missing file or an empty list just means no open questions were raised (an `/info` explanation job never has any by design). Older conversations may instead have a single flattened `~/designs/<slug>.spec.html` / `.explain.html` from the legacy template flow (or `.spec.md` / `.explain.md`) — treat that file itself as the doc in that case.
- If no such artifact exists in this conversation:
  - Do **not** start implementing.
  - Tell the user: "No /aim artifact found in this conversation — run /aim first, then /do."
  - Stop. Do not infer a spec from prior chat messages alone; the artifact set is the contract.

## Workflow

### 1. Locate And Read The Set

- Identify the most recent `/aim` set root mentioned in this conversation (or the explicit path the user passes as an argument).
- Read `00-overview.md` in full, then every `.md` file in the set root other than `00-overview.md` in full (covers `5N-*.md` and any `6N+` section docs), then the open-questions record in full (standalone: `questions.yaml` if it exists; in a cell: `kraken questions get <slug>`). The set is the source of truth — do not rely on chat memory of what it said. (Diagram cards are supporting detail; skim captions/titles rather than reading every SVG body.)
- If working from a legacy single-file doc instead, read it in full the same way.
- The open-questions record is OPTIONAL: a missing `questions.yaml` (or an empty `kraken questions get`) means zero open questions for this set — skip straight to implementation (do not refuse or treat it as an error).
- If any section doc this workflow names (`50-components.md`, `51-code-map.md`, `52-testing-plan.md`) — or one referenced elsewhere in the set (e.g. by `51-code-map.md`'s review guide) — is absent, say so explicitly and fall back to `00-overview.md` plus whatever section docs do exist — never invent content to fill the gap. A solo set legitimately has none of the three named docs; that is not an error.

### 2. Resolve P0 Open Questions

- Collect every open-questions entry with `importance: P0` and no answer yet.
- Unresolved P0s block the build exactly as a mid-build question round does (step 5): run `kraken load set` for the spec-gate state, end your message with `questions pending: <P0 qids> (P0) · also <open P1/P2 qids, or none> · <what the answers decide> · answer on the board, then tell me to continue`, and end the turn — never `AskUserQuestion`: the board renders it as single-digit buttons that cannot carry a free-text answer. The release is {{operator}}'s next prompt (step 5's resume rule). Outside a cell, where there is no board, ask them in chat by id instead, grouped.
- An entry that already has an answer (and `answered-at`) is a **decision, not a question** — never re-ask it; treat the answer as settled and cite it if relevant. In a kraken cell those two fields arrive as silent row updates from {{operator}} answering on the board, never as pane messages — re-run `kraken questions get <slug>` before this step to pick up anything answered since the set was last read. Two staleness gates before treating an answer as settled: an answer standing on a question whose TEXT you rewrote after it was given is an answer to the OLD question (`questions update` upserts by qid under the standing answer, and nothing marks it stale), and an answer older than a later pane steer on the same subject is superseded by the steer — the pane is the newer channel. In both cases the answer is history, not a decision: act on the steer, or re-ask.
- If there are no unresolved P0 entries, skip straight to implementation.
- Do **not** block on P1/P2 questions — state assumptions for those, build on the recommendation, and surface them after implementation; mid-build, a new P1/P2 is filed in a question round (step 5) rather than carried silently to the gate.

### 3. Record Newly Resolved Decisions

- After P0 answers come in outside a cell (where there's no board to append `answer`/`answered-at` for you), edit `questions.yaml` yourself: remove the resolved entry and note the decision in the relevant section doc (an `Assumptions`/`Decisions` note) instead. Leave P1/P2 entries untouched.
- In a kraken cell, never write `answer`/`answered-at` yourself — that's kraken's job once {{operator}} answers from the board.

### 4. Plan The Implementation

- Build a TaskCreate plan grouped by `50-components.md`'s component table. One task per component is a good default — that is the planning unit, not automatically a delegation unit (see the fan-out rule below).
- Honor the set's scope/non-goals/constraints section doc(s) strictly — do not expand scope.
- Use `51-code-map.md` (where things live, review guide) as the file-targeting guide. Verify those paths still exist before relying on them.

**The next six bullets apply only when you DELEGATE.** Work you keep for yourself — including every `solo: true` job, where there is no crew at all — skips to step 5, where the un-delegated path has its own instruction. There is no point freezing a contract against yourself.

- **Freeze the contract BEFORE you dispatch anyone — `50-contract.md` in the set root.** Whoever implements a slice must not also be the one who decides what that slice was supposed to do, so the requirement is written down first, by you, and both sides are held to that same text. One table per slice: **symbol · signature · obligations · owner**, where obligations are the behavioural claims the slice must satisfy, one short line each ("bumps NEITHER `rev` NOR `updated_at`", "both numbers or neither — a half estimate is refused"). It is symbol-level rather than conceptual — name `tokenGroup.commit` as readily as `core.SumTokensDelta` — but the symbol must be one the test file can actually reach, and that differs by language. Go and Python tests reach unexported names in their own package, and Swift reaches `internal` through `@testable import` (this repo sets `ENABLE_TESTABILITY` and every file in `ios/KrakenTests/` uses it); its real limit is `private`/`fileprivate`, which `@testable` does NOT reach. **TypeScript is the one with no escape hatch at all** — an unexported symbol is unreachable from any other file, test included — so there the export is part of the frozen signature and must be written into it. The test of a good contract is one question — **could someone write a compiling test from this alone, with no access to the implementation?** If not, it is not frozen yet. For Python that question includes the IMPORT SHAPE of any callee an obligation names: `patch()` targets where the name is *looked up*, so whether the caller binds it at module level or imports it inside the function decides the patch target. State it beside the obligation that names the callee, or in a note under that slice's table (along with any harness fixture quirk a mock-based suite will hit with it). Two more checks before the freeze. A contract that states concrete expected VALUES — a match table, a lookup matrix — has those values EXECUTED against the stated fixture before it freezes: a table derived by reading is a hypothesis, and labelling unexecuted values as "the ones a naive implementation gets wrong" invites the implementer to bend the code until the table passes. And a matcher or formatter whose input CONCATENATES fields gets at least one fixture where those fields collide (equal, overlapping, one containing another) — fixtures where every entity's fields are distinct are exactly the case where a doubled-field bug cannot appear. A contract line about the test ENVIRONMENT ("in tests there is no `OPENAI_API_KEY`") is a hypothesis like the value tables, and briefs copy it forward as fact — so write environment obligations as ISOLATION requirements the test must enforce ("the test isolates HOME and the key"), never as descriptions of what the environment supposedly holds. Write it even when Phase 1 never ran and the job spec is one paragraph; that is the case that needs it most. You own amendments; a teammate never edits it. **On a repeat `/do` for the same slug** — a follow-up PR off the recycled branch — earlier rounds' blind tests are still in the repo and still asserting, so the new contract must re-state every obligation they pin, or those tests fail against a contract that no longer claims what they test. Re-cover them, or delete the ones the change deliberately obsoletes; never leave them failing.
- **Dispatch the implementer and the test authors in ONE message.** The implementer gets the contract, its file targets, **no test list** — it implements and never writes a test for the spec (a regression pin for a defect it fixes is fine: the implementer tests bugs, the authors test requirements) — and **an explicit instruction not to read the blind test files before the join has arbitrated them**: an implementer that reads the tests resolves every contract silence to whatever the fixture asserts, and when the contract is then amended to match, the test has defined the requirement. Seeing a compiler diagnostic that quotes a blind test file is not reading it — in Go the blind files share the implementer's package, so its own build output can leak their lines; report the diagnostic, do not open the file. **The implementer's verify-as-you-go commands must EXCLUDE the blind suites too**: a failure's output names the fixture's stubbing, and implementing to that is sighted authorship through the back door. Scope the implementer's own checks to its regression pins and the pre-existing suite; the blind suites run at the JOIN, by the authors, on your signal. **Write that exclusion as a PATTERN, never as a list of exact files, and check that it bites**: an author may split an oversized suite into per-slice files, and an `--ignore` naming the unsplit files then excludes nothing. Where the runner excludes by path glob — pytest, for example; vitest's `--exclude` is the same idea — bind THIS round's blind files, any split form and any helper module included, to one filename prefix in the author briefs, and exclude by it at any depth: `--ignore-glob='test_<subject>_*' --ignore-glob='*/test_<subject>_*'`, quoted. Both globs are needed: pytest resolves a relative glob against the directory it is run from, so a `tests/test_<subject>_*` form run from anywhere else, or over a nested test directory, silently excludes nothing. Choose the prefix so it matches nothing that must keep running: a pre-existing suite, or another subject's files, under it means a different prefix, the implementer's regression pins take a name outside it, and authors put helpers in a prefixed module, never in a shared `conftest.py`. The one thing it may match is an earlier round's blind file for the same subject, which the append rule below sends this round's authors back into; a filename cannot split one file, so that file is left out of the implementer's gate whole and its earlier tests run at the join with the rest. State the no-read ban by the same prefix. Then prove the command before it goes in a brief, with a placeholder — at dispatch no blind file exists yet, so an exclusion with nothing to exclude passes whatever it says. Write a throwaway `test_<subject>_placeholder.py` holding one trivial test into each directory the authors may write to, run the implementer's exact command with `--collect-only -q` once with the two flags and once without, and compare: the only files missing from the flagged run are the placeholders, plus that earlier same-subject file if there is one. A placeholder still collected means the exclusion misses; anything else missing means the prefix is too wide. Delete the placeholders before dispatch. When an author's report names a file outside the prefix, have the author rename it into the prefix rather than widening the pattern, and record in `90-build-report.md` any implementer run that had already collected it. The two-glob form is pytest's. Any other runner needs its own form, proven the same way before the command goes in a brief: a placeholder blind test that the implementer's command demonstrably does not run. In the same message, **one** logic author and **one** edge author for the whole fan-out, however many slices there are — they get the contract, `50-components.md`'s per-component test plans, `52-testing-plan.md` when the doc phase produced one, and an explicit instruction not to read the implementation files. **That no-read clause names the byte routes, not the Read tool** — stated as "reads" plus a file list, agents parse it as a ban on `Read` alone. So the clause says: `grep`/`sed`/`awk` over those files, `git show`/`git diff` of them, and any in-place rewrite of them are all reads — and any accidental contact is DISCLOSED in the report, because an undisclosed graze reads identical to a clean silence. **Concurrency is the mechanism, not a courtesy**: when they start there is nothing to look at, so blindness is a property of the schedule rather than a promise nobody can audit. Split by dimension — logic authors the stated invariants and happy paths, edge authors boundaries, error paths, and refusals. **Both sides' briefs convey the contract by quotation or pointer and add NO expected outcomes of the lead's own**: a brief that pairs each case with its verdict has the authors transcribe the lead's answers instead of deriving assertions from obligations, and a green join built that way certifies the lead's reading rather than the contract. The schedule keeps the authors blind to the CODE; only the brief's restraint keeps them blind to your conclusions. They **author but do not run**: tests written against code that does not exist yet fail for uninteresting reasons, so they report the file written and wait. And the "a contract silence is join evidence, not something to work around" instruction covers EVERY silence, not just a failing import: a tolerant multi-shape probe improvised around an unstated return shape converts the contract gap into a false PASS. Assert one answer, strictly, and let the join arbitrate the failure.
- **Give each author its own test file, and its own identifiers inside it.** File ownership stops an edit race, which is all it stops — two blind authors in one Go package share a declaration space, so both writing `func mkCase(...)` fails the whole package's test binary and takes every unrelated test in it down too. So: prefix every package-level identifier a test file declares with its dimension (`contractMkCase`, `edgeMkCase`). Names, by language, because a blind author cannot check what the runner collects and a file that is silently never collected reports as a pass:

    | | test author's file |
    |---|---|
    | Go | `<subject>_contract_test.go` · `<subject>_edge_test.go` |
    | Python | `test_<subject>_contract.py` · `test_<subject>_edge.py` — and put it where that repo's runner already looks (`testpaths`/`python_files` in `pytest.ini` or `pyproject.toml`, or the paths CI passes), NOT beside the module: the filename matches everywhere, the LOCATION is what decides collection |
    | TypeScript | `<subject>.contract.test.ts` · `<subject>.edge.test.ts` — vitest collects only `*.{test,spec}.*`, so an underscore name is never run |
    | Swift | `<Subject>ContractTests.swift` · `<Subject>EdgeTests.swift` — and regenerate the xcodeproj before the join, or the file sits outside the target |

    If the file already exists from an earlier round, **append — never replace it**. Earlier rounds' blind tests are regression coverage, and reading a test file is not reading the implementation.
- **Signal the run only when EVERY implementation slice is done.** One barrier for the whole fan-out, not per slice: a slice's tests routinely touch a symbol another slice owns, so a per-slice run reports failures that are just the other half of the work missing, and the noise trains everyone to ignore the signal. When the last slice reports, `SendMessage` both authors to run their suite and report results — and the join signal carries **no diagnosis**: a heads-up that pre-classifies a likely failure seeds still-blind authors with the lead's verdict before arbitration, and the table below is then applied to a conclusion it did not produce. If a slice never reports, the barrier never fires — treat it exactly as the expiry case below: find out whether that teammate died, then re-brief it or proceed without it and say which.
- **Then arbitrate every failure, against the contract text — and do this BEFORE any review round.** The order is not stylistic: reviewing means reading the implementation, and an author that has read it cannot un-read it, so every author must finish arbitrating its own tests while still blind. Three verdicts. **Arbitrate one ASSERTION at a time, not one test at a time** — a single test routinely asserts several things at once ("a half pair is refused, nothing is stored, and the response is 400"), and a test whose assertions land on different rows has no verdict as a whole. Take the assertion that actually failed; if more than one did, or if one assertion bundles a stated obligation with an unstated extra, split them and run each through the table on its own. Then start from what the contract SAYS about that assertion — the observability check below is scoped to what that answer turns up, not asked ahead of it:

    | Does the contract… | Verdict | Action |
    |---|---|---|
    | state the obligation the test asserts — including a signature the code drifted from | **code bug** | Fix brief to the implementer |
    | state the opposite, or place that obligation explicitly elsewhere | **test bug** | Fix brief to the authoring agent, quoting the contract line: drop the assertion or move it |
    | say nothing about it, and the answer is not a product decision — the author asserted a requirement nobody set | **test bug** | Fix brief citing the silence. The author may answer once by deriving the assertion from an obligation that IS stated; if it does, that re-classifies as a **code bug** and goes to the implementer. Otherwise the assertion is dropped |
    | say nothing about it, and the answer is a genuine product decision | **contract defect** | A question round (step 5): file the row at the importance step 5 gives it. P1/P2: amend `50-contract.md` to your recommendation, re-brief both sides, keep going. P0: hold the dependent slice and stop on the closing line — the answer, not your default, is what the contract is then amended to |

    **Then one further check, and only on row 1** — where the test asserts exactly what the contract states, so the assertion is right and something else must be wrong: **can that STATED obligation be observed from the symbols the contract names?** If not, or if the test cannot compile against a contract the code did honour, it is a **contract defect**: amend `50-contract.md` to name a symbol that exposes it, re-brief both sides, and re-run. The scoping is the whole of it, in both directions. Ask observability about the *contract's* obligation and it catches a real gap in the frozen surface; ask it about the *test's* assertion and it swallows rows 3 and 4, because an assertion nobody ever specified need not be observable from symbols chosen without it in mind — and the verdict it would hand you is `contract defect`, which writes the author's invention into the contract as a requirement. Keeping it off row 2 matters for the same reason in reverse: there the assertion contradicts the contract and is wrong whether or not anything can observe it, so letting an unobservable obligation re-classify it would leave a wrong assertion red with nobody owning it. If a row-2 contract also turns out to name no reader for its obligation, that is a contract improvement worth making — after the test bug is fixed, not instead of it.

    Every branch ends in an action that makes the suite green or the assertion gone; a verdict that leaves a red test with no owner is not one of them. The row-3 appeal is the corrective for the one judgment here that is genuinely hard — "is the contract silent on this, or does it follow from something it does say?" — and it is what keeps a wrong reading from silently deleting real coverage. Silence otherwise splits by whether anyone could have decided it in advance, and routing it to `contract defect` by reflex writes an invented requirement into the contract, which is the author defining the requirement just as surely as reading the code would be.

    Two compile failures are neither: a **name collision or a missing import** in the test file is a mechanical fix by the owning author, and code that **deviates from a frozen signature** is a `code bug` — read that row first, because a compile failure routed to `contract defect` by default would have you amend the contract to match whatever the implementation happened to do, which is the implementation defining the requirement and is exactly what this arrangement exists to prevent. **Compile-gate the test files FIRST, before either author runs a suite** — blind authors cannot run anything, so mechanical compile errors (an unused variable, a typo) ship as a class, and in Go both authors' files share one package: either one's compile error takes down the package's whole test binary, blocking the OTHER author's run. Route each mechanical error to its owning author as a mechanical fix, not an arbitration. And an author blocked by a sibling's compile error reports it and waits — never blanks the sibling's file out (an overlay mapping it to an empty stub) to get its own suite running: a join reported over half the blind suite is a partial answer wearing a green shape.

    A **fix brief cites the contract obligation, never the failing assertion** — cite the test and the test becomes the requirement. A fix brief to the implementer never authorises a change to a test file: while the authors are still blind, only the authoring agent edits its own file, and only on a `test bug` verdict (after they are sighted, see below). On a `test bug` that author may contest once, but only by quoting a contract line; an appeal that argues without citing the contract is not one. And **never resolve a contract defect by sending an author to read the implementation** — that is the single move that destroys the property, and a blind test that will not compile is the design working (the contract was ambiguous and said so early) rather than failing. The mirror move is equally banned: a contract silence is never resolved by the implementer reading the blind tests to learn the answer — the same collapse run from the other side, and the dispatch bullet above bars the read outright. Re-run the suite after every fix, and cap it: two rounds per failure, then work the contract text directly yourself. **The blind suite stays live for the rest of the job**, not just for this phase — a review-round fix, or any later change, can turn a green blind test red, and when it does it re-enters this same table rather than being edited to fit. Arbitration is one-shot only in the sense that the AUTHORS stop being blind after it; the tests do not stop being the requirement. One thing changes once they are sighted: a `test bug` verdict after that point is **yours to apply** — you drop or correct the assertion yourself, citing the contract — because you are the contract's author and the arbiter of every other verdict, and handing the pen to the agent whose own assertion is in question is what the split exists to prevent.
- **A round where every blind test passes first time has failed, and it looks exactly like success.** It means the contract was written from code that already existed, or the tests were written loose, or someone peeked — or, the fourth cause, the contract specified the MECHANISM at implementation granularity (exact DDL, buffer constants, seek-and-discard steps), so author and implementer shared a mechanically complete oracle and blindness bought nothing a compile check would not; "the contract was written tight" names this cause, and it is a finding about the contract, not absolution — the next contract states obligations at the level of observable behaviour instead. The mechanism cause has a second-order form with no alarm on it: **when the contract also prescribes how the TEST DOUBLE behaves, the double inherits the algorithm's blind spot**, and both blind authors build exactly what they were told, so the join goes green over the very boundary the bug lives in. State the fake's obligations as observable behaviour too, and when a review does catch a defect the suite missed, require the fix's test to PROVE DISCRIMINATION: the previously-broken implementation must fail it, and say so in `90-build-report.md`. The same discount applies per slice: **a green join over a KNOWN contract silence is not evidence about the silent part.** When an author reports pre-run that a slice freezes no symbol for some obligations, put that in writing and hold the dispatch until the contract is amended — a slice with no frozen symbol fails the compiling-test question above and is not dispatchable, and a 0-code-bug join for that slice says nothing about those obligations. **The authors' join reports get the same read-in-full treatment the review bullet below gives verdicts — a keyword grep is not reading them**: the disclosed silences are the only thing that makes a green join interpretable, and each one gets an explicit disposition (amend the contract; pin it at the join — a pin authored by the DISCLOSING author, re-briefed while still blind, since a lead-authored pin is a sighted test and is recorded as one in `90-build-report.md`; or record it there as unpinned).
- Fan components out to teammates — `Agent` calls that each pass a `name`, so each gets its own pane and stays addressable by name — when the work genuinely runs in parallel: components that touch disjoint files and don't depend on each other's output. A change that is one coherent edit, however many files it spans, is faster done directly than briefed out; file count is not the test, independence is. Unnamed in-process subagents are for read-only exploration only — never for an agent that writes a file **into the repo** or judges another agent's output. "Read-only" is about the repo, not the filesystem: a researcher still writes its own report to a scratch path, per the output-file rule below.
- **A teammate starts in YOUR shell's current cwd, not the worktree root — so return the shell to the root before any spawn.** The Bash tool's cwd persists, and an Agent call inherits it: a teammate spawned from a subdirectory resolves "the worktree root" to the wrong directory and files its transcripts under a sibling project dir. **The stakes are the hook envelope, not just paths**: `.claude/settings.json` binds by cwd, so a teammate spawned from a subdirectory runs with NO bash-lint, no recall hook, none of the cell's guardrails. Make the return-to-root a step in the SAME message as the spawn (`cd <worktree root>; pwd` immediately before the Agent calls), not a habit.
- **Every brief names the agent's output file, before that agent starts.** Give each teammate — an implementation slice and each of the three single-dimension review variants alike — one exact scratch path outside the repo (`/tmp/<slug>-<agent-name>.md` is a fine default; never a path inside the worktree, since a report is not part of the change), and tell it plainly: the full findings go in that file, and the chat reply is a one-line pointer to it. The teammate→lead reply channel truncates a long message and is not reliably readable by the lead at all. The **review** briefs need this most: three variants report at once and a findings list is the longest thing any of them writes.
- **A brief conveys a contract obligation by QUOTING the contract line, or citing it by file:line — never by restating it in the slice's language.** A restatement is a second source of truth: two slices' restatements of one shared rule diverge, and the divergence the contract exists to prevent enters one level ABOVE the code, in your own words. An implementer that catches its brief contradicting the contract should trust the contract and say so.
- **The Bash tool is zsh on macOS, and every brief that includes shell work says so.** The abort shapes, each silent: an unquoted glob (`--include=*.py`) dies with `no matches found` — that COMMAND never runs (even a `rm -f`: NOMATCH fires before rm sees the flag) and an `&&` chain stops there, though later `;`-separated commands do still run, so a skimming reader records the abort as "no files match"; any UNQUOTED word beginning with `=` — a bare `===SECTION===`, a plain `echo ===`, a wordless run of `=` — is equals-expanded and kills the compound AFTER printing its first half, leaving only a short `(eval): == not found` tail behind a page of legitimate output. QUOTING is the entire fix — `echo "==="` is safe — and the rule is the mechanism, not the example shape. `path` as a variable name wipes PATH (`fpath` clobbers the function search path the same way). `timeout(1)` does not exist (use a background watch, not a wrapper that kills the verification it wraps) — and `timeout … 2>/dev/null | wc -l` is the worst form, because the `command not found` is swallowed, the pipeline exits through its last stage, and the probe returns a silent FALSE ZERO with `is_error: false` (the bare unpiped form at least exits 127). So: quote every glob, quote any separator that starts with `=` (or open with another character), never leave a `grep`/`sed` that may legitimately match nothing as the LAST command of a `;`-compound — a tail no-match exits 1 with every wanted byte already printed, so the call reads as a failure that wasn't; put it earlier or close with `; true` — and prefer absolute paths — whether cwd persists across calls is HARNESS-DEPENDENT (one shell keeps the previous call's `cd`, another resets to the worktree root between calls), so a relative path is a bet on which behaviour this session has, and nested layouts (`core/core/...`) alias the loss into failures shaped exactly like "this file does not exist". **What goes in a BRIEF is the fixed forms, never the abstract rule**: "quote every glob" does not land, and compressed briefs shed the `timeout`/`path=`/cwd clauses first — so every brief that includes shell work carries this line verbatim rather than a paraphrase: *Shell is zsh on macOS: quote every argument containing `*` `?` `[` `(` — `--include='*.py'`, a bare path glob (`'internal/cmd/*.go'`), a parenthesized API name (`'textselection(_:)'`) all abort the whole command unquoted — write `echo "==="` (quote any word starting with `=`), `timeout N cmd` does not exist (use a background watch), never name a loop/read variable `path` or `fpath` (`while read sid path` wipes PATH for the rest of the run), use absolute paths (an earlier call's `cd` may still be in effect, or the cwd may have reset — a relative path is a bet either way), and never end a `;`-compound with a grep/sed that may match nothing (close with `; true`).* The glob clause is stated as the CHARACTER SET deliberately: a brief that shows only the `--include=` example literally permits a bare path glob and Swift selector syntax, and both abort. The cwd clause is worded around the `cd`, not around "instability": "cwd is not stable" reads as "random, so be careful", and relative paths then work for dozens of calls and break after someone `cd`s, in both directions.
- **A brief that orders a gate run names the exact interpreter or binary path, EVERY round.** A cell worktree has no venv and no node_modules, so `python3 -m pytest` hits `ModuleNotFoundError` and the agent detours into venv archaeology — or builds a throwaway `/tmp` venv and runs the gate against pip-resolved versions, and a gate run in a different dependency set is not the repo's gate however identical its counts. First-round briefs tend to carry the path (`~/Developer/<repo>/<service>/.venv/bin/python -m pytest …`); compressed fix-round briefs shed exactly this clause, so restate it every time. The path must be an ABSOLUTE path to a binary in a venv that EXISTS — never `poetry run <tool>` from a fresh worktree, which does not fail loudly: a venv-less `poetry run` silently CREATES an empty venv and the tool then emits phantom missing-import errors instead of "no environment". Where this collides with the make-target preference below, the tiebreak is: run the command YOURSELF first — a make target that works from the worktree is named as-is, and one that needs a venv the worktree lacks is named with the absolute interpreter substituted in, saying so. A brief that names a command is asserting the command works — same rule as the bullet below. And the BUILD ENVIRONMENT is shared even where file ownership is partitioned: venv creation and removal, dependency installs, and any other toolchain mutation belong to you or to ONE named agent, stated in every brief — two teammates with disjoint file lists can otherwise rebuild the same `.venv` in opposite directions, each correct in isolation. And when the repo has a make target for the gate, name THAT (`make lint-check`) rather than hand-expanding it: a hand expansion drops the flags the Makefile passes, and a false "clean" then reaches the build report before CI fails on it.
- **A brief may only assert what you checked this session — same rule as a code comment, and it is broken most often in briefs.** Step 5 already forbids a comment that claims something you did not verify; the same sentence in a BRIEF is worse, because the agent has no way to check it and every reason to trust it. Two shapes to watch. A number lifted from a counter or a tool schema is a HYPOTHESIS, so write it as one ("the digest reports X; verify before building on it"). And an anomaly goes over as a QUESTION, not a claim: "say what that shape means" gets you the real cause, "confirm that X" gets you X. This bites hardest in a fix-round brief, whose justification text is often written straight into the repo — a false fact there ships unless a reviewer happens to measure it. **A command line in a brief is a fact like any other: run it first, or label it unverified.** `xcodebuild … -only-testing:` takes `Target/ClassName`, and this skill's own filename + identifier-prefix rules GUARANTEE the class names differ from the file name — so `-only-testing:KrakenTests/<FileName>` can never match; name the classes, not the file. (`/aim` already holds itself to this: hermes gets the lint command "with its flags already filled in".)
- **Then wait on that file existing, not on a guessed duration.** The output file appearing is the real completion condition — wait for it, then read it; do not treat the chat reply as the report. Never sleep a guessed number of seconds hoping the work is in by then: a guess is either dead time or a read of a report that isn't written yet.
- **How to wait: ONE background until-loop over every report path — then end your turn.** A hand-rolled poll burns a turn per check, and a blind `sleep` is refused: a standalone long sleep, or one that OPENS a compound command, comes back `Blocked: standalone sleep …`. (Put anything in front of it and it runs — that is a gap in the check, not permission. The rule stands on the argument above it: a guess is either dead time or a premature read.) The refusal names both affordances — `Monitor` with an until-loop, and `Bash` with `run_in_background: true` — and a sleep INSIDE the loop is the sanctioned form, not the banned one. The ban extends to BRIEFS you write: "re-check once after a few minutes" in a teammate's instructions induces the exact guessed-duration sleep this bullet forbids, owned by an agent the rule never reaches. Give the teammate the CONDITION to re-check on ("when the edit lands", "when the report file exists"), never a duration.
    - **Fetch the tools first, in one call.** `Monitor`, `SendMessage` and `TaskStop` are all DEFERRED, absent from the default roster. `ToolSearch("select:Monitor,SendMessage,TaskStop")` at the top of the fan-out, before you need any of them. `SendMessage` is how a fix round reaches the same teammate; `TaskStop` is Clean Up Agents below. `TaskList` is deliberately NOT in that list — it answers neither question this step or that one asks of it, and the reasons are below and in Clean Up Agents.
    - **Wait for the whole fan-out in one watch, not one per agent.** `until [ -s a ] && [ -s b ] && [ -s c ]; do sleep 15; done; echo READY` — three review variants report at once, and three separate watches wake you on the FIRST arrival, which reads as the round being complete when two thirds of it is missing. One conjunctive watch gives one wake, and its expiry means "at least one is missing", which is the diagnostic you actually want. That reason bounds the rule: wait for the whole set when you need the whole set before you can act, which is always true of a review round. If the slices are independent and you would act on each arrival, wake per arrival — but `echo READY <path>` so an arrival is never mistaken for the round. Use `-s`, not `-f`: `-f` is true at byte zero, and the heredoc fallback in the read-only-researcher bullet below creates the file before it fills it.
    - **Pick either affordance; write the call out — but inside a cell, wait with `Monitor`.** Both work — `Bash` with `run_in_background: true` is the harness's own recommendation for a single notification, and `Monitor` gives you an event stream you can widen. The difference a cell sees is on the BOARD, not in the harness: kraken's roll call lets a Monitor watch VOTE the cell working, while a background shell ABSTAINS (a shell may be a dev server left running at the manual-test gate, which IS a block), so a zeus that ends its turn on a background until-loop reads BLOCKED for the whole wait, with the blocked notification sent once per wait turn. Keep `run_in_background` for a run whose end you act on in the same turn; a wait that ends your turn is a `Monitor`. One more thing the board sees: kraken's task ledger (`scanTasks`, internal/core/tasks.go) closes a Monitor on its FIRST notification, event or exit alike, so a watch that ends your turn prints exactly once, at the end (`echo READY`), and a per-arrival watch (`echo READY <path>` per report) must be re-armed after each event it delivers or the card reads blocked from the first arrival on. `description`, `timeout_ms` and `persistent` are all REQUIRED alongside `command`, and the `timeout_ms` default is only 5 minutes — shorter than most review rounds — so never leave it unset: `Monitor({command: 'until [ -s a ] && [ -s b ]; do sleep 15; done; echo READY', description: 'athena r1 reports', timeout_ms: 1800000, persistent: false})`. Never `persistent: true`: it ignores `timeout_ms`, and the expiry is the signal.
    - **Then end the turn.** Neither affordance blocks — both return immediately and wake you when the loop exits — so do not read the report in the turn you armed the watch; there is nothing there yet. The loop's condition must be the REAL one, the report paths themselves; a loop on a sentinel that cannot exist (`until [ -f /tmp/never-exists ]`) is the blocked sleep again wearing the shape of the fix, and it burns the whole timeout while telling you nothing.
    - **`ScheduleWakeup` is not a third affordance — never arm it as a belt-and-braces heartbeat.** Its wake payload is a generic autonomous-loop brief whose stated goal ("get the PR ready to merge", commit-and-push guidance) contradicts the cell's stop-gates, so the tick arrives carrying a different job contract into a cell that is correctly parked, and it adds no wake the armed watch and the daemon's bumps do not already deliver. The two affordances above plus the daemon's own bumps are the only wake sources a cell needs; if a heartbeat is already armed, `ScheduleWakeup({stop: true})` ends it — "armed" meaning you have positive evidence one exists: you armed it this session, or a tick actually arrived. Absent that evidence the stop is not a precaution to take, and it is never one to repeat: an answer saying there was no pending wakeup to cancel means there was nothing to stop and never will be until something arms one, so never call it again on that answer.
    - **Treat expiry as news, and check the PANE.** An agent can die having written nothing — an output ceiling hit mid-answer is one way — so "the file has not appeared" has two meanings, and a watch that only re-arms cannot tell them apart. On expiry, `ls` the paths to see which are missing, then look at those agents' panes with `kraken ls`: it maps each pane to the agent's NAME and status, which is the whole question, and a teammate IS a pane — its absence is the only positive evidence of death. Two mechanics of that probe: spell it `kraken ls`, never `k` — a repo's own guardrail hook can block `k` as a kubectl alias and kills the WHOLE compound it appears in, so a bundled probe's silence is indistinguishable from a negative result; and run the probe as its own command, bundled with nothing a guardrail might refuse. A nudge to a silent teammate needs positive evidence of death first, and always carries "if you already delivered, reply with the report path — do NOT re-do the work": a nudge that lands after delivery makes a reviewer rewrite a finished review against a tree that has moved, so the file on disk and the review the lead acted on are different documents. (Order matters: a finished teammate's pane is gone too, so it is missing report PLUS missing pane that means died. Raw `tmux list-panes -a` is a weak fallback for when `kraken` is unavailable — a teammate's pane title is its agent TYPE, not its name, so three athenas are three identical rows: it can tell you how many are alive, never which.) `TaskList` cannot answer this — it lists the `TaskCreate` plan board, whose status is self-reported, so an agent that died mid-answer leaves a task reading `in_progress` forever. Then either re-brief them or proceed without them and say which. Four reachability facts bound what that probe may conclude. **An `idle (available)` notification is neither a completion signal nor a probe trigger** — idle fires at every turn boundary, the armed watch already covers the report paths, and probing the paths on an idle ping RACES the very write it is checking for. When an idle ping arrives and the watch has not fired, say nothing and end the turn; a nudge is only ever earned by the watch EXPIRING, and it asks ("if you already delivered, reply with the path"), never asserts. **Check a notification's own timestamp against your dispatch time before acting on it**: a reused teammate name can deliver a queued ping from a PREVIOUS run of that name, and `TaskStop` does not cancel a stopped teammate's pending ping — it arrives on your next idle edge, and its text becomes your visible last words. **A live pane showing `question` in `kraken ls` may be sitting on Claude Code's session-limit modal.** Inbound SendMessages are QUEUED behind it, not lost, and dismissing it (`tmux send-keys -t <pane> Enter`) releases that whole backlog into a window that is still exhausted, where each message dies on a rate-limit reply. The modal exists BECAUSE the window ran out, so dismissal is the move AFTER the window has reset or an account swap has landed, never a fix for the limit itself — and since the backlog it releases is stale briefs, follow the dismissal with one message saying which of the queued asks still stand. **And `TaskStop` is terminal**: a stopped name is unreachable, not idle — a send to it bounces — so work discovered after acceptance (an answered question changing a label on an accepted artifact) goes to a FRESH spawn with a Read-then-Edit brief, which is a reason to hold acceptance until nothing pending can still change the artifact.
    - **Waiting quietly is safe — but that cover is the TEAMMATE's, not the wait's.** Inside a cell the working/blocked roll-call counts the teammate's own live pane, not just yours (`cellActive`, internal/jobs/status.go), so while a teammate is actually running the board reads the job as working however silent you are — and when the teammate dies the cell falls to blocked and the daemon flags it, so going quiet is the safer failure too. A spin loop to look busy is pure spend. But a watch armed on a long build or test run with NO teammate alive has nothing to vote for it: the cell reads blocked and the daemon pings {{operator}} for a job that is fine, so for those say what you are waiting for in the pane before you go quiet.
    - **A run or teammate that has been silent for hours is checked against the MACHINE before anything is killed.** A laptop that went to sleep — the lid closed on battery, or on AC with no external display — stops every process on it at once: the runs, the teammates, kraken's daemon and this session alike, and the stall surfaces hours later as a process that looks hung, a watch that fires the instant the machine wakes, and a "can't reach the API server" error that the daemon records as a transient API error and nudges, when none of it is the process's doing. So before you `kill` anything that went quiet, read the power log around the silence: `pmset -g log | grep -E '^[0-9-]+ [0-9:]+ [-+][0-9]{4} (Sleep|Wake|DarkWake) {2,}' | tail -40` — anchored on the event column, because a bare `grep Sleep` returns tens of thousands of power-assertion lines and the harness shows you only the oldest two kilobytes of them. If the machine was asleep across the silence (read the span as below) — asleep until shortly before now, so the process has not yet had awake time to resume in — it is not hung, it resumes on its own, and it is mid-write when you kill it. Read the span by what each line is followed by: the machine is asleep from a `Sleep` line until the next `Wake` line — `Wake from …` or `Wake … DarkWake to FullWake`, either ends it — while a `DarkWake` is normally a maintenance blip of a few seconds, rarely a few minutes (`pmset` logs one every fifteen minutes or so), answered by the next `Sleep` line, and a `DarkWake` with no `Sleep` after it means the machine is running (on AC, a power assertion such as `caffeinate` holds a dark wake open for hours); a process still quiet well after the `Wake` that ended the sleep is quiet on its own. No `Sleep` line inside the silence means the machine was awake and the silence is the process's own; if the first line printed is later than when the process went quiet, raise the tail. The same read settles what the board saw: a "blocked" flip decided inside a dark wake that a `Sleep` line closed within minutes, and an API error stamped at wake, are the sleep, not the cell.
- **Four rules make that condition honest. The first is yours; the other three belong in the brief you just wrote. Never wait on a path that could already exist**: the agent names are constants and the fix protocol is to re-brief the SAME `athena-<variant>` that flagged, so a reused path is already there from the previous round — wait on it and you read a review written before the fix landed. Suffixing the round (`/tmp/<slug>-<agent-name>-r2.md`) handles that within one run, but round numbers restart, and a repeated `/do` on one slug (a follow-up PR off the recycled branch) reuses the same slug and the same names — so the rule that actually holds is: **delete the path immediately before you spawn or re-brief**, and only then start waiting. That is one command and it is correct in every case, including the ones a naming scheme misses. **The report is written in ONE shot, as the last thing the agent does** — a file built up by a Write and then two Edits satisfies "exists" at its first byte, which hands the lead a half-written review. **And every agent writes its file even when it has nothing to say** — "no blocking findings" is a result, and it is the most common one; if a clean round wrote nothing, a clean round and a dead agent would be the same observation, and the lead would wait on a file that is never coming. **A teammate's final chat message is NOT a delivery channel — what you receive is a contentless `idle (available)` ping — so never close a brief with "your final message is your report"**: the report is the FILE, and the chat reply is one line naming its path.
- **A review round closes on verdicts, not on your own satisfaction — and the tree holds still while it runs.** This binds every review fan-out, delegated or solo-authored — the solo case is the riskiest, since the lead is then both author and closer. Four rules. (1) From dispatching a review fan-out until every variant's verdict lands, the worktree is FROZEN — yours and the crew's: no edit, and no fix brief out mid-round, or the later verdicts describe a tree that no longer exists. The freeze ends at the last verdict, at a death you have positively established per the expiry bullet above — then proceed and say which dimension went unreviewed — or at an operator steer that RETIRES the round's subject outright: when the steer makes the round's subject moot, stop the reviewers, record the round as abandoned-with-reason in `90-build-report.md`, and re-dispatch against what survives (a steer that merely ADDS work does not qualify — fold it after the round closes as before). (2) A verdict is the reviewer's own written CLEAR/BLOCKING in its report file, and you READ that file in full before acting on it: a keyword grep is not reading it (a spelling variant of the verdict slips past the grep), an idle notification is not it (idle fires at every turn boundary), and the tail of the file can be the PREVIOUS round's verdict. (3) `TaskStop` follows the verdict, never your fix: a reviewer asked to confirm a change is stopped only after its confirmation lands, or the round closes with a reviewer of record that never cleared it. (4) A post-verdict edit reopens the round for the dimensions it touches, and ONLY those — shared test infra changed after sign-off ships reviewed by nobody, and "0 blocking findings" then describes a tree older than the one that ships. One carve-out: applying a reviewer's own NON-BLOCKING text fix — a comment wording, a doc line, anything with no behavioural surface, taken verbatim or trivially — is recorded in `90-build-report.md` and does not reopen, because a reopen per prose nit turns the text dimension into a self-feeding loop in which each style round finds only defects the previous fix round's own prose edits created; an edit that touches behaviour, or that rewords a claim in YOUR words rather than the reviewer's, still reopens. The reopened round runs on the settled tree and closes when its re-run returns no blocking finding; record the round count in `90-build-report.md`. The carve-out's escape hatch is the loop arriving as BLOCKING prose: the loop is driven by NEWNESS, not severity — every fix round writes new comments, and new comments are new surface for the next comment-accuracy pass, so consecutive BLOCKING rounds can each target only prose the previous fix round wrote. So when a round's only blocking findings are comment claims on prose that fix rounds themselves introduced, the SECOND such round is the last full re-dispatch: after it, apply the reviewer's comment fixes verbatim under the non-blocking carve-out and record the chain in `90-build-report.md` — a third round of dispatching a reviewer against its own previous fix's wording is the self-feeding loop wearing blocking severity. "Verbatim" has one gap the common case falls straight into: a reviewer that NAMES a prose defect without prescribing replacement text leaves nothing to apply verbatim, and by rule (4)'s letter any authored reword reopens. The lead's MINIMAL authored fix to a textless prose finding lands under the same carve-out, quoted into `90-build-report.md` so the reword is auditable — rule (4)'s reword clause governs edits the reviewer never asked for, not the smallest edit that satisfies an ask the reviewer left textless. All four govern the tree through every revision round at the manual-test gate — the PR (step 8) opens BEFORE that gate, so "after the PR" is not the boundary; a CI fix or a review-comment fix pushed to the open PR under step 8's revision rule is not a reopen unless it changes behaviour, and a behavioural change asked for at the gate always is. What you report to {{operator}} is the round as it happened: a round that returned blocking findings which were then fixed is reported as exactly that, never as "verified clean".
- **The output-file contract does not survive re-delegation on its own.** An agent that was itself correctly briefed — report path, heredoc fallback, write-nothing-under-the-repo — drops those clauses when it writes a brief for its OWN children, and the grandchild's findings strand in a chat reply or never get written. So any brief that permits its agent to spawn further agents says the contract passes down verbatim — every spawned agent gets its own named output file under the same scratch namespace, and the same repo bar — or forbids re-delegation outright. Naming is part of it: an agent below the lead never passes `name:` on an Agent call — the harness refuses the parameter below the lead ("teammates cannot spawn teammates"); its children are its own anonymous subagents, or the work goes back to the lead to spawn properly.
- **A single-dimension review brief's numbered checks stay inside its named dimension.** A brief that says "review one dimension only" and then orders the full `go vet`/`gofmt`/test-suite gate produces three reviewers running three identical suites and the lead reading the same output three times — the fan-out pays for its one distinguishing property, independence of perspective, and then discards it. The suite run is the lead's own verification step (step 6), never a reviewer's checklist item.
- **Every review brief defines the verdict bar in one sentence, verbatim: *BLOCKING means you would not ship the tree as it stands; CLEAR means every remaining item is optional.*** Left undefined, each reviewer invents its own bar and the round-closing machinery keys on a word that means different things per reviewer — two reviewers can find the identical defects and file opposite verdicts. Severity taste is not the test; shippability is. A finding a reviewer would fix before shipping is BLOCKING however small it looks.
- **A safety-classifier stop never turns a reproduced defect into a CLEAR — every review brief says so.** A reviewer probing a security boundary can have a reply stopped by the harness's safety classifier, with an instruction not to produce that content again. Read as "do not report this", the stop silently deletes findings the reviewer had already confirmed: the review comes back CLEAR, states as verified the very thing the stop interrupted, and never mentions that a stop happened, so the lead cannot know its verdict is hollow. The brief line, verbatim: *If a safety classifier stops one of your replies, drop that line of probing, do not reproduce the stopped content in any wording, and carry on with the rest of your dimension. Your report still covers what you had already confirmed: name the component and the class of defect, not the steps, say that a stop occurred and what it left unchecked, and never mark as verified something the stop kept you from checking. A defect you reproduced keeps the verdict it would have had, whether or not you can show the probe. The verdict line stays BLOCKING or CLEAR; while an area is still unchecked, every verdict line you write names it after the verdict word, in this round and any later one.* A report that says a stop occurred leaves that area open whatever its verdict: cover it by a different method — the same probe re-dispatched meets the same stop — or carry it into `90-build-report.md` as unverified and say so in the manual-test gate message.
- **A read-only researcher is forbidden the REPO, not the filesystem — and you have to give it a way to write.** An unnamed in-process subagent spawned to explore rather than to change anything is briefed "write nothing under the repo" — never "do not write any files", which reads as a ban on its own report. It gets the same scratch output path every other agent gets. But the wording is only half of it: **spawn it with an agent type that actually has `Write`.** `Explore` does not have one — its roster is every tool EXCEPT `Write`/`Edit` — so a brief that says "write your full report to `<path>`" is unsatisfiable by construction, and the agent does not report that as a problem: it rationalises a read-only restriction while the lead waits on a file that is never coming. So: use `general-purpose` (or any type whose roster includes `Write`) for a researcher you expect a report from, and add one line to the brief — *if you have no `Write` tool, or `Write` refuses the report path (a harness message like "Subagents should return findings as text" counts), write the file with a Bash heredoc (`cat > <path> <<'EOF'`); "read-only" bars the repo, not your own report.* A researcher with no way to write is a named teammate's job instead. The fallback is for those cases ONLY: a heredoc routes report PROSE through Bash, where a text-matching guardrail hook blocks the whole write because the findings QUOTE a banned command.
- **Every teammate runs on Opus** (`model: opus` — Claude Opus 5): the mechanical component tasks the set already pins down as much as the judgment-heavy ones (ambiguous integration points, cross-cutting refactors, design gaps the set left open). Never drop a teammate to sonnet or haiku to save tokens, and never leave the model unset. The LEAD's own tier is a separate axis and never an argument for lowering a teammate's — your brief states yours, and it is not necessarily your crew's; a lead deliberately placed on a faster tier is placed there precisely because the deep work is the part it delegates.

### 5. Implement

- **A product decision, or a deviation that changes the spec, met mid-build is a QUESTION ROUND — never a default disclosed at the gate.** The round opens when you face a decision that is (a) a product decision — a choice {{operator}} could make the other way that changes what a user sees or may do: a visible default, a refusal vs an allowance, a permission or visibility level, a name on a surface, a cost a user pays — or (b) a technical deviation that changes an obligation the set, the contract or the job spec states: a component the set did not name, a wire or schema change it did not plan, a scope cut, a measured fact that invalidates a stated assumption. The test is aim's own: it is not codebase-answerable, and a different answer builds something different. A decision the set, an answered row, a pane steer or a mental-model item already settles is not a round, and a steering item phrased as a question is still an answer, never a row.
- **Importance decides what blocks, and only a P0 blocks.** P0 is anything that changes the functionality or usage of the core feature the job is about — what a user would do differently — and a spec-changing deviation whose dependent slices are not yet dispatched. Scale decides, not category: a product call that leaves the core feature's functionality and usage as specified is P1 when a reversal is one small commit and P2 when cosmetic, and a deviation whose slices are already built is P1, since it changes the report rather than the build.
- **Batch the round.** The moment a P0 is filed, file every P1/P2 default you are carrying unfiled in the same round, each with its recommendation, so {{operator}} answers in one sitting; a round that would hold only P1/P2 rows is filed and NOT waited on — build on the recommendation. File with `kraken questions add <slug>` (one JSON object on stdin per row: `id`, `text`, `context`, `importance`, `recommendation`; ids continue the set's numbering), per aim's Core Rules.
- **Timing, and the crew.** File a P0 BEFORE the contract freeze or dispatch that depends on it. Mid-fan-out, hold only the dependent slice: teammates on independent slices keep running (their panes vote the cell working until they finish, after which it reads blocked), and nothing is stopped for a round.
- **Stop, and say exactly what the round needs.** After the rows land, run `kraken load set <slug> --unblock 3 --scope <remaining build, 1-10> --note "<the P0 in one line>"` (the load skill's `Mid-build question round` row), end your message with exactly `questions pending: <P0 qids> (P0) · also <other qids, or none> · <what the answer decides, one clause> · answer on the board, then tell me to continue`, and end the turn. Kraken types nothing into the pane when a row is answered, and you never arm a watch to poll the rows — a Monitor votes the cell working and hides the very block you declared.
- **Resume on {{operator}}'s next prompt, whatever it says.** The release is their prompt — `continue`, a steer, or the answer typed into the pane — because the recall hook places every unread answer at the top of it. On it: re-run `kraken questions get <slug>`, apply step 2's two staleness gates (an answer standing on a question whose text you rewrote is history; a later pane steer on the same subject outranks the row), and continue from the held slice. A P0 answered in the pane rather than on the board is removed with `kraken questions remove <slug> <qid>` and recorded in `90-build-report.md` as a decision, so "no open P0" stays true. A prompt that arrives with a P0 still unanswered and not settled by its own text gets the closing line again, never a build on a default.
- **Record every round.** `90-build-report.md`'s Discrepancies section lists each one: the qids, what was held, and how long the block lasted.
- **Where the per-component test plans go depends on whether you delegated.** When you did, `50-components.md`'s unit/integration/e2e plans are the **test authors'** brief input rather than the implementer's checklist — they went into the test authors' briefs in step 4, and what the implementer is held to is `50-contract.md`. **When you implement a slice yourself — including every `solo: true` job — you write its tests from those plans, exactly as before**, because there is no author to write them and an un-delegated slice must not ship untested. On a repeat `/do` for a slug that delegated last time, earlier rounds' blind tests are still in the repo and still asserting — a follow-up is usually small enough to keep for yourself, which is exactly when this is easy to miss — so re-cover what they pin or delete the ones the change deliberately obsoletes, never leave them failing; "deliberately" is the word doing the work, since without it this reads as permission to delete any test your change happens to break. Note in the build report that authorship was not split for it, since you were both parties and the separation the split buys is simply absent.
- Match the project's existing conventions; do not introduce new abstractions the set did not call for.
- **A steering item phrased as a question gets an answer, never an implementation.** A question sitting numbered between two build items ("this restarts on its own, right?") is a request for a yes/no. Answer it in your reply; if the honest answer implies work worth doing, name it as an offer and build it only when {{operator}} converts it into an ask.
- **A destructive command runs ALONE, in its own call, after you re-read it — never inside a compound, and never with its stderr silenced.** Destructive means anything that removes or overwrites state you did not just create: `rm`/`rmdir`, `find … -delete`, `git checkout/restore -- <path>`, and every `--apply`/`--write`/`--prod` invocation of a mutating script. Inside a compound an over-matching delete is hidden behind the other clauses' output, and with stderr silenced a typo'd `cd … 2>/dev/null;` ahead of a mutating script leaves its path resolving by chance. A `find -delete` also needs its match list printed first (`find … -print`) in a separate call — `find` cannot tell tracked from generated, so you look before it deletes.
- **Edit repo files with the Edit tool, never through Bash — the ban is the ROUTE, not one idiom.** A python heredoc's `read_text()/str.replace()/write_text()`, `sed -i`, `perl -pi`/`-0pi`, an `awk > tmp && mv` — every Bash-route in-place rewrite of a repo file is the same banned move, because agents pattern-match the named example and read the unnamed twin as permitted. The Bash route fails SILENTLY: a replacement that matches zero times still writes the file and exits 0, and a script that dies mid-way leaves the file unwritten while the rest of the compound still runs, printing success and a green suite over the unmodified file, `is_error: false`. `Edit` fails the turn loudly when its `old_string` no longer matches, which is the whole difference. **This ban goes into every implementation brief verbatim**, exactly as the shell line above does: it lives in a section only the lead reads, and a lead that forwards the zsh clause and drops this one gets a crew that uses the banned idiom on repo files. And "repo files" means any git checkout, scratch worktrees included: the ban is a property of the idiom, not of the cell worktree.
- Mark each TaskCreate task complete as soon as it is done.
- **A comment may assert a fact about anything outside itself only if you checked it in this session.** Not "it is probably true", not "it reads like the sort of thing that would be true" — you ran the `grep`, the `git show`, the test, in the same turn you wrote the sentence. This is the single most expensive habit the review round catches, and it is a habit of the *comment*, not the code: review rounds routinely flag comments asserting something false about code that is fine. **Two things make this specific rather than a plea for care.** First, the repo's house voice is the cause: comments here explain WHY, including what a thing replaced and what broke before, and an agent imitating that voice with no access to the history will *generate* the history — the style is load-bearing and stays, so the evidence rule is what has to carry the weight. Second, a fix in the same round can *make* a neighbouring comment false, so re-read the comments around every line you change, not just the ones you wrote. If you cannot check a claim, describe what the code does and stop there; a comment that explains less is free, and one that explains wrongly is read as precedent.
- **When you create, move or rename code the set CITES, you update the citation in the same change.** The set's artifacts link into the repo — `path:line` tokens in the mds (`51-code-map.md` is nothing but those), and `data-code` attribute values on the already-rendered diagram fragments — and every one of them is a claim about where code lives that your change can silently falsify. A stale citation is worse than none: it opens the wrong file with the reader's full confidence, and nothing in the pipeline re-checks it, because the lead verified each ref once, before hermes was ever briefed. So after the code lands, grep the set root for the paths you touched and fix what moved. The two surfaces take different edits. A `path:line` token in a markdown artifact is an ordinary `Edit`. A `data-code` value on a fragment is an **attribute-only** `Edit` — changing that one string and nothing else is sanctioned for you, and it is the sole exception to "you never write diagram bodies"; report the fragments you touched so the lead re-lints them and re-wraps the affected cards. Anything beyond the attribute value — a box that should now say something different, a component that moved, an edge that no longer exists — is a change to what the diagram DEPICTS and goes back through `hermes-<diagram-id>`, never through your own hand on the markup.
- **When a change retires a meaning — a symbol, a column, a phrase, a rule — grep the whole repo for its remaining references ONCE, before any review round.** Fix the class in one sweep; reviewers surfacing leftover references one at a time is the most expensive possible form of that grep.
- **Pre-fix verification uses an isolated copy, never `git stash`, and a probe file never lands in the worktree.** Verifying that a test fails without the fix means reconstructing the unfixed tree OUTSIDE the shared one: `git show HEAD:<path>` the changed files into a scratch dir, or — when a probe must compile against unexported symbols — stage the probe file in scratch and map it into the package with `go test -overlay` (a JSON file mapping the in-package path to the scratch copy). Never `git stash` in a worktree other agents share: it sweeps their uncommitted work. And never write a probe into the shared package "briefly": two agents' probes collide while the suite runs over the same tree, and `git status` cannot distinguish never-written from written-and-deleted, so a "worktree left clean" report proves nothing. For a whole-suite baseline — proving failures pre-existing rather than asserting it — the clean form is a throwaway `git worktree add` at pristine HEAD with the cell's venv symlinked in, run, compared, removed: it never touches the shared tree. **This bullet's rules go into every implementer brief verbatim, exactly as the dialect line and the Edit-tool ban do**: stated only here, they reach the lead and nobody else, and each implementer then invents its own baseline method. The brief line: *never `git stash` (mutating forms are hook-blocked in cells); never write a probe or scratch file into the repo; baseline via `git show HEAD:<path>` into scratch or a throwaway `git worktree add`.*
- **Never write an incident history for something that never happened.** A defect caught in review, in an uncommitted tree, has no incident; a comment that says it "shipped" reads to the next maintainer as a post-mortem of a real outage, and gets cited as one. Say what the guard prevents, not a story about the time it didn't.

### 6. Verify Against The Set

- Run `52-testing-plan.md`'s checks that are practical locally (unit tests, type checks, targeted integration tests).
- **Your verification gate is the CI command, over the CI scope, on the CI merge base.** Every axis you narrow is an axis CI fails on after the PR opens: a targeted file list instead of the package, a type check that skips the test files, a suite run against the cell branch's stale base instead of latest main — each a different axis, so no single habit covers them. Run what CI runs, from where CI runs it.
- **Never filter a suite's output through `head`.** `go test ./... | grep -v "^ok" | head -5` reports GREEN over a red suite when the five-line window fills with benign log noise and the `FAIL` line falls outside it — and a package is noisy exactly when something is wrong, so the truncation inverts the answer precisely when it matters. Use the count form (`… 2>&1 | grep -cv "^ok"` — a count cannot truncate; a non-zero count is the signal to read the FULL output, since test-free packages and stray log lines count too) or read the full output directly.
- For UI changes, drive the feature in a browser before reporting done — and drive it: click, type, navigate every surface the change touches, and say which interactions you performed. A page that renders is not a feature that works, and "I loaded it" satisfies the letter of this step while establishing nothing.
- **A taste-gated change goes in front of {{operator}} BEFORE the review fan-out.** When the acceptance criterion is how it looks, sounds or feels — cursor art, a colour, a sound kit, anything {{operator}} phrased "let's try" — the deciding input is their eyes, and a review round run first is paid for on an artifact they may retire on sight. Drive it, put the URL or screenshot in front of them at the manual-test gate's early form, and dispatch the review on whatever survives their look. The review still runs — after the taste decision, not before it.
- **Browser mechanics, so you do not rediscover them.** Drive only the surfaces your change touches, and never a destructive one against live state — the kraken dev board proxies to the real `kraken serve` and the real `kraken.db`, so Done, Archive, Stop, Reactivate and Update act on other people's live jobs; exercise those against a job you made for the test, or read-only (open the confirm, do not confirm), and say under Verification what you could not drive safely. Browser work is the LEAD's step and singular: the MCP server drives one browser with one profile, so two agents doing it at once interleave on the same tab and read as flaky UI. Use the `playwright` tools, not `claude-in-chrome` — that one drives {{operator}}'s own Chrome through an extension whose per-site permission nobody is present to grant — and load them in one `ToolSearch` call. (`/aim` and `/info` say "there is no browser in a cell"; that is about `open` launching the operator's desktop browser with nobody watching, not about this one.) Two refusals are worth knowing before you hit them, because the workaround for each is a line. **`file:` URLs are blocked** — `browser_navigate` refuses the scheme outright, so serve the directory instead: `python3 -u -m http.server 0 --bind 127.0.0.1 --directory <dir>` under `run_in_background: true`, and READ BACK the port it prints (`Serving HTTP on 127.0.0.1 port 54321`) — a fixed port that is already taken dies with `Address already in use`, which backgrounded is invisible, and you then verify whatever another cell is serving. The `-u` is load-bearing rather than decoration: without it CPython block-buffers stdout when it is not a TTY, so with an ephemeral port the one line that tells you the port never reaches the log at all. **A screenshot may only be written inside the worktree** — the allowed roots are the worktree and its `.playwright-mcp/`, so `/tmp`, your scratchpad and `<cellDir>/artifacts/` (a sibling of the worktree, not under it) are all refused. Omit `filename` and the shot lands in `.playwright-mcp/` on its own; the tool result names the path it wrote, so copy from that rather than assuming it. `.playwright-mcp/` is gitignored in kraken but not in most repos a cell targets — copy out what {{operator}} should see, then `git check-ignore -q .playwright-mcp/ || rm -rf .playwright-mcp/` before the PR step — `check-ignore` exits 1 when the path is NOT ignored, so that one line is the whole guard and is a no-op in the repos that do ignore it. Do not add it to the target repo's `.gitignore` (that is a change to the repo, not to your change), and never write `.git/info/exclude` — in a worktree that resolves to the shared common dir and edits the operator's main checkout.
- If a check is not runnable locally, say so explicitly.

### 7. Write The Build Report

Always write **one brief artifact** recording what actually happened: `90-build-report.md` in the set root (in a kraken cell: `<cellDir>/artifacts/90-build-report.md`). Like every md artifact, it opens with a one-liner stating its main message — the headline delta between plan and reality, or "shipped as planned" when that is the truth — before any section, so a reader who stops there still has the point. Never hard-wrap its prose: one paragraph — and one bullet, and one table row — is ONE source line, however long; a mid-sentence line break renders as a broken paragraph on the board. The `90` band sorts it last, after the overview, the cards, and the section docs. Write it even when the implementation went exactly to plan, and even when there was no `/aim` set to begin with (a job spec implemented directly is still a plan reality can diverge from).

Keep it to a page. It is a record of the *delta between plan and reality*, not a second copy of the set — link to `00-overview.md` rather than restating it. Sections, in order:

| Section | Content |
|---|---|
| What shipped | One row/bullet per component or slice, each naming the files it landed in. Terse. |
| The join | How many blind tests were authored, how many failed on the first run, and the verdict for each (code bug / test bug / contract defect). Zero failures is a finding, not a clean bill — say so. When nothing was delegated, one line saying so is the content; never drop the row. |
| Discrepancies vs. the plan | **The point of this artifact.** Every place reality diverged from the set (or the job spec): what the plan said, what you did instead, and why — and every question round (step 5), with its qids, what was held and how long the block lasted, plus any P0 answered in the pane and removed from the rows. Wrong assumption in the spec, an API that doesn't work as described, a component that turned out unnecessary, a boundary drawn in the wrong place — all of it. If nothing diverged, write "None" as an explicit line; never omit the section. |
| Artifacts invalidated | Every phase-1 artifact the implementation CONTRADICTED — a diagram card still depicting a design this phase deleted, an overview claim the code now falsifies — with what each now claims wrongly. The flat set makes every card independently shareable, which is exactly what makes a stale one dangerous, and the most expensive artifacts (rendered diagrams) are the ones a reversal is most tempting to leave un-retouched. Re-check the diagram cards' claims against the shipped design before writing this row; "None" spelled out when the set survived intact. |
| Complications | What fought back and how it was resolved or worked around — flaky/blocked tests, missing fixtures, ordering constraints, an unrelated bug hit on the way. Include ones you resolved; they are the cheap warning for the next person. |
| Deferred | Scope deliberately left out, each with the reason and what it would take. Includes P1/P2 questions that stayed open. |
| Verification | What was actually run and its result, plus anything that could not be run locally. |

Uncomfortable findings belong here in plain words: a spec section that turned out wrong, a decision that made the implementation awkward, an estimate that was off. A build report that reads like the plan was perfect is a report that isn't worth writing.

Two truthfulness rules, because this is the one artifact NO review round covers — the athenas review the code diff, the report is written after they are torn down, and a false claim in it is read by {{operator}} and by every later job as fact. First, every factual claim in it gets the same evidence bar as a code comment: checked this session, in the raw, not recalled — never claim the manual-test gate verified something it did not, and never understate a stall your own transcript records. Second, when anything changes after the report is first written — a revert, a late steer, a fix round — re-READ the whole report and correct it as a document, never by grepping it for sentences that mention the changed thing: a patch pass that hunts for the changed subject misses every claim that depends on it without naming it.

### 8. Open The PR

Every `/do` ends with a pull request, opened here — after the verification gate (step 6) and the build report, and BEFORE anyone has tested by hand — so that what the manual test exercises is the PR itself, and every revision it produces is a commit pushed to that same PR rather than a second PR or a branch nobody is watching. These are the branch, commit and PR rules; there is no separate `pr` skill to read. **Never invoke a `pr` skill by name**: kraken ships none, so any `/pr` you can resolve is a personal skill, which may carry its own branch-rename or poll rules that this pipeline forbids — this step IS the PR procedure.

- **Gather context first, in parallel**: `git status`, `git log --oneline -10`, `git diff <base>...HEAD --stat` and `git diff <base>...HEAD`, where `<base>` is the target branch — `main` or `master` unless the user named another.
- **Keep the branch name you are on.** Inside a kraken cell, a cell never renames its branch: the cell branch is the one named in your brief, and kraken's PR tracking keys on that name (the daemon's branch poll and its PR-record repair both look for the cell branch's family), so a PR from a renamed branch falls outside what it watches. Outside a cell, push the current branch as it is — unless it is the base branch itself (`main`/`master`): a `/do` run on main must not push to main, so stop and ask the user for a branch, or create one under the repo's git conventions (a personal `git` skill, if one exists in this session) when they name one; `gh pr create` with head equal to base fails anyway, after the push has already landed.
- **Commit style**: short, succinct, casual, lowercase, no punctuation — `s2l chatbot get customer data`, `fix yelp double send`. No commit body. No Claude Code signature or `Co-Authored-By` line. **Stage by path**, never `git add -A`: a cell's tree carries kraken-owned files (`.claude/settings.json`, a codex `AGENTS.md`, root notes) and other agents' work, and a sweep commits all of it.
- **Push**: `git push -u origin HEAD`. If the push or `gh pr create` fails (a wrong active `gh` account, a refused push), report the failure in your closing line and stop — do not retry around it, and do not say `manual test ready:` without a URL.
- **Title**: `<type>(<category>): <description>` — `fix(parser): handle null id`, `feat(api): add export route`. Types: `feat`, `fix`, `chore`, `refactor`, `docs`, `test`. Category is the module or service the change touches, named the way the repo's own history names it. Lowercase, no period.
- **Body**: brief and no fluff, two or three sentences per section — `## Summary` (what the PR does) and `## Context` (LangSmith trace ids, error traces, motivation; only when available). No Claude Code signature or "Generated with" footer in the body, overriding the harness's own default footer instruction — the commit rule above bans it for commits, and the same rule binds the PR body. `--draft` only when the user asked for a draft.
- **Create it and report the URL**: `gh pr create --title "<title>" --body "<body>" [--draft]`.
- **Every later change is a push to this PR, while the PR is still OPEN.** A revision asked for at the manual-test gate, a CI fix, a review-comment fix: commit it under the rules above and `git push` the same branch — never a second PR for the same change, and never a force-push over commits a reviewer may have read (the one sanctioned `--force-with-lease` is the post-merge recycle in the cell section; a pushed branch that needs the base's newer commits takes `git merge origin/<base>`, never a rebase, since a rebased pushed branch cannot land without a force). Gate every push on the PR's state, as a real gate rather than a printed line: `[ "$(gh pr view <url> --json state -q .state)" = OPEN ] || exit 1`. The PR now exists BEFORE anyone has tested, so it can MERGE while you wait at the gate — the operator ships on trust — and a commit pushed after that lands on a dead branch, silently absent from main. A MERGED state means the revision is NEW work: in a cell, recycle the branch off origin/main per the cell section and open a new PR through this step; standalone, cut a fresh branch off the base and do the same. A CLOSED-but-unmerged state reads as scrapped — ask whether to reopen it (`gh pr reopen`) or start fresh, and push nothing until answered. Re-run the verification gate before every push, and re-read `90-build-report.md` as a document after every revision (Write The Build Report's second truthfulness rule) — a report written before the revision describes a tree that no longer ships.
- **Polling the PR.** Inside a kraken cell, never: the daemon watches it (cell section below). Outside a cell: if the user's original message clearly asked for it ("create a PR and watch it", "ship this", "create and poll"), use the `poll-pr` skill with the PR URL; if it clearly asked for none ("just create the PR", "draft only", "don't watch it"), do not; if unclear, ask whether to poll the PR until green.

### 9. Report Back

- **Search {{operator}}'s mental model before writing the report or the summary** — `kraken mm get --q "<subject>"` (a case-insensitive substring over every live item's title, body and quote), then `kraken mm show <id>` for every relevant hit and `kraken mm source <id>` only when the body is not enough — and should an item contradict another item or the transcript, run `kraken mm flag --item <id> --note "<what contradicts what>"` and proceed (a teammate names the flag id in its report; zeus, the lead, is the only agent that raises or dismisses a flag, with `kraken mm flag raise|dismiss <id> --note …`, before its next stop, saying so in its final message): abstract what they already know, spell out what they are unfamiliar with. Mandated, not suggested — agents do not pull spontaneously. This binds `90-build-report.md`'s prose too. Spell them `kraken`, never `k`, each as its own command: a repo's own kubectl guardrail can block any compound containing a bare `k` and kills everything bundled with it. The per-file half is equally mandated: before explaining a file or citing a code ref in anything {{operator}} reads, run `kraken mm get --file <path>` for that file — the exact lines they have read there decide whether the reference gets a clause or a walkthrough — and any teammate brief that produces operator-facing prose citing code carries the same mandate.
- One short summary in chat: what shipped, which P0 answers shaped it, what verification was run, the PR URL, and the headline discrepancy if there was one.
- Link `90-build-report.md` and `00-overview.md` — do not re-summarize either in chat.

### 10. Clean Up Agents

Stop each agent as soon as its output is ACCEPTED — an implementation slice once the join has produced no `code bug` against it **and** the review round has cleared it, not the moment it reports done, since a blocking finding has to go back to that same teammate. Both gates come after the barrier, which fires only when the LAST slice reports; a slice stopped before then leaves nothing to send an early `code bug` back to. By the time verification passes and the report is written, tear down anything still resident:

- **Teammates (named `Agent` spawns)**: stop each still-running teammate with `TaskStop`, addressing it by its bare name (or `name@team` if the name is ambiguous across teams). That releases its tmux pane. There is no team-delete step — a team with no live members is already gone.
- **Unnamed background subagents / tasks (Agent, Workflow)**: stop any that are no longer needed with `TaskStop`, addressing them by task id — the id from the spawn result, or from the task notification one fires when it stops. **`TaskList` cannot see a background agent**: it lists the `TaskCreate` plan board, which is a different thing that happens to share the word (the same reason step 4 says it cannot tell a dead agent from a slow one). Nor are the stop notifications a reliable inventory on their own: an agent that dies mid-answer may never fire one, and an unnamed subagent has no pane, so the `kraken ls` fallback step 4 leans on does not apply to it either. So **write the ids down as you spawn** — in your scratch dir, not only in context, which a compaction or a resumed session will not preserve. Nothing anywhere will re-derive them for you.
- **Armed watches are residents too.** A background until-loop or Monitor watch that was waiting on a round outlives it silently — stop it when the round it watched closes, alongside the agents it watched. An orphaned watch's late "stopped, no completion record" notice is not free: notifications queue indefinitely, and one that flushes into a session whose cache has expired costs a full context re-cache to say "no action". The watch ids are background task ids like any other: write them down as you arm them, same rule as the spawn ids above.
- Do this even when implementation failed or was cut short — a partial run must not leave orphaned agents behind.
- Exception: if a teammate is mid-way through work the user explicitly asked to keep running (e.g. a long verification job), say so in the report instead of killing it.

## Inside A Kraken Cell

When a kraken job brief sends you here, these deltas apply — the brief wins wherever it is more specific, and it is the only place the cell's real paths appear:

- **There may be no artifact set at all.** Skipping the doc phase is a kraken job's default: when Phase 1 never ran, the JOB SPEC is the contract and it is what you implement, exactly as written. The Preconditions refusal above applies to standalone `/do`, not here — a cell with no set root is the normal case, not an error.
- **The crew is the brief's crew, and the crew are TEAMMATES.** Implementation slices go to teammates named hephaestus — which write no tests for the spec — with athena-logic and athena-edge authoring those tests blind from `50-contract.md` and athena-style joining them for the three-dimension review: athena-logic checks correctness, bugs, and scalability; athena-edge checks edge cases and boundary conditions; athena-style checks stylistic standards, best practices, and CLAUDE.md compliance. The brief owns the crew's IDENTITY — what makes an agent a teammate, when delegating is worth it at all, the teardown-on-acceptance principle, and the solo case — so read it there rather than re-deriving it here; the dispatch, join, arbitration and review CHOREOGRAPHY is this file's (step 4 above), applied in a cell with the names bound as this bullet says. Three cell-specific bindings on top of step 4: the review round is dispatched in parallel in one message, and — since SendMessage resumes a live teammate — it is **ONE new Agent call, not three**: the two blind authors are resumed with single-dimension reviewer briefs (never hephaestus' brief) and only athena-style is fresh. On a blocking finding, the fix brief goes back to the same hephaestus by name, and the re-review runs with **only the flagging variant(s)** — not all three. And hold every hephaestus until BOTH gates have cleared its slice — the join first, then the review round, which is the later one and so the one that releases it. What the brief does NOT carry is the output-file contract above: every hephaestus and athena brief still names its agent's scratch report path, and you still wait on that file rather than on a sleep — in a cell the lead's own pane is the channel {{operator}} reads, so a review that exists only as a truncated chat reply is lost to both of you.
- **Write `90-build-report.md` into the brief's SET ROOT** (`<cellDir>/artifacts/`), per Write The Build Report above. It is written on EVERY phase 2, including a job that never had an artifact set — a job spec is still a plan reality can diverge from.
- **Open the PR, then stop at the manual-test gate.** After the tests and linters pass and the report is written, open the PR per step 8 — a cell's `/do` ALWAYS ends in a PR, whatever the manual test later says, so there is never a "PR step" waiting behind the gate — then say:

  `manual test ready: <PR url> · <urls + what to try>`

  and STOP (end the turn). {{operator}}'s reply is what passes the gate. **When the gate involves a process listening on a port** — a parallel server, a dev server, a tunnel — register every such URL FIRST, before that line, with `kraken stack add <slug> <url> --label <short name>` (one call per service; `kraken stack get <slug>` reads them back): the board renders each as a clickable chip on the card beside the PR chips, and dims it when the port stops listening, which is how {{operator}} reaches your stack without parsing the line. The line still lists the URLs in prose, since the status text has to stand on its own. A gate that involves no port — a CLI to run, a file to read, an iOS build — registers nothing; that is fine and common. A reply that asks for changes is a revision round, not a new job: make the change (a behavioural change reopens the review for the dimensions it touches, per step 4's post-verdict rule; a CI fix or a review-comment fix does not unless it changes behaviour, and a prose nit with no behavioural surface lands under the same carve-out that rule gives a reviewer's textless finding), re-run the gate, re-read the build report as a document, commit and push to the SAME PR under step 8's revision rule — which includes its OPEN-state gate, since the PR may have merged while you waited — and say `manual test ready:` again naming what changed. A reply that scraps the change leaves an open PR behind: close it (`gh pr close <url>`), say so, and stop. **When their reply passes it**, shut any test services down, run `kraken stack clear <slug>` so the chips go with them (`kraken stack rm <slug> <url-or-label>` for one service you stopped early), and STOP — the PR is already open and awaiting checks, and there is nothing left for you to open.
- **A question round stops the cell the way the gate does.** Step 5's `questions pending:` line is the card's detail text while a P0 waits; {{operator}} answers on the board and then prompts the pane, and that prompt is the release. Kraken never wakes a cell for a question — the operator's decision — so the only daemon-side sign of a round is the blocked notification naming the open P0, and a round nobody steers stays blocked.
- **PRs are per-slice, not per-job.** Kraken records every PR opened from the cell's branch on the job's board, and a PR merging NEVER ends the job — teardown happens only when {{operator}} accepts it from the board.
- **You never need to report the URL for the board's sake.** A PostToolUse hook attaches each PR the instant `gh pr create` returns — confirm from that command's output (or the board) that it did, since `/api/pr-attach` refuses a PR whose repo is not the job's — then report it to {{operator}} anyway in the `manual test ready:` line, noting it as awaiting checks.
- **Never poll your own PR.** Kraken's daemon watches every open PR of the job's cell for failing CI or new comments and bumps your pane when either happens — when bumped: fix failing CI, and address new review comments per the repo conventions; do this only once bumped, not preemptively, and push the fix to the same PR under step 8's revision rule. The PR is open while the manual-test gate is, so a bump usually lands on a zeus stopped at that gate: after the fix, close with the `manual test ready:` line again — your last message is the card's detail line, and "fixed CI, pushed" would erase the instructions {{operator}} needs. If no bump ever arrives, the job is NOT done silently — the PR simply stays awaiting checks. Polling your own PR from inside the cell duplicates the daemon's job and wastes the turn.
- **Recycle the branch after a merge.** If a PR of yours merges and more work arrives, reset the branch before starting it — `git fetch origin && git checkout -B <cell branch> origin/main` — then ship the follow-up as a new PR through step 8 again. The cell branch is the one named in your brief. Two shapes of the recycle that read as breakage and are not: a `git push --force-with-lease` failing with `(stale info)`, or a `git fetch origin <branch>` failing with `couldn't find remote ref`, mean the merge auto-deleted the remote branch and your remote-tracking ref is stale — run `git remote prune origin` first. And an instruction that your branch "is behind" main may itself be stale: check `gh pr view --json state` FIRST — a branch whose PR already MERGED is contained in main, not behind it, and rebasing it replays already-merged commits into spurious conflicts; the recycle above is the correct move.
- **A post-merge steer is still gated.** After a PR merges, the pipeline has no gate left — the manual-test gate is behind you and the PR is closed — so a pasted CI failure or deploy error on merged work arrives in the one phase with nothing between you and production. A bare log paste with no verb is equally readable as "FYI", "diagnose this", and "make it green by any means"; read it as DIAGNOSE. Diagnose freely, but any production mutation — a deploy, a cloud env or secret change, a machine-wide identity switch (`gcloud config set account`, `vercel deploy --prod`) — still gets an explicit ask first, exactly as the manual-test gate would have: name the one action you propose, then stop for {{operator}}'s yes.
- **A commit that restores something upstream removed names its culprit from `git log -S`, never from reading the current code.** Run `git log -S'<the exact removed text>' -- <file>` and cite the commit that actually deleted it; pattern-matching "what recently touched this area" files a regression against an innocent PR in a commit subject that is then permanent on main. An unverified culprit in a commit subject is worse than none.
- **Rebasing with kraken's own dirt in the tree.** A rebase is for history that has not been pushed; a cell branch with an open PR takes `git merge origin/<base>` instead (step 8), so this bullet applies before the first push or on a freshly recycled branch. In repos that TRACK `.claude/settings.json`, kraken's per-cell settings merge leaves a permanent ` M .claude/settings.json` line, so `git rebase` refuses with "cannot rebase: You have unstaged changes" on a tree where every changed file is kraken's. The sanctioned dance: `cp .claude/settings.json <scratch path outside the repo>`, `git checkout -- .claude/settings.json`, rebase, then `cp` it back.
